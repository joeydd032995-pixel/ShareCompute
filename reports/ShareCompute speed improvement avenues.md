# Measure first: cheap fixes outrank speculation

The source report's ranking does not survive ShareCompute's own byte counts and timings. **Speculative decoding and expert parallelism, its headline levers, belong near the bottom of the queue; activation quantization should be dropped; live re-balancing should shrink to planning at epoch boundaries.** Three unglamorous items rise to the top: per-node compute timing plus Wi-Fi round-trip measurement (neither has ever been done), a CPU build baseline that CI logs show has no dot-product/i8mm on either phone and whose CMake file forces AVX/AVX2/FMA off for x86, and removal of the logits return. Per-token traffic is **92.7% F32 logits (0.608 MB) and 6.2% activations (~8 KB per hop)** ([F49](../findings.md)), so Q8_0 activations save about **3.5 ms** of a ~730 ms token while backend sampling would save about **101 ms** at 48 Mbit/s, a derived figure for a path nobody has run over RPC. The network is still not the main cost: its modelled ~118 ms explains only **29–41% of the gap** between loopback (0.44 s/token) and physical decode (0.73–0.85 s/token), so deleting every network byte yields at most **+16–19%**, and roughly 0.3–0.6 s/token of unmeasured compute and overhead remains. The report's speculation numbers (3.4x, 1.5–2.0x, 1.9x MTP) are real but narrow: the first is a 27B model on an M3 Ultra GPU, a 0.5B draft model on the laptop cannot break even at its measured 0.65 s per draft token, and only draftless n-gram speculation is plausible, on repetitive text, where it collides with backend sampling over the very logits it needs. MoE helps only as a small-active model run through the existing layer split. Nothing was built or run for this report; every projected gain below is derived or unverified, and the closing plan orders the cheapest measurements first.

## Measured against F43–F51, the report's headline bets rank near the bottom

I did not have the supplied report's text; its claims here are as quoted in the assignment and in the seven research notes (tagged SPEC, DIST, TRAFFIC, PHONE, PLAN, MOE and OVERLAP below). Evidence is graded **V** (measured in the project, read in CI logs, or read in repository or pinned-llama.cpp source), **S** (secondhand: a fetch tool's summary of a PR, paper or page, which covers nearly every external number), **D** (arithmetic on cited inputs) and **U** (unverified). All physical evidence is one 16-token factual prompt with a 5-token prefill on one home Wi-Fi network, and the 0.44 s/token figure is the Linux **loopback** decode (7,027 ms over 16 tokens), not a physical one; physical decode is 11,624 ms cold and 13,621 ms warm, i.e. 0.73 and 0.85 s/token ([F43](../findings.md); TRAFFIC).

## Where the 0.73–0.85 s goes: logits dominate the bytes, but compute dominates the time

### Logits are 93% of the traffic, yet the network explains only 29–41% of the slowdown

The counting proxy on the 3B Q8_0 layer split measured 0.011/0.011/0.010 MB client-to-worker and 0.008/0.008/**0.608 MB** worker-to-client per token on links 1/2/3, because the output layer sits on the last endpoint and returns 151,936 F32 logits; activations are about 8 KB per hop, inferred from size ([F49](../findings.md); TRAFFIC) [V]. Five activation crossings total 40,960 B against 607,744 B of logits [D]. At the phones' measured 6.1 MB/s weight-upload rate the logits cost **101 ms** per token and all activations 4.7 ms, so Q8_0 saves 3.45 ms (F16 2.35 ms), **29x less than removing the logits** [D]. That rate was measured laptop-to-phone; the phone-to-laptop rate logits actually travel is unmeasured, and the relay's 27 MB/s ceiling would shrink the same term to 22.5 ms. Quantizing activations also breaks the bit-exact token gate and meets the residual stream's "massive activations" of 10^3–10^4x the median (2,622 against 0.2 in LLaMA2-7B), which a 32-element Q8_0 block scale would flatten ([Sun et al.](https://arxiv.org/abs/2402.17762)) [S]; Petals' "no noticeable effect" is for 176B-class models and a different quantiser ([Petals](https://arxiv.org/abs/2312.08361)) [S]. No fork or PR quantizes activations over RPC; the only reduced-precision wire path is a BF16 cast inside a two-rank server-to-server all-reduce that a star topology cannot use ([PR #26610](https://github.com/ggml-org/llama.cpp/pull/26610)) [S]. The "~2x from community patches" for graph caching could not be traced to any source: the measured gains in the original PR are +1% to +24.5% ([PR #15405](https://github.com/ggml-org/llama.cpp/pull/15405)) [S], the mechanism is already in the pin, and the 11 KB of upstream bytes per link is far too small for a re-serialised graph, so reuse is evidently active [D, not instrumented].

The decomposition is where the network case weakens. Physical decode exceeds loopback by 287 ms (cold) and 412 ms (warm); the modelled network cost (101 ms logits + 5 ms activations + ~11 ms RTT ≈ **118 ms**, 16% of the token) explains **41% and 29%** of those gaps, and removing it entirely lifts 1.38 tok/s to at most 1.64 (+19%) cold, +16% warm [D] (TRAFFIC). Four qualifiers cut both ways. The 11 ms RTT is F49's emulation (1, 5 and 5 ms), never a measurement. The loopback baseline ran on a 4-core Xeon, so the gap also contains a CPU difference; if the 0.50 s loopback re-run in F49 is used instead of 0.44 s, the network share becomes 34–52% [D] (OVERLAP). F49's emulated link added roughly 0.05–0.15 s to decode, matching the 118 ms in magnitude, but it used the same assumed rates, so it checks the arithmetic rather than reality, and F49 itself judged the emulation about 1.5x pessimistic on whole-loop time. And the device holding the output layer changes by run: the iPhone in F43, possibly the Android phone in F48 (TRAFFIC).

Backend sampling is the right first network lever on paper. It was merged on 2026-01-04 and is in the pin: the greedy sampler is a single `ggml_argmax`, the chain is built for the buffer type of the output device, and the full-logits host copy is skipped when every sequence has a sampler, leaving a 4-byte token ([PR #17004](https://github.com/ggml-org/llama.cpp/pull/17004); pinned `llama.h`) [V for the API, S for the RPC reading]. Nobody has run it over RPC, it is marked EXPERIMENTAL, and four risks are open: the sampler nodes could defeat graph reuse and flip `GRAPH_RECOMPUTE` back to a full `GRAPH_COMPUTE` (+0.1–0.3 MB per link per token, enough to erase the saving); RPC's `supports_op` returns true unconditionally, so a missing kernel is an uncatchable worker abort rather than a fallback; argmax tie-breaking must match the CPU greedy sampler to keep tokens equal; and it is documented as one output per sequence per batch. The configuration-only fallback, `n_gpu_layers = n_layer` to put the head on the laptop, nets −45 to −83 ms at 48 Mbit/s but adds 315 MiB to a laptop whose free RAM bottomed at 89.2 MiB ([F45](../findings.md); TRAFFIC) [D]. Once the logits are gone the remaining ~0.03 MB per token makes every bandwidth change worth under 5 ms, so a faster phone link (worth 83 ms today) then buys only latency.

Latency is the one network term that could be much larger than modelled. The Android app logs `wifilock_skipped: inert from API 34` in every physical run, and Android's low-latency Wi-Fi mode applies only with the screen on and the app in the foreground ([AOSP](https://source.android.com/docs/core/connect/wifi-low-latency)) [V/S]. Each phone is busy about a third of every token, so a radio that dozes between stages could add a 0–102 ms beacon wait per phone per token, about 100 ms in total, the same size as the logits cost. This is a hypothesis with a clean test (ping each phone at 0.5 s spacing during a decode and look for 0–100 ms jitter), not a finding (TRAFFIC) [U].

### The builds forgo dot-product and AVX kernels, and nobody has timed a node

Subtract the modelled network (~0.12 s) and the phones' DRAM-bandwidth floors (0.03–0.07 s for the iPhone stage, 0.12–0.17 s for the Android stage, from soft bandwidth figures) from the 0.73–0.85 s token, and **roughly 0.3–0.6 s per token** remains for the laptop stage, the host and relay path, phone compute above its floor, and radio wake-up [D] (PHONE; TRAFFIC). The laptop is the prime suspect. It is a 2-core AMD A9-9420e that runs the relay and its worker on the same two cores, and it needed 0.62–0.73 s per token to run the whole 0.5B model alone ([F37](../findings.md); SPEC). Its 3B stage, layers 0–6, holds 562 MiB of Q8_0, about 555 M weights, nearly the same arithmetic as the 0.5B model's 630 M parameters, so the laptop stage plausibly takes several tenths of a second [D, U; the Q8_0 and Q4_K_M kernels differ]. No per-node compute time has ever been recorded, which is why this stays a hypothesis.

The build evidence is the strongest new fact in the notes. ggml's configure step in CI run 38992359364 reports `HAVE_DOTPROD`, `HAVE_MATMUL_INT8`, `HAVE_FP16_VECTOR_ARITHMETIC`, `HAVE_SVE` and `HAVE_SME` all failed for both the Android and iOS device jobs, with only `HAVE_FMA` succeeding ([Actions run](https://github.com/joeydd032995-pixel/ShareCompute/actions/runs/38992359364); PHONE) [V]. CPU dispatch is compile-time at the pin, so with `GGML_NATIVE` off and no `GGML_CPU_ARM_ARCH` the build adds no `-march`, dot products are emulated with `vmull_s8` plus `vpaddlq_s16`, and the two-row i8mm path is compiled out ([pinned ggml-cpu CMake](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-cpu/CMakeLists.txt); [arm quants.c](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-cpu/arch/arm/quants.c)) [V, source read]. For x86 I read `native/split/CMakeLists.txt:17-20`: it unconditionally forces `GGML_NATIVE`, `GGML_AVX`, `GGML_AVX2`, `GGML_AVX512`, `GGML_FMA`, `GGML_F16C` and `GGML_BMI2` off on every platform [V]; what instruction set the shipped Windows binary actually runs is unconfirmed, because its logs contain no `system_info` line [U]. The same forced-off flags build the Linux loopback runs, so loopback numbers will move too.

This is "potentially the cheapest, largest speedup", and the qualifiers matter. Upstream's Android guide calls the portable baseline a deliberate portability choice ([docs/android.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/docs/android.md)), so it is a decision to revisit rather than an oversight. The gain is lopsided: large for multi-token work (prefill, speculative verification), modest for one-token phone decode, which is DRAM-bound; PHONE estimates the Android stage's emulated dot-product compute (~0.07 s) at the same order as its memory floor (0.12–0.17 s) [U]. The laptop may gain the most, if its stage is compute-bound and its CPU supports AVX2 (my recollection is that Excavator-class cores do, but nothing in the project confirms it) [U]. Five things must be verified before trusting any of this: the CPU feature lists (Android `Features` for all eight cores, iOS `hw.optional.arm.*`, laptop cpuid), none of which was ever logged; the ISA of the shipped x86 binary; a decode A/B with and without each flag; token equality against `reference-capacity.json` afterwards, since accumulation order changes and F37/F40 already record near-tie drift; and SIGILL risk, because the iOS deployment target is 16.0 (an i8mm baseline crashes on A11–A14) and Android needs a pre-start feature check. The usual larger win, Q4 repack or KleidiAI, is blocked over RPC because the server's `init_tensor` refuses tensors carrying backend "extra" data (`ggml-rpc.cpp:1570-1574` at the pin), which would take a fourth carried patch [V, source read].

Other compute levers do not pay on this evidence. Both phones run a literal two threads, equal to their big-core count, and affinity is never set; a thread sweep (2/4/6/8) is unmeasured (PHONE). No GPU or NPU path has been shown on the moto g's Snapdragon 4 Gen 1 (a secondary-source identification): OpenCL's doc says Adreno 6xx phones are "likely not supported", Hexagon targets v73–v81, and the Vulkan reports on Adreno are slower than CPU or wrong ([OpenCL doc](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/docs/backend/OPENCL.md); [issue #20603](https://github.com/ggml-org/llama.cpp/issues/20603)) [S]. Metal on the iPhone 16e is bounded by an iPhone stage of only ~0.03–0.07 s and by RPC's lack of per-op CPU fallback [D]. A Q4-class file would read 1.9x fewer bytes (4.5 against 8.5 bits per weight) but reverses F40's deliberate choice of Q8_0 to prove pooling and needs a new token reference [D]. Every thermal sample on both phones in every physical run was nominal, and the GPU throttling studies (−44% for an iPhone 16 Pro) do not transfer to a CPU worker at this duty cycle ([arXiv 2603.23640](https://arxiv.org/html/2603.23640v1)) [S].

## Speculative decoding's headline numbers belong to GPUs, not to this pipeline

**Claim 1, 3.4x on Apple Silicon after v0.6.0, is real and narrow.** The figure traces to PR #29869 (merged 2026-10-05): Qwen3.8-27B Q4_0 with a Q8_0 DFlash2 drafter on an M3 Ultra GPU, server decode, median of 5, code prompts at temperature 0, 110.0 t/s against ~32 t/s serial. The same table gives about 1.9x for prose at T=0, 2.5x for code at T=1 and 1.5x for prose at T=1; it is author-reported, and before the new kernels speculation on Metal was slower than serial ([PR #29869](https://github.com/ggml-org/llama.cpp/pull/29869)) [S]. The v0.6.0 release notes say "up to ~3x faster mat-mul", not 3.4x, and one aggregator states it could not find 3.4x in primary sources ([release](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0); [explainx](https://explainx.ai/blog/llama-cpp-metal-few-row-mma-speculative-decoding-m3-ultra-2026)) [S]. **Claim 2, 1.5–2.0x typical,** holds for predictable text and fails for chat: EAGLE-3 on an RTX A6000 ranged 0.83x to 3.28x ([PR #18039](https://github.com/ggml-org/llama.cpp/pull/18039)), a Qwen2.5 draft sweep on an RTX 5060 Ti gave 1.25–1.37x ([sweep](https://inventivehq.com/blog/speculative-decoding-draft-model-size-sweep)), Qwen2.5-Coder 7B gave 0.95x and 1.16x, and a CPU-only 3B run (setup unstated) averaged 1.72x with chat at **1.01x** ([consumer-GPU piece](https://inventivehq.com/blog/llama-cpp-speculative-decoding-consumer-gpu)) [S]. **Claim 3, 1.9x MTP median, is unverified:** the one controlled benchmark found 1.6x (+59.8% at two draft tokens, RTX 3090), the community table spans +33% to +145% with no median, an external 0.8B drafter on the dense target lost 29.8%, and 76–100% of requests diverged from serial greedy output ([benchmark](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090.md); [community repo](https://github.com/sudoingX/qwen38-mtp)) [S]. It is also moot, since Qwen2.5 ships no MTP heads and no MTP model under 9B was found.

Nobody has published speculation with the **target** split across RPC workers; the maintainer confirmed only the reverse, a draft on an RPC device via `--spec-draft-device RPC0` ([issue #23982](https://github.com/ggml-org/llama.cpp/issues/23982)) [S]. Mechanically it should work, since the loop needs only `llama_decode`, per-position logits and `llama_memory_seq_rm`, which is metadata-only and free over RPC [S]. The cost sits elsewhere: verification needs logits at every drafted position, which is **0.608 MB per row over the last link**, about 0.10 s per extra row at 6 MB/s [D]. Backend sampling is documented as one output per sequence per batch, so the two best levers collide, and combining them would need a carried worker-side multi-row argmax patch (DIST). The speculative helpers also live in `common`, which the build disables (`LLAMA_BUILD_COMMON OFF`), so the probe needs either that library or about 100 lines of its own [V].

The notes disagree on δ, and the answer is unmeasured. SPEC measured a 5-token prefill at about 4x a one-token step on the laptop (3,554 against 726 ms) and about 2.25x on the 0.5B three-device split (at most ~0.10 s per extra position). OVERLAP derived only ~1.45x for five tokens from F27's Xeon figures. DIST assumed 1x and flagged it optimistic. The laptop is already compute-bound, so its seven layers get no verification discount, and no 3B datapoint exists (its 5-token prefill took 11.3–28.9 s). The architectural ranking in DIST, draft on the laptop with greedy verification, is therefore correct in shape and wrong in price: the 0.5B draft needs 0.65 s per token on that laptop, which is nearly the cost of the whole three-device target step (0.77 s). A draft also competes for memory: 463 MiB for a Q4_K_M 0.5B against a laptop free-RAM floor of 89.2 MiB, a 700 MiB Android budget spare whose available RAM already dipped to 282–439 MiB, and 237 MiB on the iPhone. A draft on a phone loses by the survey's rule that remote drafting cannot win when RTT ≥ γ times the draft step time ([Lyu et al.](https://arxiv.org/html/2606.25091)) [S]. That leaves draftless n-gram (~16 MB, no network), useful only where output repeats the prompt: one explainer's 32%-acceptance n-gram run (hardware unstated) lost 17% of decode speed ([explainer](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html)) [S], and acceptance on the project's 16-token factual prompt should be near zero [U].

Pipeline-aware designs do not rescue it. PipeInfer reports up to 2.15x over standard speculation on 8–32-node CPU clusters with Gigabit Ethernet or InfiniBand but calls gains "marginal" in shallow pipelines, and it is a frozen 2024 MPI fork whose ideas (several runs in flight, cancellation without closing the connection, per-run KV) need protocol changes that F35's dead-endpoint latch makes harder ([PipeInfer](https://arxiv.org/html/2407.11798v1); [repo](https://github.com/AutonomicPerfectionist/PipeInfer)) [S]. FlowSpec's 1.37–1.73x over a plain pipeline was shown down to 125 Mbps on five Jetsons, 2.6x the phones' 48 Mbit/s ([FlowSpec](https://arxiv.org/html/2507.02620v3)) [S]. AMUSD's "multi-device" is shared host memory and says nothing about Wi-Fi. A last practical cost: speculative output may legitimately diverge from serial greedy decoding, so the proof gate needs a same-build non-speculative control instead of the pinned reference.

## Expert parallelism, live re-balancing and overlap fail on structure, not tuning

**Expert parallelism is neither a speed nor a capacity lever here.** Layer split already pooled 3,209.1 MiB against a 2,048 MiB largest budget ([F43](../findings.md)), so splitting experts adds no capacity. It adds synchronisation: with a coordinator holding attention and routing, each MoE layer needs a round trip to every device owning a selected expert, 16 exchanges per token for OLMoE, 32 for Granite 3B-A800M, 48 for Qwen3-30B-A3B, against one exchange per link for layer split. At the emulated 5 ms RTT OLMoE's floor is 80 ms/token with one blocking call per layer (a 12.5 tok/s ceiling), or 240 ms/token (about 4 tok/s) if each layer needs three, and it can cut serial expert compute by at most the two phone owners while adding at least 14 extra round trips, so it loses to layer split on the same model at any RTT above ~2 ms [D] (MOE). The report's "far less data movement per token" holds only against weight offloading and tensor parallelism: OD-MoE's measured 16 KB hidden-state exchange per layer per token reached 75.5% of fully cached speed on ten RTX 3090s over 1 GbE ([OD-MoE](https://arxiv.org/html/2512.03927v1)), and Prism's gains are simulated on one four-A100 machine with no pipeline baseline ([Prism](https://arxiv.org/html/2508.12851v4)) [S]. At the pin, expert weights are fused 3D tensors (`ffn_{gate,up,down}_exps`) placeable only per tensor, the upstream expert caches are GPU-only and postdate the pin ([PR #29887](https://github.com/ggml-org/llama.cpp/pull/29887)), and no upstream expert-parallel-over-network work was found [S]. The one variant worth testing is a small-active MoE through the existing path: OLMoE Q3_K_M (3,189 MiB) or Granite 3.1 3B-A800M Q8_0 (3,350 MiB, almost F43's footprint) read ~4.6x fewer weight bytes per token, for a derived 1.3–2x only if the physical gap is compute-bound ([OLMoE GGUF](https://huggingface.co/allenai/OLMoE-1B-7B-0125-Instruct-GGUF); [Granite GGUF](https://huggingface.co/bartowski/granite-3.1-3b-a800m-instruct-GGUF)). `MUL_MAT_ID` over `sc-rpc-worker` has never run, no quality comparison against the dense 3B exists, and top-k routing makes cross-architecture token equality more fragile (MOE) [D/U].

**The makespan objective is wrong for one user.** Pipeline latency with B micro-batches is the sum of stage times plus (B−1) times the slowest, which collapses to a plain sum at B = 1 ([Alpa](https://arxiv.org/pdf/2201.12023)); prima.cpp's planner explicitly minimises a sum of per-device times rather than their maximum, EdgeShard uses a sum DP for latency and min-max only for throughput, and Parallax scores allocations additively ([prima.cpp](https://arxiv.org/html/2504.08791v2); [EdgeShard](https://arxiv.org/html/2405.14371); [Parallax](https://arxiv.org/html/2509.26182v1)) [S]. PLAN's worked example, with ASSUMED per-layer speeds calibrated only to reproduce 727 ms, shows the structure: the current memory-proportional split costs 735 ms, the min-max plan 750 ms (worse, though its bottleneck is lower), the min-sum plan 613 ms (−17%), and a min-sum plan that moves the output slot to the laptop 520 ms (−29%); min-max wins only once about 3–4 sequences are in flight [D]. Only the structure is evidence. The min-sum plan puts 21 layers on the Android phone, about 320 MiB more than the 1,348 MiB it held when its available RAM already fell to 282–439 MiB, so a feasible plan would shift load toward the iPhone, whose `os_proc_available_memory` never fell below 2,061 MB [D] (PHONE; MOE). `StagePlanner` today is memory-proportional apportionment with no speed or link input, and the native path bypasses it by passing budgets as `tensor_split` ([StagePlanner.swift](../Sources/ShareComputeCore/StagePlanner.swift); [probe.cpp](../native/split/probe.cpp)) [V].

**A live re-balance costs a full reload and cannot pay back on short runs.** F35 shows a failed endpoint is dead for the life of the process, so any changed placement means a fresh context; the physical reload is 98 s of strictly serial loading inside a 140 s warm run (about 190 token-times, against LinguaLinked's ~0.5) and 492–557 s with a cold phone cache, when moved layers must be uploaded at ~6 MB/s ([F48](../findings.md); [LinguaLinked](https://arxiv.org/html/2312.00388)). With a 122 ms/token gain the break-even is **N\* = R/(T_old − T_new) ≈ 800–1,150 generated tokens**, 8–12 minutes of continuous generation, while the project's proofs generate 16 [D]. The systems that do re-balance live have replicated weights (prima.cpp mmap, LinguaLinked replicas), replay inputs instead of migrating KV, and throttle with a 20% hysteresis threshold (Petals). The defensible design is the one PLAN recommends: observe-only telemetry (per-stage ms inside the worker, per-link RTT at the coordinator, free-memory floors, thermal state) written to a persisted device profile and consumed when the next epoch plans; the propose/commit machinery agrees the next plan and does not migrate anything.

**Overlap cannot help single-sequence decode, and the pin already has all of it.** Upstream's async and event work (PR #18626, merged 2026-08-26) is present: F45 and F48 `split.log` show "pipeline parallelism enabled", 4 splits and 4 scheduler copies on the physical runs ([PR #18626](https://github.com/ggml-org/llama.cpp/pull/18626); OVERLAP) [V]. Autoregressive decode keeps one stage working at a time, and the original pipeline-parallel PR measured no generation gain even on eight GPUs (74.12 against 71.87 t/s) ([PR #6017](https://github.com/ggml-org/llama.cpp/pull/6017)) [S]. Reported prefill gains are +30–70% for two stages on GPUs, worse with three, and the prompt here has five tokens; RPC still lacks `cpy_tensor_async` and a remote-completion event, so every stage hand-off blocks through the laptop [V, source read]. The real anomaly is F48's 28.9 s prefill against 11.3–15.3 s in four other runs of the same prompt; at the steady 0.77 s step a 5-token prefill should take about 4 s, so at least 25 s is unexplained, and F48 itself could not say whether it is waiting or computing. The leading candidate is laptop paging under its 89–197 MiB free-RAM floor, ahead of blocking `GET_ALLOC_SIZE` misses on new graph shapes, host-side work and first-run phone costs, none tested (OVERLAP) [U].

## Conclusion

Each lever in the source report optimises a term the measurements show is small: bytes of activations (0.5% of the token), idle pipeline stages (which only speculation or batching can fill), expert placement (a capacity trick the layer split already delivers) and makespan (a throughput objective). The term that is large, 0.3–0.6 s/token of compute and overhead, has never been timed, and the project's own build configuration is the cheapest suspect. Equally telling, the two most promising levers conflict: removing the logits (rank 3) and verifying several tokens at once (rank 6) both want control of the last link's output, so the order of work is forced, backend sampling first and a worker-side multi-row argmax only if speculation survives E5 and E6.

A second pattern runs across the notes: most of the surviving gains, including compile flags, speculation, a Q4 file and an MoE model, can stop being bit-exact against the pinned token reference that the F37/F43 gate relies on, and backend sampling keeps tokens equal only if argmax ties break the same way. The gate, not the lever, is the hidden blocker. Rebuilding it around a same-build control run is the cheapest enabling work in the list, and it should land before the first optimisation does. Everything here rests on one 16-token prompt, one Wi-Fi network and three devices, so whichever lever survives its experiment still needs a longer run to be believed.
