## Q1. Which speculative-decoding modes does llama.cpp support today, how are they driven, and which models ship MTP heads?

### Takeaway
At master and at our pin, llama.cpp has one unified speculative framework selected by `--spec-type` (comma-separated, chainable): `draft-simple` (separate draft model), `draft-eagle3`, `draft-dflash`, `draft-dspark`, `draft-mtp` (heads inside the target GGUF), and the draftless `ngram-cache`, `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`, `ngram-mod`. Qwen2.5 (our models) has no MTP heads and no EAGLE-3 draft that I could find, so for us the realistic modes are `draft-simple` (0.5B drafting for 3B) and the n-gram family.

### Cited Findings
- `docs/speculative.md` on master lists `--spec-type` values `none`, `draft-simple`, `draft-eagle3`, `draft-dflash`, `draft-dspark`, `draft-mtp`, `ngram-cache`, `ngram-simple`, `ngram-map-k`, `ngram-map-k4v` (experimental), `ngram-mod`; types can be mixed, e.g. `--spec-type ngram-mod,ngram-map-k4v`; default `none`; `--spec-default` turns on a preset. — [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md) (secondhand summary)
- The same document **at our pinned commit** lists the same set (all of `draft-simple/eagle3/dflash/dspark/mtp` and the five n-gram types), so every mode below exists in our pin. — [docs/speculative.md @ 4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/docs/speculative.md) (secondhand summary)
- Draft-model flags: `-md` / `--spec-draft-model` (also `--model-draft`), `-hfd` / `--spec-draft-hf`, `--spec-draft-n-max` (default 3), `--spec-draft-n-min` (0), `--spec-draft-p-min` (0.00), `--spec-draft-p-split` (0.10), `--spec-draft-ngl`, `-devd` / `--spec-draft-device`, draft thread/CPU-mask flags (`-td`, `-tbd`, `--spec-draft-cpu-mask` ...). Draftless mode takes precedence if combined with a draft model. — [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md)
- Defaults changed in May 2026: PR #23269 (merged 2026-05-19, ggerganov) cut default `--spec-draft-n-max` from 16 to 3, made `--spec-draft-p-min` functional again (default 0.0), let every implementation see accepted tokens, and made chaining of several types valid. — [PR #23269](https://github.com/ggml-org/llama.cpp/pull/23269)
- n-gram parameters per docs: `ngram-mod` uses a ~16 MB hash pool shared across slots, defaults `--spec-ngram-mod-n-match 24`, `-n-min 48`, `-n-max 64`, and is aimed at "iterating over text or code, reasoning models, and summarization"; `ngram-simple` drafts the m tokens that followed the most recent matching n-gram (lowest overhead); `ngram-cache` keeps n-gram statistics (external statistics files loadable). — [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md)
- One explainer reports n-gram acceptance "~30-90%" workload-dependent, "zero overhead", useful only when output repeats prompt vocabulary; its own 128K test shows ngram-cache at 32% acceptance giving **-17% decode** while MTP n=2 (76% acceptance) gave +5%. Hardware and date not stated, so indicative only. — [HF Space explainer](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html)
- MTP: PR #22673 "llama + spec: MTP Support" (author am17an, opened 2026-05-04, **merged 2026-05-16**) adds `--spec-type draft-mtp` with `--spec-draft-n-max N`; the MTP head loads from the same GGUF but gets its own context and KV cache; tested on Qwen3.6-27B and Qwen3.6-35B-A3B; ggml-org published converted GGUFs for those two. Limitations at merge: slower prompt processing (device-to-host embedding transfers), `--parallel 1` in early builds, opt-in extra memory (one user ~2.5 GiB VRAM), early Vulkan garbage output. — [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)
- Other MTP-capable models: Qwen3.8-27B works with `--spec-type draft-mtp` per a community repo and the Metal PR's benchmarks (community repo says Qwen3.8 was released 2026-08-14); Qwen4Exp gained MTP in release v0.6.0 ("~1.5x decode speedup on DGX Spark"); a HF community card says the official Qwen3.5-9B ships a 4-layer MTP head (~243M params). — [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp), [PR #29869](https://github.com/ggml-org/llama.cpp/pull/29869), [release v0.6.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0), [QwenPaw-Flash-9B-MTP card](https://huggingface.co/SC117/QwenPaw-Flash-9B-MTP-GGUF) (the card is a community model card, unverified)
- EAGLE-3: PR #18039 (author ruixiang63, **merged 2026-06-12** by ggerganov): `--spec-type draft-eagle3` with `-md` pointing at an EAGLE-3 draft GGUF; supported families Llama 3.x, Qwen3, GPT-OSS, Gemma 4; Qwen3.5/3.6 added by PR #24593; docs list ~17 supported drafts. EAGLE-3 drafts must be converted with `convert_hf_to_gguf.py --target-model-dir`. — [PR #18039](https://github.com/ggml-org/llama.cpp/pull/18039), [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md)
- DFlash (block-diffusion draft, emits a block per step) and DSpark (DFlash backbone plus a Markov head; Qwen3 backbones only) are documented; a DFlash2 PR merged 2026-08-27. — [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md), [hackmd benchmark post, 2026-08-29](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090.md)
- **C++ API (not in `llama.h`; lives in `common/`)** at the pin: `common_speculative_init(params, n_seq)`, `common_speculative_begin`, `common_speculative_process(batch)` (feeds the target batch to the drafter so a draft model/EAGLE/MTP context stays in sync), `common_speculative_draft`, `common_speculative_accept(spec, seq_id, n_accepted)`, `common_speculative_free`, plus `common_speculative_init_from_params`. — [common/speculative.h @ 4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/common/speculative.h) (secondhand summary)
- Reference loop (`examples/speculative-simple`): (1) build `batch_tgt` = last committed token + each draft token, **with logits requested at every position** (`common_batch_add(..., true)`); (2) one `llama_decode(ctx_tgt, batch_tgt)`; (3) `common_sampler_sample_and_accept_n(smpl, ctx_tgt, draft)` returns accepted tokens plus one new token; (4) advance `n_past` by accepted count; (5) roll back with `llama_memory_seq_rm(llama_get_memory(ctx_tgt), seq_id, n_past, -1)`; if the target cannot do partial removal it restores a checkpoint instead. — [speculative-simple.cpp @ 4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/examples/speculative-simple/speculative-simple.cpp) (secondhand summary, quoted lines as returned)
- Draft-model compatibility check (`common_speculative_are_compatible`): same vocab type, same BOS/EOS (add flag and id), vocab-size gap <= `SPEC_VOCAB_MAX_SIZE_DIFFERENCE` = 128, and token text equal from id 5 up to the smaller vocab. The draft-simple drafter uses a top-k=10 sampler, stops a draft when top probability < `p_min`, and keeps its own KV in `ctx_dft`. — [common/speculative.cpp @ 4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/common/speculative.cpp) (secondhand summary; draft-context construction and `n_ctx` were in the unread tail)
- Our two Qwen2.5 models are vocabulary-compatible by size: both report `n_vocab = 151936`, 0.5B has 24 layers, `n_embd` 896, `n_head_kv` 2, 630.17 M params, 462.96 MiB Q4_K_M; 3B has 36 layers, `n_embd` 2048, `n_head_kv` 2, 3.40 B params, 3.36 GiB Q8_0. — [physical-three-device/baseline.log](../../docs/evidence/physical-three-device/baseline.log), [physical-3b-capacity/cold/split.log](../../docs/evidence/physical-3b-capacity/cold/split.log)
- The pin's server-side per-implementation statistics counters (`#gen drafts`, `#acc drafts`, `#gen tokens`, `#acc tokens`, timings) are the supported way to read acceptance. — [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md)
- Deprecated flag names are risky: one transcript warns a renamed flag is "still accepted but silently ignored", so speculation silently turns off. — [SozAI transcript](https://sozai.app/transcript/qwen-38-27b-3x-faster-one-setting/) (low-quality source; treat as a caution only)

### Inferences
- Qwen2.5-0.5B-Instruct and Qwen2.5-3B-Instruct should pass the vocab-compatibility check (equal `n_vocab`, same family tokenizer), but I did not run the check; the token-text comparison from id 5 is the part that can fail.
- None of the MTP-capable models found (Qwen3.5-9B, Qwen3.6-27B/35B-A3B, Qwen3.8-27B, Qwen4Exp) is small enough for our budgets (3,209 MiB pooled for the 3B). MTP is therefore not an option unless a small MTP model appears; I found none under 9B.
- `common_speculative_*` is not part of the stable `llama.h` API, and our CMake sets `LLAMA_BUILD_COMMON OFF` ([CMakeLists.txt](../../native/split/CMakeLists.txt)); `probe.cpp` links only `llama ggml-rpc ggml-cpu`. Using the library implementation means turning `common` on for the desktop probe (the probe is not built for iOS); otherwise the loop must be re-implemented against `llama.h` (batch with per-position logits flags, `llama_get_logits_ith`, `llama_memory_seq_rm`), about 100 lines for greedy verification plus a small in-probe n-gram table.

### Gaps
- The current `--spec-default` composition is unclear: the docs summary says it enables `ngram-mod`; PR #23269 says it added `ngram-k4v` to the default. Check `--help` at the pin.
- I could not read the tail of `common/speculative.cpp` (draft-context sizing, threads) or the full text of PR #23269 and #18039 (summaries covered the first ~100k characters).
- No primary source confirms an EAGLE-3 or other trained draft for Qwen2.5-3B; absence is from a docs summary, not a search of the 17-draft list in #18039.

## Q2. The source report's three claims: verified, refuted, or unverifiable?

### Takeaway
(1) "up to 3.4x on Apple Silicon after v0.6.0 kernel improvements" is **substantively real but narrow**: the numbers are in PR #29869 (merged 2026-10-05, in release v0.6.0), they are a best case (code prompt, greedy) for a 27B target with a DFlash2 drafter on an M3 Ultra GPU, author-reported, and do not apply to CPUs. (2) "1.5-2.0x typical" is the right order of magnitude only for high-acceptance workloads on GPUs; chat/prose is often 1.0-1.4x and some configurations are slower than baseline. (3) "Qwen3.8-27B MTP ~1.9x median" is **UNVERIFIED as stated**: the sources I found give 1.6x (one controlled benchmark) and a community range of +33% to +145% with no stated median.

### Cited Findings
- **Claim 1, what the primary source says.** PR #29869 ("metal : few-row MMA mat-mul and batched copies for speculative decoding", merged 2026-10-05, target "v0.6.0"): hardware Apple M3 Ultra 60-core GPU, macOS 15.7.9; model Qwen3.8-27B Q4_0 with a Q8_0 DFlash2 drafter; server decode, 64 tokens, median of 5. Master -> PR: Code T=0 **30.2 -> 110.0 t/s**, Code T=1 24.3 -> 80.9, Prose T=0 16.8 -> 62.6, Prose T=1 13.9 -> 48.8; "serial decoding stayed about 32 t/s on both builds" (tg128 32.45 vs 32.36). The headline ratio is therefore 110/32 = **3.4x for code at T=0**; the same table gives about 1.9x (prose T=0), 2.5x (code T=1) and 1.5x (prose T=1) versus serial (my arithmetic on the PR's numbers). Reviewer notes: row thresholds tuned on the M3 Ultra only; the PR description discloses Claude Code wrote the kernels/tests/benchmarks. — [PR #29869](https://github.com/ggml-org/llama.cpp/pull/29869) (secondhand summary)
- **The tag exists.** The GitHub release `v0.6.0` exists (tag commit `d812350`, published "05 Oct"); its notes mention few-row MMA kernels for speculative and batched decoding, "up to ~3x faster mat-mul on Apple GPUs", and no 3.4x figure. A separate pre-release `b11404` (2026-10-05, PR #29869) carries the same change. — [release v0.6.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0), [b11404 on newreleases.io](https://newreleases.io/project/github/ggml-org/llama.cpp/release/b11404) (summaries; the year of the v0.6.0 page was not shown, but the tag commit and PR agree)
- **Why the Metal gain happened (relevant to the "verify N ~ 1 token" question).** Before the PR, Metal ran 2-16 row matmuls with mat-vec kernels whose time grows with each row: `llama-batched-bench` TG at 1/2/3/4/8 parallel sequences was 32.9/32.7/36.2/36.3/38.6 t/s on master and 32.9/49.7/62.2/76.1/119.7 t/s with the PR. In other words, speculative decoding was *slower than serial* on Metal until kernels for few-row matmul existed. Kernel times n=2..8 fell to 0.21-0.58x of master. — [PR #29869](https://github.com/ggml-org/llama.cpp/pull/29869)
- Caveats from secondary coverage: explainx.ai says the 3.4x end-to-end figure "is not a number we could find in the primary sources" (the PRs report kernel speedups; best published kernel-only figures 4.41x Q1_0 at 8 rows, 4.30x Q2_K, 4.03x TQ2_0 at 16 rows) and flags b11404 as a pre-release; byteiota (2026-10-12) states "32.1 -> 110 tok/s" as a v0.6.0 headline and "no regressions reported" without a source; aiweekly.co (2026-10-05) names the release "llama.cpp v0.6.0" with a headline about Qwen4Exp/GLM-5.3-Flash and cites no PR. These aggregators are low quality; the primary data is the PR table above. — [explainx.ai](https://explainx.ai/blog/llama-cpp-metal-few-row-mma-speculative-decoding-m3-ultra-2026), [byteiota](https://byteiota.com/llama-cpp-060-metal-speedup-decision-models/), [aiweekly.co](https://aiweekly.co/alerts/llamacpp-v060-adds-glm-53-flash-3x-apple-metal-matmul)
- A separate user-filed issue reported MTP on Metal as slower than baseline at every draft ceiling tried (before these kernels); I only saw it as a search snippet. Community rows in the Qwen3.8 repo show Apple M4 24 GB at 0% and Mac Studio M3 Ultra at +6% with MTP (pre-kernel). — [llama.cpp issue #23752 (snippet)](https://github.com/ggml-org/llama.cpp/issues/23752), [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp)
- **Claim 2, "1.5-2.0x typical on consumer GPU/CPU".** Spread of measured results: EAGLE-3 PR on an RTX A6000 (draft n=8): Llama 3.1 8B BF16 3.28/2.85/2.55x, Q4_K_M 2.26/1.97/1.62x, Qwen3 14B BF16 1.46/1.41/1.26x, Qwen3 32B Q4_K_M 1.24/1.30/1.16x, GPT-OSS-20B/120B 0.83-1.08x. — [PR #18039](https://github.com/ggml-org/llama.cpp/pull/18039). Draft-model sweep on an RTX 5060 Ti (Qwen2.5-Coder-14B Q4_K_M target, baseline 42.45 t/s, n-max 5, greedy, published 2026-06-26): 0.5B Q8_0 draft 26% acceptance 1.37x; 1.5B 40% 1.32x; 3B 87% 1.25x. — [InventiveHQ sweep](https://inventivehq.com/blog/speculative-decoding-draft-model-size-sweep). Same author, Qwen2.5-Coder 7B: 0.95x on an RTX 5060 Ti and 1.16x on a GTX 1080 Ti (per a search-result summary). — [InventiveHQ](https://inventivehq.com/blog/llama-cpp-speculative-decoding-consumer-gpu). **CPU-only** Qwen2.5-Coder 3B: 12.9 -> 22.1 t/s (**1.72x**) overall, math 2.03x, code 1.96x, reasoning 1.74x, summarize 1.69x, **chat 1.01x**; CPU model, threads, draft and acceptance not stated (published 2026-06-25). — [InventiveHQ](https://inventivehq.com/blog/llama-cpp-speculative-decoding-consumer-gpu)
- **Claim 3, "Qwen3.8-27B MTP ~1.9x median".** The only controlled benchmark found (preregistered, 875 request records, RTX 3090, Q4_K_XL, `--parallel 1`, greedy, 2026-08-29): MTP n-max 2 = 66.39 vs 41.55 t/s (**+59.8%, 1.6x**), n-max 3 +52.3%, n-max 5 +32.1%; per-class MTP n-max 2: code +92%, reasoning +74%, prose +49%, chat +47%, Chinese +38%; no median reported; an external 0.8B drafter on the dense target was **-29.8%**; and 76-100% of requests diverged from serial greedy output by 400-1,600 tokens. — [hackmd post](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090.md). Community repo: "+33% to +145%" across ~100 rows (RTX 3090 +33%, 4090 +60%, A6000 +97%, 5090 +110-137% at n-max 2-7), no aggregate median or mean given. — [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp). PR #22673 user reports: DGX Spark 27B Q8 wall time 201 s -> 84 s (about 2.4x, N=3, ~72% acceptance); RTX 3090+3060 23 -> 42 t/s (1.8x). — [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)

### Inferences
- "~1.9x median" plausibly describes the upper half of the community rows (many show +90-100%), but it is not stated anywhere I could read and the one controlled benchmark is 1.6x. Treat as UNVERIFIED; do not carry it forward as a "median".
- "3.4x" is a ceiling for a GPU, a 27B model, a trained drafter and code at T=0. Nothing in it speaks to a CPU pipeline.
- The consistent pattern across sources: gain tracks workload predictability (code/math/reasoning high; chat/prose ~1.0-1.5x) and drafter alignment, and is *negative* when the drafter is misaligned or the verify kernel does not amortize.

### Gaps
- I could not read the full list of ~100 community rows, so no median can be computed.
- I could not read the full v0.6.0 release notes; the page summary did not contain a 3.4x figure, and the exact year on that page was not shown.
- Qwen3.8's release is attested by the community repo and the PR's benchmarks, not by a primary Qwen/Alibaba source that I read.

## Q3. Does speculative decoding work when the target is split over ggml-rpc backends? Known issues?

### Takeaway
I found **no primary report, issue or benchmark of speculation with the *target* split across RPC workers**. The maintainer has confirmed the reverse arrangement (target local, *draft model on an RPC device*, `--spec-draft-device RPC0`). The speculative loop only uses `llama_decode`, per-position logits and `llama_memory_seq_rm`, which are backend-agnostic, and `seq_rm` is metadata-only at our pin, so it should work in principle; it is untested here and by anyone I could find.

### Cited Findings
- Issue #23982 "Distributed speculative decoding: GPU draft model over network" (opened 2026-06-01, closed 2026-06-22): ggerganov answered that this "is already supported via the RPC backend (`-DGGML_RPC=ON`)", giving an example where the main server runs the target locally with `--rpc 127.0.0.1:50052`, `--spec-type draft-mtp` (with a draft file), `--spec-draft-n-max 3` and `--spec-draft-device RPC0`, and the other machine runs `rpc-server`. No benchmarks or networking-cost discussion followed; one commenter raised overhead concerns about drafting off-device. — [issue #23982](https://github.com/ggml-org/llama.cpp/issues/23982) (secondhand summary; I did not see the exact command lines)
- An old TODO in the original llama-server speculative PR listed "test offloading draft model with RPC" as unfinished. — [PR #10455](https://github.com/ggerganov/llama.cpp/pull/10455) (search snippet only)
- `llama_memory_seq_rm` (`llama_kv_cache::seq_rm`) at our pin only edits cell metadata and the head index, contains no `ggml_backend_tensor_set`/`memset`/`buffer_clear`, and always returns true; stale K/V bytes stay in the buffers. So rolling back rejected draft tokens sends nothing over RPC. — [src/llama-kv-cache.cpp @ 4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/src/llama-kv-cache.cpp) (secondhand summary)
- RPC deadlock report, relevant because we use three endpoints: issue #28487 "RPC deadlocks with 3+ endpoints; 2 works reliably" (opened 2026-09-06, still open, `bug-unconfirmed`, `stale` added 2026-10-07): all-CPU path, 8 Xeon nodes on 10 GbE, hang within two minutes with 3+ `rpc-server`s, no maintainer reply, no fix PR, speculative decoding not involved. — [issue #28487](https://github.com/ggml-org/llama.cpp/issues/28487) (secondhand summary). The project could not read it earlier (HTTP 403) and ran 4 to 15 loopback endpoints without a hang ([F49](../../findings.md)).
- Prior art on a pipelined, multi-node CPU cluster: **PipeInfer** (Butler, Yu, Mazaheri, Jannesari; arXiv 2407.11798, v1 2024-07-16, v2 2024-11-16; SC24) is implemented on llama.cpp with MPI; clusters up to 8-32 nodes (Gigabit Ethernet and InfiniBand); it overlaps several speculative runs ("Continuous Asynchronous Speculation") and cancels invalidated runs; reports up to **2.15x over standard speculative inference**, largest on Gigabit Ethernet and on poorly-aligned pairs; acceptance in its pairs 52-79% (e.g., Dolphin 70B/TinyLlama 79%, Goliath/XWin-7B 52%). — [arXiv abstract](https://arxiv.org/abs/2407.11798), [HTML v2](https://arxiv.org/html/2407.11798v2) (secondhand summary)
- Pre-existing project fact that bears on structure: each endpoint has one dispatcher thread; `ggml_backend_rpc_buffer_cpy_tensor` returns false between different servers so activations go via the laptop; the async RPC API (PR #18626) merged 2026-08-26. — [F49](../../findings.md), [F50](../../findings.md)

### Inferences
- With the target on RPC, a verification batch of N tokens is one `llama_decode` and so (by the existing layer-split design) still one blocking exchange per link, with per-link payload scaling with N: roughly 8 KB x N of activations per hop and **0.608 MB x N of F32 logits on the last link**, because verification needs logits at every position (the reference loop requests logits at all positions). KV rollback adds no traffic.
- Standard (synchronous) speculation leaves two of three stages idle during each verify, exactly the bubble PipeInfer attacks; getting PipeInfer-style overlap would need several graphs in flight at once, and our probe issues one blocking `llama_decode` at a time. I did not find a way to do that through the public API; it would be a research project, not a flag.
- Draft-on-RPC works by design but each draft token is one blocking round trip *plus a full logits return* (the drafter must read its argmax/top-k on the client), so it inherits the same per-token network cost as our target.

### Gaps
- No evidence on whether `n_outputs > 1` graphs (the log shows the scheduler reserved with `n_tokens = 64, n_seqs = 1, n_outputs = 1`) trigger a buffer re-reservation on the RPC workers and whether our budget patch ([llama-budget.patch](../../native/split/llama-budget.patch)) would accept it. Needs a run.
- No benchmark of target-on-RPC speculation anywhere I could find; issue #28487's real cause is unknown.

## Q4. Does speculation help or hurt on CPU-only, low-thread-count ARM devices, and how does CPU decode scale with batch size 1..8?

### Takeaway
I found **no primary dataset of CPU tokens/s versus batch size 1-8 and no CPU-ARM speculative benchmark**; whether verification of N tokens costs about the same as 1 depends on being memory-bandwidth-bound at N=1, and the project's own data suggests our laptop is already compute-bound while the phones are unmeasured. The only hard evidence about "verify N ~ cost of 1" is GPU (0.25-0.29 of a plain step per extra position on a 3090, and a Metal case where it was false until new kernels).

### Cited Findings
- GPU verify cost: a fitted "roughly 0.25-0.29 of a plain decode step per extra verified position" on an RTX 3090 (CUDA), with memory-clock elasticity falling from 0.79-0.81 (baseline) to 0.13-0.18 under speculation. — [hackmd post, 2026-08-29](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090.md)
- Metal batch scaling before/after few-row kernels: TG 32.9/32.7/36.2/36.3/38.6 t/s at 1/2/3/4/8 sequences on master (no batching benefit) vs 32.9/49.7/62.2/76.1/119.7 with the PR. — [PR #29869](https://github.com/ggml-org/llama.cpp/pull/29869)
- Single-stream decode is memory-bandwidth-bound and batching moves the bottleneck toward compute (general statement, not a CPU measurement); a dual-socket NUMA run can be slower than single-socket. — [InventiveHQ local-LLM piece](https://inventivehq.com/blog/local-llm-performance-what-to-expect), [llama.cpp issue #1437](https://github.com/ggml-org/llama.cpp/issues/1437) (search snippets)
- CPU-only 3B: 1.72x overall but chat 1.01x (setup unstated). — [InventiveHQ](https://inventivehq.com/blog/llama-cpp-speculative-decoding-consumer-gpu)
- A server-vs-example gap: `llama-server` speculation was 10-15% slower than `llama-speculative-simple` at ~97-100% acceptance (Qwen2.5-72B IQ4_XS target, Qwen2.5-0.5B IQ4_XS draft, n 3, ROCm, build 5142, opened 2025-04-16, closed 2025-12-08 by PR #17808). Our probe would be closer to the example loop. — [issue #12968](https://github.com/ggml-org/llama.cpp/issues/12968)
- Claims of Android speculative speedups (40+ t/s on a Pixel 9, "2-3x") come from tutorials that use NNAPI/GPU or NPU and have inconsistent hardware; I discarded them. — [DEV Community tutorial](https://dev.to/software_mvp-factory/speculative-decoding-on-android-wiring-a-draft-model-to-llamacpp-for-2-3x-token-throughput-26nl) (low quality)
- **Project measurements that bear on batch scaling (read directly):**
  - Laptop alone, Qwen2.5-0.5B Q4_K_M, 2 threads, 5-token prefill vs one decode call: F37 3,554 ms vs 726 ms (4.9x); F39 cold 2,632 vs 660 ms (4.0x); F39 warm 2,593 vs 619 ms (4.2x). A 5-token batch costs about **4x a single-token step** (so little batching discount); the prefill figure includes first-call overhead, so this is an upper bound on batch cost. — [physical-three-device/baseline.log](../../docs/evidence/physical-three-device/baseline.log), [physical-weight-cache baselines](../../docs/evidence/physical-weight-cache/)
  - The same 0.5B model split over laptop+Android+iPhone: 5-token prefill 740-780 ms vs 328-347 ms per decode call (2.25x), implying at most about **0.10 s per extra position** (upper bound, includes first-graph warm-up; logits requested only for the last token, so no extra logits traffic included). F37's first run was 5.3x (1,942 vs 366 ms). — [physical-weight-cache](../../docs/evidence/physical-weight-cache/), [physical-three-device/report.json](../../docs/evidence/physical-three-device/report.json)
  - 3B: 5-token prefill took 11.3-15.3 s (F43/F45) and 28.9 s (F48) against 0.76-0.91 s per decode call, and F48 could not say whether the excess is waiting or computing. **No usable 3B batch-cost datapoint exists.** — [F43, F45, F48](../../findings.md)
  - Per-node compute has never been measured and Wi-Fi round-trip time has never been measured. — [F49 "Not verified"](../../findings.md)
  - Build flags: `native/split/CMakeLists.txt` forces `GGML_NATIVE`, `GGML_AVX`, `GGML_AVX2`, `GGML_AVX512`, `GGML_FMA`, `GGML_F16C`, `GGML_BMI2` and `GGML_OPENMP` OFF, and `build_split_runtime.py` adds `-DGGML_LLAMAFILE=OFF` for Android. `probe.cpp` sets `use_extra_bufts = false`, `n_threads = 2`. The Windows log files contain no `system_info` line. — [CMakeLists.txt](../../native/split/CMakeLists.txt), [build_split_runtime.py:76-77](../../scripts/build_split_runtime.py), [probe.cpp:55-71](../../native/split/probe.cpp)

### Inferences
- **Roofline reasoning (inference, not measured).** A decode step reads every weight once (3B Q8_0 is 3.36 GiB across three devices; the Android share is ~1.35 GB) and does roughly one int8 multiply-accumulate per weight byte per token. Verification of N tokens reads the weights once but does N times the arithmetic. It is "free" only while the arithmetic stays below the memory-bandwidth limit. A 2-thread phone core with NEON dot-product instructions has much more int8 throughput than a phone's DRAM can feed, which suggests decode is bandwidth-bound there and the crossover is at a few tokens (my rough range 3-8, UNVERIFIED); without dot-product/i8mm paths (Android `GGML_LLAMAFILE=OFF`; repacked kernels not used by plain RPC buffers) the ggml generic path multiplies each weight row against each of the N columns, so extra tokens cost compute linearly even though weight bytes are amortised.
- **The laptop is the suspect.** Its 0.5B Q4_K_M decode (0.62-0.73 s per token on a 630 M-parameter, 463 MiB model) is slow enough to indicate it is compute-bound already at N=1 (a ~0.5 GB read per token would be sub-100 ms at ordinary DRAM bandwidth), and its batch-5 prefill is 4x a decode step, consistent with that. The forced-off AVX/AVX2/FMA flags are a candidate cause (plus 2 cores shared with the relay and worker, F50), but I did not confirm what instruction set the shipped Windows binary uses. This matters for speculation twice: it removes the verification discount on the laptop's 7 layers, and it makes any draft model *on the laptop* slow (Q5).
- Hence "N tokens cost about 1 token" is plausible on the phones, doubtful on the laptop, and in any case **not the dominant term for us**: the added per-position cost on the last link is the 0.608 MB logits return (about 0.10 s at the 6.1 MB/s phone rate seen in F46/F48, or 0.02 s at 27 MB/s), which is network, not compute.
- Speculation helps when (verify cost growth) + (draft cost) is small relative to one step; on a CPU pipeline the draft is the hard part (Q5/Q7).

### Gaps
- No pp1..pp8 / tg-vs-batch measurement for ARM CPU with 2 threads in any source I could open; the llama-bench README sweeps `-b`/`-p`, not 1..8 tokens. A direct measurement (`llama-bench -p 1,2,3,4,6,8 -n 0 -t 2` on the Android and iPhone builds, or a probe change that times an N-token `llama_decode`) is the missing number.
- The Android phone's CPU (reported `motorola moto g 5G - 2024`) and whether it has dot-product/i8mm support were not looked up here. The iPhone model is not recorded.
- The laptop's x86 feature level in the shipped binary is unverified.

## Q5. Memory implications of a draft model: on the 4 GB laptop versus another node

### Takeaway
A draft model would not fit comfortably on the laptop (free RAM bottomed at 89.2 MiB of 3,973 MiB in the 3B run), and the Android phone's spare budget (~700 MiB, with available RAM dipping to 282-439 MiB) is only just enough for a Q4 0.5B draft; the iPhone has ~237 MiB spare. A draftless n-gram table costs about 16 MB.

### Cited Findings
- Laptop free RAM bottomed at **89.2 MiB of 3,973** during the 3B run; the 3B laptop share is 562.2 MiB (layers 0-6) plus a 315.3 MiB host-mapped `token_embd`. — [F45, F43](../../findings.md)
- Worker budgets and holdings in F43: laptop 562.2 of 768 MiB; Android 1,348.3 of 2,048 MiB (700 MiB spare); iPhone 1,298.6 of 1,536 MiB (237 MiB spare). Android reports 3,472 MiB visible; `avail_mib` fell to 282 MiB (F45) and 439 MiB (F48) with resident size peaking at 1,173 and 1,050 MiB. — [F43, F49 section 5](../../findings.md)
- Draft file sizes: Qwen2.5-0.5B-Instruct Q4_K_M is 491,400,032 bytes (462.96 MiB, 24 layers, `n_head_kv` 2); a Qwen2.5-**Coder**-0.5B Q8_0 is 531 MB. — [THREE-DEVICE-MODEL-SPLIT.md](../../docs/THREE-DEVICE-MODEL-SPLIT.md), [InventiveHQ sweep](https://inventivehq.com/blog/speculative-decoding-draft-model-size-sweep)
- The 3B target's compute buffer was 37.53 MiB on the CPU backend at `n_ubatch = 64`. — [physical-three-device/baseline.log](../../docs/evidence/physical-three-device/baseline.log) (0.5B) and [3B split.log](../../docs/evidence/physical-3b-capacity/cold/split.log)
- `ngram-mod` keeps a ~16 MB hash pool; classic draft needs "VRAM for the second model" (1-7 GB files); MTP adds a separate context and KV (one user ~2.5 GiB VRAM on a 27B). — [docs/speculative.md @ master](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md), [HF Space explainer](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html), [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)
- The draft context keeps its own KV (`ctx_dft`). — [common/speculative.cpp @ 4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/common/speculative.cpp)

### Inferences
- 0.5B draft KV is small: 24 layers x 2 KV heads x 64 head-dim x 2 (K and V) x 2 bytes (F16) is about 12 KB per token, about 6 MB for a 512-token context (my arithmetic from the logged dims); the draft's weights and its ~40 MB compute/logits buffers are what matter.
- **On the laptop** the draft's ~463 MiB weights (mmapped, so evictable page cache rather than an OOM) would compete with the laptop's 562 MiB share and the host-mapped embedding on a machine with ~89 MiB of floor headroom; expect paging, which F43 already flags for Windows.
- **On Android** a 463 MiB Q4 draft fits inside the 700 MiB spare only if nothing else grows, and Android's available RAM already fell to 282 MiB; a Q8_0 0.5B (~531 MB or more) would not fit comfortably. **On the iPhone** (237 MiB spare) it does not fit. A third RPC worker process on one phone would also need a second budget.
- **Draftless n-gram** sidesteps all of this (about 16 MB, in the probe process on the laptop).

### Gaps
- The Qwen2.5-0.5B (non-Coder, non-Instruct) Q8_0 size and the draft's runtime resident set were not measured; the laptop's paging behaviour with a second model is unmeasured.

## Q6. Feasibility for our setup, and what `probe.cpp` would need

### Takeaway
Technically small and low-risk to *try* (about 100 lines of probe code for a draftless n-gram speculator, no change to workers or the wire protocol), but the evidence we have says a 0.5B draft model is a net loss here and that gains depend on text that repeats. The decisive number nobody has measured is the wall-time of an N-token, all-positions-logits `llama_decode` across the three devices.

### Cited Findings
- Current probe: `n_ctx = 512`, `n_batch = 256`, `n_ubatch = 64`, `n_threads = n_threads_batch = 2`, prefill via `llama_batch_get_one`, greedy `llama_sampler_sample(sampler, ctx, -1)`, then **one-token** `llama_decode(ctx, llama_batch_get_one(&token, 1))` per step; prompts limited to 1..256 tokens, 1..128 generated; no `common` library linked. — [probe.cpp](../../native/split/probe.cpp), [CMakeLists.txt](../../native/split/CMakeLists.txt)
- Layer split costs about one blocking exchange per link per token, ~0.011 MB each way on the first links and **0.608 MB (151,936 x 4 B F32 logits)** on the last link; the output layer sits on the last endpoint. — [F49 section 3](../../findings.md)
- Physical decode per call, 3B Q8_0: F43 cold 0.775 s, warm 0.908; F45 cold 0.815, warm 0.866; F48 warm 0.764; loopback 0.468 s. Prefill is a different regime (11-29 s for 5 tokens physical). — [reports](../../docs/evidence/), [F43](../../findings.md)
- Reference loop and rollback API: see Q1 and Q3. `seq_rm` is metadata-only (no RPC traffic).
- Speculative output need not be bit-identical to serial decoding: in the GPU benchmark 76-80% of requests diverged from serial greedy by 400 tokens (batch vs single-token kernels give different rounding), and a PR #23269 commenter saw output change with draft settings. — [hackmd post](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090.md), [PR #23269](https://github.com/ggml-org/llama.cpp/pull/23269)

### Inferences
What `probe.cpp` would need (all inference from the reference loop and the current file):
1. **Batch with logits at every position.** Replace `llama_batch_get_one` with a `llama_batch` whose `logits[i]` is set for the committed token plus every draft token (`llama_batch_get_one` computes logits only for the last position). Verification: for position i, take the greedy argmax from `llama_get_logits_ith(ctx, i)` (or `llama_sampler_sample(sampler, ctx, i)`), compare with draft[i], accept the longest matching prefix, and take the next position's argmax as the bonus token.
2. **Rollback:** `llama_memory_seq_rm(llama_get_memory(ctx), 0, n_past, -1)` after each round. Free over RPC (metadata-only).
3. **A draft source.** Either (a) link `common` and call `common_speculative_*` (requires `LLAMA_BUILD_COMMON=ON` for the desktop probe only; drafter selection is a parameter), or (b) an in-probe n-gram lookup over prompt + generated tokens (hash of last n tokens -> following tokens), about 50 lines, no model, no extra memory. For `draft-simple` a second `llama_model` and `llama_context` must be loaded in-process (on the laptop's CPU, or with `params.devices` pointing at a phone's RPC device, which needs a second worker budget).
4. **Config limits:** `n_ubatch = 64` covers any N <= 64; `limit <= 128` and the 256-token prompt cap are untouched.
5. **Proof gate:** `matches_baseline` compares tokens with the pinned reference; a speculative run may legitimately diverge after some tokens because N-token batches use different kernels. The gate would need a non-speculative run of the same build as its control, or a prefix-length tolerance. This is a project-design decision, flagged here only.
6. **Risk to test first:** scheduler reservation is at `n_outputs = 1` (log: `sched_reserve: worst-case: n_tokens = 64, n_seqs = 1, n_outputs = 1`); batches with N outputs may re-reserve compute buffers on the RPC workers, which interacts with the budget patch. Also each new N changes the graph shape, so graph reuse is lost (a small CPU cost against a ~0.8 s step).
7. **Where the saving comes from:** each accepted draft token saves a full pipeline round trip (about 0.77 s); each rejected position costs the marginal verify cost (compute plus 0.608 MB of logits). So expect speculation to be net positive only for repetitive or constrained text and net negative for novel short answers such as the 16-token prompt used in all physical runs.
- Design levers (untested): a cheaper last-link payload (place the output projection with the laptop, or sample on the worker via the documented but RPC-untested `--backend-sampling`) would shrink the per-position cost from 0.608 MB to ~8 KB; PipeInfer-style overlapping would need multiple in-flight graphs, which the single blocking `llama_decode` loop does not do.

### Gaps
- Nothing was implemented or run. No measurement exists of an N-token verify batch on the physical pipeline for N > 1 with 3B, of the Android/iPhone per-token compute time, or of Wi-Fi RTT. The backend-sampling-over-RPC idea is not supported by any source I read beyond one docs line ("tensor split mode is not supported; unsupported layouts fall back to CPU").

## Q7. Back-of-envelope: break-even acceptance rate and draft length, and expected speedup (Qwen2.5-0.5B drafting for Qwen2.5-3B Q8_0)

### Takeaway
With the *measured* laptop speed, a 0.5B draft model on the laptop **cannot break even at any acceptance rate**. A draft model only becomes viable if drafting gets about 6x cheaper than measured and the verify-per-extra-position cost stays under ~0.05-0.15 s, and even then the speedup is modest (about 1.2-1.8x at 70-80% acceptance). A draftless n-gram speculator needs only about 30-45% acceptance on drafted tokens to break even, with upside of 1.3-2.2x on genuinely repetitive text and no gain on novel text.

### Cited Findings
- Model: Leviathan et al. define the cost coefficient c as the ratio of the draft's per-run time to the target's (Definition 3.7), expected tokens per iteration `E = (1 - alpha^(gamma+1)) / (1 - alpha)` (Equation 1), and expected walltime improvement `(1 - alpha^(gamma+1)) / ((1 - alpha)(gamma*c + 1))` (Theorem 3.8), under an i.i.d. acceptance assumption. — [arXiv:2211.17192, ICML 2023 (formulas read from the ar5iv rendering)](https://ar5iv.labs.arxiv.org/html/2211.17192), abstract at [arxiv.org/abs/2211.17192](https://arxiv.org/abs/2211.17192) (2x-3x on T5-XXL)
- Inputs measured in this project: target step `T_t` = 0.76-0.91 s per `llama_decode` call physical (median 0.815; 0.77 used below), 0.44-0.47 s loopback; 0.5B draft step on the laptop alone `d` = 0.62-0.73 s per token (F37/F39 baselines: 9,281-10,885 ms / 15); logits 0.608 MB per position on the last link; phone link rates 6.1 MB/s (iPhone, F46/F48) and 27 MB/s (laptop link, F49 emulation). — [F43-F49](../../findings.md), [baselines](../../docs/evidence/physical-weight-cache/)
- Acceptance reference points (other pairs, not ours): PipeInfer pairs 52-79%; Qwen2.5-Coder 0.5B drafting for a 14B target 26% (greedy, n-max 5); MTP on Qwen3.6-27B ~72-76%. — [PipeInfer](https://arxiv.org/html/2407.11798v2), [InventiveHQ sweep](https://inventivehq.com/blog/speculative-decoding-draft-model-size-sweep), [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)

### Inferences
**My model (extends Leviathan with an explicit verify-batch cost).** One round = draft gamma tokens (`gamma*d`) + one verify batch of gamma+1 positions (`T_t + gamma*delta`), producing E tokens. Speedup `S = E*T_t / (gamma*d + T_t + gamma*delta)`. Break-even means `sum_{k=1..gamma} alpha^k = gamma*(d + delta)/T_t`, i.e. the mean of alpha^k over the drafted positions must exceed `c + eps` where `c = d/T_t`, `eps = delta/T_t`. `delta` = extra wall time per extra verified position. Estimate for `delta`: 0.05 s (bandwidth-bound compute + logits at 27 MB/s), 0.15 s (central: the 0.10 s upper bound from the 0.5B split prefill, or 0.10 s of logits at 6.1 MB/s, plus some compute), 0.30 s (compute-bound laptop / both). All three are UNVERIFIED guesses bracketing the little data above. `alpha` for Qwen2.5-0.5B vs 3B is UNVERIFIED (no source for this pair); 0.4-0.7 is plausible for chat, higher for code or repeated text.

**Draftless n-gram (d ~ 0), T_t = 0.77 s: break-even alpha (acceptance of each drafted token) by gamma**

| delta | g=1 | g=2 | g=3 | g=4 | g=6 | g=8 |
|---|---|---|---|---|---|---|
| 0.05 s | 0.06 | 0.12 | 0.16 | 0.21 | 0.28 | 0.34 |
| 0.15 s | 0.19 | 0.30 | 0.38 | 0.45 | 0.55 | 0.61 |
| 0.30 s | 0.39 | 0.51 | 0.60 | 0.66 | 0.74 | 0.78 |

Best expected speedup (best gamma in 1..8) for T_t = 0.77 s:

| alpha | delta 0.05 | delta 0.15 | delta 0.30 |
|---|---|---|---|
| 0.3 | 1.23 (g=2) | 1.09 (g=1) | 0.94 (g=1) |
| 0.5 | 1.57 (g=3) | 1.26 (g=2) | 1.08 (g=1) |
| 0.7 | 2.22 (g=5) | 1.60 (g=3) | 1.23 (g=2) |
| 0.9 | 4.03 (g=8) | 2.41 (g=7) | 1.60 (g=4) |

At the brief's T_t = 0.44 s the same approach is stricter because delta is a larger fraction: delta 0.05 s breaks even at alpha 0.19 (g=2) and gives 1.91x at alpha 0.7 (g=4); delta 0.15 s needs alpha 0.47 (g=2) and gives 1.30x at alpha 0.7 (g=2) and 1.73x at 0.9 (g=4); delta 0.30 s needs alpha >= 0.68 and tops out at 1.15x at alpha 0.9. Note alpha here is the acceptance *of drafted tokens when a draft is proposed*; n-gram only drafts on a match, and when it has no match the cost is zero, so the whole-run speedup is a time-weighted mixture, not a product: if S is the speedup on steps that have a draft and p is the fraction of baseline decode time spent on such steps, it is 1 / ((1 - p) + p / S), which is 1.0x at p = 0.

**Draft model 0.5B -> 3B, T_t = 0.77 s (best gamma, delta in {0.05, 0.15})**

| Where the draft runs | d | break-even | S at alpha 0.7 | S at alpha 0.8 |
|---|---|---|---|---|
| Laptop, as measured (0.5B Q4_K_M, 2 threads) | 0.65 s (c = 0.84) | delta 0.05: only at alpha >= 0.91 (g=1), S max about 1.05-1.07 at alpha = 1; delta 0.15: **never** (S max 0.98) | 0.89 / 0.83 | 0.94 / 0.88 |
| Laptop, hypothetically 6x faster (UNVERIFIED that this is achievable) | 0.11 s (c = 0.14) | g=2: alpha 0.32 / 0.46 | 1.56 (g=3) / 1.31 (g=2) | 1.84 (g=4) / 1.47 (g=3) |
| Phone via RPC (one round trip + logits per draft token) | 0.30 s (c = 0.39) | g=1: alpha 0.45 / 0.58 | 1.17 / 1.07 | 1.28 / 1.14 |

At T_t = 0.44 s (brief's figure): laptop hypothetical d=0.11 breaks even at alpha 0.36 (g=1) / 0.49 (g=2) with delta 0.05 and gives 1.27x at alpha 0.7 and 1.41x at 0.8; with delta 0.15 it needs alpha >= 0.59 and gives only 1.07x at 0.7. A phone-hosted draft (d=0.30) never exceeds 1.06x. Even with a *free* verify (delta = 0), the measured-speed laptop draft is a loss (S <= 0.98) while a 6x-faster laptop draft gives 1.5-2.1x at alpha 0.6-0.8, g=2-5 (T_t=0.77).

**Reading the tables.** (i) The brief's c framing (draft cost / target cost) fails first on the draft: the measured laptop can run the 0.5B draft at nearly the speed at which the whole three-device pipeline runs the 3B target. (ii) The marginal verify cost `delta` is what caps useful draft length: with delta 0.15 s the best gamma is 2-4 and returns flatten beyond. (iii) Because the Wi-Fi link makes every accepted token worth ~0.77 s, even a modest hit rate pays when the draft is free, which is why n-gram drafting is the only option with a plausible payoff; but for the 16-token factual prompt used in every physical run, n-gram acceptance should be near zero (I expect no gain, UNVERIFIED), so the benefit would show only on repetitive tasks (code editing, summarization, RAG, structured output).

### Gaps
- `delta`, `alpha` (for our pair and prompts) and the achievable draft speed are not measured; the break-even thresholds shift by tens of percentage points across the plausible delta range. The most decisive single experiment: in `probe.cpp`, time `llama_decode` of N = 1..8 tokens with logits requested at every position, on the three physical devices, plus the same on loopback; separately measure acceptance of Qwen2.5-0.5B vs 3B on loopback with the stock `llama-speculative-simple`/`llama-server` and the project's prompts (cheap, laptop-free).
- The i.i.d.-acceptance assumption of Theorem 3.8 is optimistic for n-gram drafts, whose acceptance is bursty (high inside repeated spans, zero elsewhere).
- Side observation for the project, outside this scope: the forced-off AVX/AVX2/FMA flags in `native/split/CMakeLists.txt` may be a major factor in the laptop's slow compute (laptop-alone 0.5B at 0.62-0.73 s/token). I did not verify the effect or the reason for the flags (they may be deliberate, for portability or token-equality across devices).
