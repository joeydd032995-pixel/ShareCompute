## Q1. What does the RPC protocol do per decode token at the pin, and are graph descriptors a large cost?

### Takeaway
At the pin, graph caching is **already merged and (judging by our own byte counts) active**: the client sends a tiny `GRAPH_RECOMPUTE` instead of re-serialising the graph, and `GRAPH_COMPUTE` carries no reply, so a decode token costs about one blocking exchange per link. Measured layer-split traffic (about 11 KB up per link) leaves room for only about 9 `rpc_tensor` descriptors beyond the 8 KB activation, so the graph is not being re-sent; the graph-descriptor cost for layer split is about 0.003 MB per link, not the ~85 MB seen in tensor split.

### Cited Findings
- `GRAPH_RECOMPUTE` and a per-device `last_graph_uid` exist at the pin: client logic `bool reuse = cgraph->uid != 0 && rpc_dev_ctx->last_graph_uid == cgraph->uid;` then sends `rpc_msg_graph_recompute_req` (device index only) via `send_async`, else serialises the full graph and sends `GRAPH_COMPUTE`. Server `graph_recompute` re-runs `stored_graphs[device].graph` and returns no payload. — [ggml-rpc.cpp @4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/ggml-rpc.cpp)
- The `RPC_CMD_*` enum at the pin: ALLOC_BUFFER, GET_ALIGNMENT, GET_MAX_SIZE, BUFFER_GET_BASE, FREE_BUFFER, BUFFER_CLEAR, SET_TENSOR, SET_TENSOR_HASH, GET_TENSOR, COPY_TENSOR, GRAPH_COMPUTE, GET_DEVICE_MEMORY, INIT_TENSOR, GET_ALLOC_SIZE, HELLO, DEVICE_COUNT, GRAPH_RECOMPUTE, MEMSET_TENSOR. There is no `COMM_*`, `SET/GET_TENSOR_2D`, bf16 or all-reduce at the pin; master adds `SET_TENSOR_2D`, `GET_TENSOR_2D`, `COMM_INIT`, `COMM_ALLREDUCE`, `COMM_FREE`. — same pin file; [master ggml-rpc.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-rpc/ggml-rpc.cpp)
- `serialize_graph` wire format: `device (4 B) | n_nodes (4 B) | node pointers (8 B each) | n_tensors (4 B) | rpc_tensor array`, built by walking each node's `src` and `view_src` recursively with de-duplication. `rpc_tensor` is `#pragma pack(1)`: id 8, type 4, buffer 8, ne 16, nb 16, op 4, op_params 64, flags 4, src 80, view_src 8, view_offs 8, data 8, name 64, use_count 4 = **296 B** (my sum of the quoted fields; the file only asserts a multiple of 8). — pin ggml-rpc.cpp, above
- Graph compute is asynchronous: master/pin `ggml_backend_rpc_graph_compute` queues with `send_async` and returns; GRAPH_COMPUTE has no reply; only `GET_TENSOR` (and hash-check `SET_TENSOR_HASH`) block. The client `get_tensor` calls `dispatcher->send(RPC_CMD_GET_TENSOR, ..., data, size)` which blocks on a future; a `get_tensor_async` variant exists. — pin ggml-rpc.cpp, above
- Graph-cache PR history for `ggml-rpc.cpp` (titles/dates from the file's commit list; all but #26610 and later are inside the pin): #15405 "Cache and reuse compute graphs" (2025-11-28), #21299 "Reuse compute graph buffers" (2026-04-03), #22701 "Use graph uid instead of graph cache" (2026-05-05), #23273 "Keep last_graph_uid in the device context" (2026-05-19), #18626 "Implement event and async backend APIs" (2026-08-26), #24292 "Invalidate cached compute graph when a referenced buffer is freed" (2026-09-16), #28789 "Hash-cache only weights" (2026-09-15); after the pin: #23671 (10-02), #26610 "Add -sm tensor" (10-06), #29544, #30481 (RPC logging). — [commit list](https://github.com/ggml-org/llama.cpp/commits/master/ggml/src/ggml-rpc/ggml-rpc.cpp); pin date from [commit page](https://github.com/ggml-org/llama.cpp/commits/4da6337767f973e2b4d0797e5b323d77d8565e4a)
- PR #15405 ("rpc : reuse compute graphs", rgerganov, merged 2025-11-28): server stores the last computed graph; drops the response to GRAPH_COMPUTE ("saving a network round trip"); only the last graph per device is cached. Reported tg gains: ~1% (13.62 to 13.76, 1 Gbps, CUDA, 7B Q4_0, early version); +24.5% (GLM-4 MoE 355B Q6_K, 15.64 to 19.47); +13% (gpt-oss 20B on localhost, 251.03 to 283.68); +6% (Qwen3-VL-235B, 12.98 to 13.78 short context); ~flat for MiniMax M2; the author noted the graph is a "substantial share of traffic" only for large models. Reviewer slaren: graph identification "is not reliable either". — [PR #15405](https://github.com/ggml-org/llama.cpp/pull/15405)
- PR #22701 (merged 2026-05-05, commit d5003b6): "Store the last graph uid and compare against it to determine if the same graph is being computed"; a downstream fork describes the previous design as an "unsafe memcmp graph cache" that crashed when same-shape prefill micro-batches reused a graph against a grown KV context. — [PR #22701](https://github.com/ggml-org/llama.cpp/pull/22701)
- PR #18626 (merged 2026-08-26): one `rpc_dispatcher` thread per endpoint; FREE_BUFFER, BUFFER_CLEAR and INIT_TENSOR lose their replies; its benchmarks were **prompt processing only** (A100s on localhost: +26% to +65% with 2 servers, worse with 3-4); no tg numbers, nothing on TCP_NODELAY or per-token round trips. — [PR #18626](https://github.com/ggml-org/llama.cpp/pull/18626)
- Security note: an aggregator page (AI-generated, internally inconsistent about remediation) lists CVE-2026-39909, a use-after-free in the `GRAPH_RECOMPUTE` handler in builds before b8585; #24292 (inside the pin) addresses invalidation on buffer free. — [OpenCVE](https://app.opencve.io/cve/CVE-2026-39909)
- Tensor split (F49): ~85 MB/token of non-activation client-to-worker bytes, **inferred** to be graph descriptors, 289/145/145 direction switches per token; layer split 0.011 MB up per link, ~1.9-2.0 switches. — [F49](/home/user/ShareCompute/findings.md) (lines 3559-3590)

### Inferences
- **Graph reuse is active in our runs.** Up-bytes per link are 0.010-0.011 MB. The activation input is 2048 x 4 = 8,192 B, so non-activation bytes are about 2.8 KB = 2,808 / 296 = **9.5 `rpc_tensor`-equivalents**. A 7-, 13- or 17-layer segment has at least 60-300 tensors (my estimate: 30-60 per layer x 296 B = 62-302 KB per link), so a re-serialised graph cannot fit. The 2.8 KB is explained by the descriptors inside 3-4 `set_tensor` messages (positions, mask, input) plus the recompute message and headers (assumption: each set/get request carries a 296 B descriptor; the pin excerpt I got did not show the client side). **UNVERIFIED by instrumentation** (`GGML_RPC_DEBUG` was not used); the counting proxy can distinguish `GRAPH_COMPUTE` from `RECOMPUTE` by size.
- **If it were not active** it would cost about 0.1-0.3 MB per link per token, up to ~0.6 MB/token in total, comparable to the logits. So the thing to protect is that any change (backend sampling especially, see Q4) does not silently disable reuse.
- Remaining upside from graph caching for layer split: bounded by the 2.8 KB x 2 phone links / 6.0 MB/s = **0.9 ms/token**, i.e. nothing.

### Gaps
- Where `cgraph->uid` is assigned in `ggml_backend_sched`/`llama-context` and what invalidates it (e.g. KV padding crossing a 256 boundary, backend samplers) was not read. Whether the first token after prefill, or each 256-token KV step, forces one full re-send is unknown.
- The client-side `set_tensor` wire layout at the pin (descriptor per call) was not confirmed.
- No upstream per-token byte or latency profile for a CPU-only layer split was found (only the PR benchmarks above).

## Q2. What compression or reduced-precision transfer exists upstream or in forks?

### Takeaway
**None for the client-to-worker or worker-to-client path in layer split, upstream or in any fork I could find.** The only reduced-precision wire path is a BF16 cast inside the RPC all-reduce for tensor split (#26610, merged 2026-10-06, after the pin, server-to-server, effectively two ranks). The pin has the content-hash weight cache (deduplication, not compression) and nothing else.

### Cited Findings
- No compression of wire data in the master RPC code; the only related mechanisms are hash dedup for weights above `HASH_THRESHOLD` (10 MiB, FNV-1a) and a BF16 reduction in `comm_allreduce` ("reduce large partials in bf16 to halve the wire bytes" in one fetch summary). A second summary of a later chunk of the same file saw an F32-only check and no BF16 comment; PR #26610's own description corroborates the BF16 cast. — [master ggml-rpc.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-rpc/ggml-rpc.cpp); [PR #26610](https://github.com/ggml-org/llama.cpp/pull/26610)
- PR #26610 ("Add -sm tensor", merged 2026-10-06 by am17an; approvals ggerganov, JohannesGaessler): async graph compute, custom all-reduce, graph UID cache, `set_tensor_2d`/`get_tensor_2d`; "partial results are exchanged directly between the servers via COMM_ALLREDUCE, with a BF16 cast for larger tensors"; the direct path "only activates with exactly two backends"; servers need direct peer connectivity (relay through the client "worked but was very slow (over 10 s/token)"); one tester reported hangs with more than one RPC backend; 2x M3 Ultra RDMA `-sm tensor` tg 9.61 vs `-sm layer` 23.05 t/s; gigabit LAN, 2 BC250 nodes, `-sm tensor` ~2.5 t/s vs `-sm layer` ~5 t/s. — [PR #26610](https://github.com/ggml-org/llama.cpp/pull/26610)
- The RPC README mentions a local tensor cache (`-c`), TCP default, optional RDMA ("lower latency and higher throughput"); no latency/bandwidth figures, no compression, no graph caching. — [tools/rpc/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)
- A web search for llama.cpp RPC compression (zstd/lz4/quantised tensors) found no PR or fork. — search, 2026-10-21 (negative result, 1 query)
- Turboload (`luxemque/llama.cpp`, branch `parallel-rpc-loading`) and prima.cpp target loading and per-device local weights, not per-token traffic; Turboload is on protocol 4.1.0 and unchecked. — [F50](/home/user/ShareCompute/findings.md) (lines 3620-3665)
- Pin facts that rule out in-protocol compression for us: `ggml_backend_rpc_get_proc_address` returns only `add_server`/`start_server`; `device_supports_op` returns `true` unconditionally (`//TODO: call the remote backend and cache the results`). — pin ggml-rpc.cpp, [link](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/ggml-rpc.cpp)
- Outside llama.cpp, activation compression between pipeline stages is established for other systems: Petals applies "dynamic blockwise quantization ... to the hidden states before pipeline-parallel communication, which halves the bandwidth requirements without any noticeable effect on generation quality" (BLOOM-176B/Llama 2 70B era, citing Ryabinin et al. 2023); BloomBee (arXiv 2604.21072, 2026-04-22) uses **lossless** FP16 byte-split plus ZSTD, up to 1.76x throughput / 43.2% lower latency vs Petals and Helix in low-bandwidth settings (secondhand summary; combined with micro-batching); TAH-Quant (arXiv 2506.01352) reaches 3-4 bit activations with up to 4.3x throughput over FP32 but is a **training** method. — [Petals 2312.08361](https://arxiv.org/abs/2312.08361) (text read from the PDF); [BloomBee](https://www.emergentmind.com/papers/2604.21072); [TAH-Quant](https://arxiv.org/abs/2506.01352)

### Inferences
- Anyone wanting Q8_0/F16 activations on the RPC wire today must carry a patch (new op in the graph at split boundaries, or a protocol extension); there is no upstream flag, and the closest upstream precedent (BF16 all-reduce) is a server-to-server path that our star topology cannot use (F49: no device-to-device path; the direct path needs exactly two ranks).
- Lossless compression (BloomBee style) would preserve the token-equality gate, but FP16 activations are not what we send (F32), and at 8 KB/crossing the saving is below 5 ms/token anyway (Q6).

### Gaps
- Only three searches targeted compression; a fork-level code search (GitHub) was not possible, so "no fork" means "none surfaced".
- I could not read Petals' section on how outliers are treated; its quantiser (bitsandbytes dynamic blockwise, large blocks, non-uniform code) is not Q8_0.

## Q3. Does activation quantization change model output? Evidence on Q8 quantising the residual stream

### Takeaway
Yes, it changes outputs (any lossy cast does), so it **breaks ShareCompute's bit-exact "tokens equal to the pinned reference" gate** (F37/F43/F45) and would need a tolerance-based gate. Whether the change is benign is open: pipeline systems report no noticeable quality loss at 8 bits (Petals, BLOOM), but the stage-boundary tensor is the residual stream, where "massive activations" of 10^3-10^4x the median live, and Q8_0's per-32-element block scale lets one such value flatten its 31 neighbours.

### Cited Findings
- Petals: dynamic blockwise 8-bit on hidden states "halves the bandwidth requirements without any noticeable effect on generation quality (Ryabinin et al., 2023)"; "For inference, performance does not depend much on bandwidth or sequence length but degrades with higher latency." — [Petals, arXiv 2312.08361](https://arxiv.org/abs/2312.08361)
- Massive activations (Sun et al., COLM 2024): LLaMA2-7B top activations 2622, 1547, 802 against median 0.2 (Table 1); Mixtral-8x7B up to 7100; "more than 4 orders of magnitude larger than the median ... larger than 15,000 in LLaMA2-70B"; "fewer than 10 among tens of millions"; they "exist and remain as largely constant values throughout most of the intermediate layers" (LLaMA2-7B layers 2 to 30); at the starting token and delimiter tokens in a few fixed feature dimensions. Setting them to zero: perplexity inf; setting to their mean: WikiText 5.47 to 5.47, C4 7.85 to 7.86 (negligible). — [arXiv 2402.17762](https://arxiv.org/abs/2402.17762) (text read from the PDF)
- A web-search summary (paper and model not identified, so treat as a lead only) reported a 2026 paper in which two dimensions of the first token exceed 1000 in a Qwen-family model. — no URL attributable; search "massive activations large language models residual stream" 2026-10-21
- TAH-Quant: tile-wise Hadamard activation quantisation at 3-4 bits for pipeline-parallel **training** over slow networks (motivated by outlier handling); not inference. — [arXiv 2506.01352](https://arxiv.org/abs/2506.01352)

### Inferences
- **Q8_0 arithmetic (llama.cpp block format, 32 values + F16 scale = 34 B):** 2048-wide F32 (8,192 B) becomes 64 x 34 = 2,176 B (**3.76x**); F16 (4,096 B) becomes 2,176 B (1.88x). Per-element error is about max/254; for a typical block (max ~2.2 sigma) the RMS error is ~0.5% of sigma. In a block holding a massive value of ~2000 the step is 2000/127 = 15.7, so the other 31 values (typical magnitude 0.2-1) all round to 0 or +/-15.7. That is destructive in absolute terms, but after RMSNorm the norm is dominated by the massive dimension (rms ~ 2000/sqrt(2048) = 44), so those neighbours are ~0.005 in normalised units; the damage may be small in effect. **UNVERIFIED for Qwen2.5-3B**; needs a measurement (KL divergence and top-1 agreement over a few hundred tokens, with and without the cast at the stage boundaries).
- F16 has range 65,504 (covers 15,000) and ~0.05% relative error, and BF16 has the range of F32 and ~0.4%; neither has the block-outlier problem, which is why a F16/BF16 cast is the lower-risk reduced-precision option. Upstream chose BF16 for its all-reduce partials.
- Our own matmuls already quantise their F32 activation inputs to Q8_0 when weights are Q8_0 (ggml-cpu `vec_dot_type`; from my knowledge of ggml, **UNVERIFIED here**), but that happens after the norm, not on the residual; a stage-boundary cast would add error to the residual path itself, which persists to the logits.
- The F37 caveat already on file: near-tie token flips between x86 and ARM; lossy transfer adds another flip source, so the gate would need a defined tolerance.

### Gaps
- No llama.cpp discussion or benchmark of Q8/4-bit activation transfer over RPC was found. No measurement of Qwen2.5-3B's hidden-state outliers exists in the repo or in sources found.
- The Petals quality claim is for BLOOM-176B-class models and a different quantiser; no source shows it for a 3B Qwen with Q8_0.

## Q4. Avoiding the 608 KB logits transfer: backend sampling (i) and running the output layer on the coordinator (ii)

### Takeaway
**Backend sampling exists, merged 2026-01-04 (PR #17004), is in the pin, and on a read of the pin's source nothing excludes the RPC device**: the sampler is built for the buffer type of `model.dev_output()` (the last RPC endpoint in our runs), greedy is a single `ggml_argmax`, the support check goes through `ggml_backend_dev_supports_op` (RPC answers `true`), and the full-logits host copy is skipped when every sequence has a sampler, leaving a 4-byte token. It has **never been run over RPC by anyone I could find**, it is marked EXPERIMENTAL, and it is disabled in tensor-split mode (irrelevant to layer split). Moving the output layer to the coordinator (`n_gpu_layers = n_layer` instead of 999) gives the same network saving but trades it for laptop compute and RAM.

### Cited Findings
- PR #17004 "sampling : add support for backend sampling": merged 2026-01-04 by ggerganov after 179 commits; sampler ops become part of the model graph; "only the sampled token needs to be transferred from device memory to host memory" when the backend selects a token, otherwise "only the filtered logits or probabilities"; recommended CUDA with `-DGGML_CUDA_CUB_3DOT2=ON` and `--backend-sampling --parallel 1`; samplers top-k, top-p, min-p, temp; incompatible with grammar; one output per sequence per batch; flags `-bs/--backend-sampling`, `LLAMA_ARG_BACKEND_SAMPLING=1`; one commit shows 278.4 to 373.5 t/s on a small model (device not named). The page text read (about 300k of 585k characters) has no mention of RPC. — [PR #17004](https://github.com/ggml-org/llama.cpp/pull/17004)
- API at the pin: `llama_context_params.samplers` / `n_samplers` ("backend sampler chain configuration ... the samplers must be sampler chains"), `llama_set_sampler`, `llama_get_sampled_token_ith`, `..._logits_ith`, `..._probs_ith`, `..._candidates_ith`; header warns EXPERIMENTAL parameters "may cause crashes or incorrect results in certain configurations"; `llama_sampler_i` has `backend_init(smpl, buft, n_outputs_max_per_seq)`, `backend_apply`, `backend_set_input`, `backend_reset`. — [llama.h @4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/include/llama.h)
- `src/llama-sampler.cpp` at the pin: greedy backend apply is `struct ggml_tensor * curl = ggml_argmax(ctx, logits);` (named `greedy_argmax`, set as `data->sampled`); dist uses SOFTMAX, CUMSUM, STEP, SUM, CLAMP, GET_ROWS plus a uniform-random **input tensor** set each token; `llama_sampler_backend_support` builds a probe graph and tests every node with `ggml_backend_dev_supports_op(device, op)`. — [llama-sampler.cpp @4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/src/llama-sampler.cpp)

- The probe today samples on the CPU: `native/split/probe.cpp:77-80` uses `llama_sampler_init_greedy()` and `llama_sampler_sample(sampler, ctx, -1)`; `n_gpu_layers = 999` (`:56`), `split_mode = LLAMA_SPLIT_MODE_LAYER` (`:57`). — [probe.cpp](/home/user/ShareCompute/native/split/probe.cpp)
- Physical placement (F43 run): `layer 36 assigned to device RPC2` (the output slot), `offloaded 37/37 layers to GPU`; RPC0/1/2 free memory 768/2048/1536 MiB, which the coordinator log maps to laptop/android/iphone budgets, so the **iPhone** held the head and returned the logits in that run; `CPU_Mapped model buffer size = 315.30 MiB` equals the Q8_0 size of 151,936 x 2048 (330,612,736 B = 315.30 MiB), i.e. the head is a tied copy of `token_embd`. - F46 (repo): about 54 s of the cold interval is plausibly the first 330 MB tensor at the iPhone's 6.1 MB/s. — [F45/F46 text in findings.md](/home/user/ShareCompute/findings.md) (line 2983 onward)

### Inferences
- **(i) Backend sampling over RPC, arithmetic:** the logits are 151,936 x 4 = 607,744 B per token. Replaced by one I32 (4 B): saves 607,740 B = **101.3 ms at 6.0 MB/s (48 Mbit/s)**, **22.5 ms at 27 MB/s (216 Mbit/s)**. At 726.5 ms/token that is 1.376 to 1.599 tok/s (+16.2%); at 851.3 ms, 1.175 to 1.333 (+13.5%). Probe change: build the context with a `llama_sampler_seq_config` holding a chain with `llama_sampler_init_greedy`, then call `llama_get_sampled_token_ith(ctx, -1)` (or `llama_sampler_sample`, whose behaviour with backend tokens I did not read). Fallback if ARGMAX misbehaves: a chain `top_k(k)` on the backend then greedy on the CPU moves only k x 8 B, since the PR runs "the longest contiguous chain of backend supported samplers from the start".
- **Risks specific to us, all UNVERIFIED:** (a) the sampler nodes may change the graph or defeat `can_reuse`, flipping `GRAPH_RECOMPUTE` back to full `GRAPH_COMPUTE` (+0.1-0.3 MB/link/token, could cost more than it saves): check client-to-worker bytes stay ~11 KB per link; (b) RPC's `supports_op` is always true, so a missing kernel on a worker is an uncatchable abort (F25), not a graceful fallback (ARGMAX is a standard CPU op, from my knowledge); (c) EXPERIMENTAL flag; (d) token equality relies on `ggml_argmax` and the CPU greedy sampler breaking ties the same way (first maximum), unread; (e) sending 4 B instead of 608 KB removes no round trip, so only the bandwidth term improves.
- **(ii) Output layer on the coordinator:** `n_gpu_layers = n_layer (36)` instead of 999 puts the head on the host (assumption from llama.cpp's n_gpu_layers semantics: the +1 offloaded layer is the output; consistent with `offloaded 37/37` at 999). The last phone then returns an 8,192 B activation instead of 607,744 B: net bytes saved 599,552 B = **99.9 ms at 48 Mbit/s, 22.2 ms at 216**. Cost: the laptop must read 330.6 MB of Q8_0 per token (311.2 M weights, 0.62 GFLOP): **33 ms at 10 GB/s, 55 ms at 6 GB/s, 17 ms at 20 GB/s** (laptop bandwidth unmeasured), minus whatever the phone no longer spends on the head (unmeasured, and I count 0 as a worst case). Net change in token time at 48 Mbit/s: -45 to -83 ms (faster); at 216 Mbit/s: -5 to +33 ms (no gain, possibly slower). Other effects: frees 315.3 MiB of the phone's budget (pooled 3,209.1 to 2,893.8 MiB, still above the 2,048 MiB largest budget), removes the 330.6 MB cold upload (about 54.2 s at 6.1 MB/s), but puts a 315 MiB hot working set on a laptop whose free RAM bottomed at 89.2 MiB (F45) and whose checksum reads ran at 134 MiB/s (if the pages are evicted each token that is 2.3 s/token: UNVERIFIED worst case), and changes F43's byte-identical pooled-allocation baseline.
- **(i) dominates (ii)** unless (i) fails over RPC: same network saving, no laptop compute, no RAM risk, no change to the budget accounting; (ii) is a configuration-only fallback (one constant in `probe.cpp:56`).

### Gaps

## Q5. Message coalescing, TCP_NODELAY, socket buffers (v) and link choice (vi)

### Takeaway
TCP_NODELAY is **already on at every hop** (RPC client and server sockets at the pin, both phone apps, and asyncio's default in the relay), so there is no Nagle/delayed-ACK stall to remove. Coalescing is a few milliseconds at most and unmeasured; socket buffers are irrelevant at these bandwidth-delay products. Link choice matters twice: bandwidth (a faster phone link is worth up to about 83 ms/token until the Python relay's ~27 MB/s ceiling) and latency, where the Android app currently runs **with no Wi-Fi lock on API 34+**, so Wi-Fi power save may be adding delay we have never measured.

### Cited Findings
- Pin `transport.cpp`: `setsockopt(... TCP_NODELAY ...)` in `accept()` (server side) and `connect()` (client side); `SO_REUSEADDR` on the listener only; no `SO_SNDBUF`, `SO_RCVBUF`, keepalive, `TCP_CORK` or `MSG_MORE`; `send_data`/`recv_data` loop plain `send`/`recv` with flags 0; `MAX_CHUNK_SIZE` = 1 GiB. `socket_t::flush()` "must be called at every message boundary: the RDMA transport coalesces writes ... No-op on TCP." — [transport.cpp @4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/transport.cpp), [transport.h @4da6337](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/transport.h)
- Pin `send_rpc_cmd` issues **three** `send_data` calls per message (1-byte command, 8-byte size, payload) then `flush()`. — pin ggml-rpc.cpp
- Python asyncio: "The socket option TCP_NODELAY is set by default for all TCP connections" (3.6+, `create_connection`/`create_server`; the page does not mention `start_server`, which calls `create_server` per my knowledge, not verified here). — [asyncio event loop docs](https://docs.python.org/3/library/asyncio-eventloop.html)
- Repo: Android sets `setTcpNoDelay(true)` on both sockets (`WorkerSession.java:75,116`); iOS sets `tcp.noDelay = true` (`WorkerModel.swift:106`); the relay `copy()` reads 65,536 B chunks and `drain()`s per chunk (`scripts/split_cluster.py:125-128`), with `limit=16384` on its streams. — repo files
- Repo: on the Android phone (Android 15, `motorola moto g 5G - 2024`) every physical log shows `{"ev":"wifilock_skipped","why":"inert from API 34"}`; the code comment: HIGH_PERF "deprecated" in Android 14 and LOW_LATENCY "needs the screen on". - Android's Wi-Fi low-latency mode disables power save only when Wi-Fi has internet access, the app holds the lock **and is in the foreground with the screen on**; it needs vendor HAL/driver support. — [AOSP Wi-Fi low latency](https://source.android.com/docs/core/connect/wifi-low-latency)
- Wi-Fi power-save tradeoff: a larger DTIM interval saves power at the price of response time (Espressif doc); typical beacon interval 102.4 ms (my background knowledge, not in the results). — [Espressif Wi-Fi low power](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-guides/low-power-mode/low-power-mode-wifi.html)

- Repo: the relay moved the laptop worker's 573.9 MB at 27.1 MB/s (F48); the iPhone's own rate was 6.1 MB/s (F46); Wi-Fi RTT "has never been measured in this project" (F49); F49's emulation used 0.5 ms one-way to the laptop and 2.5 ms to each phone. — [F48/F49](/home/user/ShareCompute/findings.md)

### Inferences
- **Coalescing:** with NODELAY each of the three `send()`s can leave as its own TCP segment, and each small segment is a separate TLS record on the phone tunnel and a separate `read`/`write`/`drain` pass in the Python relay. Messages per link per token are unmeasured; assume ~5 up and 1-2 down, ~17-20 segments per link per token; at ~0.1-0.3 ms per small Wi-Fi frame that is **~2-6 ms/token for two phone links** (0.3-0.8% of 726 ms). A ~10-line sender patch (one `send` of header+payload for payloads under a few KB, or `MSG_MORE` on the first two) is the fix; **UNVERIFIED**, measure message count with the counting proxy first.
- **Socket buffers:** bandwidth-delay product at 6.0 MB/s x 10 ms = 60 KB; at 27 MB/s x 10 ms = 270 KB. Default (autotuned) buffers exceed 60 KB; the 608 KB logits burst is bandwidth-limited, not window-limited. No gain expected.
- **Round trips:** about 1.9 direction switches per connection per token means about 1 blocking round trip per link, 3 in series through the star. Per-token RTT cost = sum over links: with the emulation values 1 + 5 + 5 = **11 ms**; at 3 ms Wi-Fi RTT, 7 ms; at 10 ms, 21 ms.
- **Power save is the one unmeasured latency candidate worth an experiment.** Each phone is busy for roughly a third of a ~0.73-0.85 s token and idle for the rest, so a Wi-Fi radio that dozes after a short idle timeout would make the first downlink packet of each token wait for the next beacon/DTIM (0-102 ms at DTIM 1, so ~51 ms mean per phone, ~100 ms per token for two phones: the same size as the logits cost). That is a **hypothesis**, not a finding: no RTT was measured, and the idle timeout of these two phones is unknown. It would partly explain why physical decode is 287-412 ms/token slower than loopback when bandwidth plus emulated RTT explain only about 118 ms. Test: `ping` each phone from the laptop during a decode (jitter of 0-100 ms between 0.5 s-spaced pings is the signature), then re-measure with a laptop-side keep-warm ping every ~30 ms or with the screen on and a `WIFI_MODE_FULL_LOW_LATENCY` lock.
- **Link choice arithmetic** (phone links to 27 MB/s, the relay's ceiling; laptop link fixed at 27): total bandwidth term goes from 106.9 ms (0.70 + 3.17 + 103.0) to **24.3 ms** (0.70 + 0.70 + 22.9), a **saving of 82.6 ms/token (11.4% of 726.5 ms)**, plus the RTT difference: (5 ms - 0.5 ms) x 2 = 9 ms at the emulated RTT, more if power save is real. Once backend sampling is in, the phone-link bandwidth term is only 0.019 + 0.010 MB over 2 links (4.8 ms at 6.0 MB/s, 1.1 ms at 27), so a faster link then buys only ~3.7 ms of bandwidth, and its remaining value is latency. USB tethering to Windows needs RNDIS (Android) or Apple's driver stack (iPhone) and a charging/thermal plan; Ethernet via USB-C dongle needs a switch or the laptop's second port (4 GB laptop, two phones). None tried here.
- The relay is itself a ceiling: a Python asyncio hop at ~27 MB/s (F48) means the 608 KB burst costs at least 22.5 ms on the laptop even on an infinitely fast phone link.

### Gaps
- No Wi-Fi RTT, packet count, or per-message count has been measured on the physical setup; "messages per token" and "ms per small frame" above are assumptions.
- The phones' Wi-Fi standard/band and why the iPhone sustains only 6.1 MB/s are unknown; whether the 48 Mbit/s is the radio, TLS in the Java/Network.framework path, or the relay is not established (F50 lists it unmeasured).
- No controlled USB-tethering throughput/RTT data for iPhone or for a TLS-reverse-tunnel workload.

## Q6. Ranking, with arithmetic: is "activation quantization (Q8_0) the highest-ROI network win" true?

### Takeaway
**No. For ShareCompute's measured layer-split decode the claim is wrong by a factor of about 30.** Activations are 6.2% of per-token bytes (40,960 of 656,000 B; 24,576 B on Wi-Fi) and cost **4.7 ms** of a 726 ms token at 48 Mbit/s even if sent for free, so Q8_0 saves **3.5 ms**; the F32 logits are 92.7% of bytes and cost **101 ms**. The ranking is: backend sampling (about -101 ms) > a faster phone link (about -83 ms bandwidth, plus an unmeasured latency term) ~ output layer on the coordinator (net -45 to -83 ms) >> coalescing (0-6 ms, unverified) > F16/Q8_0 activations (2.4 / 3.5 ms) > graph caching (already merged, about 0). No network-only change reaches 2x: removing every network byte and 11 ms of RTT gives 726.5 to ~608 ms = 1.64 tok/s (+19%).

### Cited Findings
- The source report's claim and the "~2x token-generation speedup from community patches" for graph caching: **no source found** for either as stated. The only graph-caching measurements are PR #15405's: +1%, +6%, +13%, +24.5% depending on model and link, and the feature is already in the pin (Q1). — [PR #15405](https://github.com/ggml-org/llama.cpp/pull/15405); searches 2026-10-21 for a "2x RPC" patch returned nothing
- Per-token byte counts and timings are those in the preamble. — [F49](/home/user/ShareCompute/findings.md) (3559-3590), [physical-3b-capacity README](/home/user/ShareCompute/docs/evidence/physical-3b-capacity/README.md)

### Inferences
Assumptions: phone links 6.0 MB/s (48 Mbit/s) or 27 MB/s (216 Mbit/s); laptop link 27 MB/s (relay ceiling, F48); the logits-carrying phone is behind a phone link; decimal MB; 5 activation crossings per token (embedding input to link 1, link 1 down, link 2 up, link 2 down, link 3 up), of which 3 cross Wi-Fi.

**Per-token network cost, current state**

|---|---:|---:|---:|
| logits (151,936 x 4 B, last link down) | 607,744 | 101.3 | 22.5 |
| activations (5 x 8,192 B; 3 on Wi-Fi) | 40,960 | 4.7 | 1.5 |
| descriptors, positions, mask, recompute msg (remainder of 656,000) | ~7,300 | ~1.0 | ~0.3 |

- **When activation compression would matter:** long-prompt prefill (activations scale with tokens: a 512-token ubatch is 4.19 MB per crossing, 2.1 s over three Wi-Fi crossings at 6.0 MB/s, Q8_0 would save ~1.5 s of it) and large hidden sizes with small vocabularies. Our measured 5-token prefill took 11.3-12.4 s on hardware against 1.04 s on loopback with about 0.2 MB of activations moved (5 tokens x 40,960 B), so prefill time in our tests is not bandwidth: the cause is unexplained (F48 saw 28.9 s warm).
- **Order of work:** (1) one cheap loopback run of backend sampling (check tokens, check client-to-worker bytes stay ~11 KB per link, check bytes from the last link drop to ~0.01 MB); (2) a `ping`-during-decode measurement of the two Wi-Fi links and a power-save A/B (screen-on LOW_LATENCY lock on Android; keep-warm ping for both); (3) only then consider link changes; (4) leave activation quantisation and coalescing until (1) and (2) are known, since after (1) the remaining network bytes are ~0.03 MB/token and every bandwidth-side change is worth under 5 ms.
- Not additive: (i) and (ii) are alternatives; (i) and (vi) overlap on the logits term.

### Gaps

- The 11 ms RTT is the F49 emulation, not a measurement. Wi-Fi RTT, power-save behaviour, per-message counts and the relay's per-hop latency are all unmeasured.
- Whether sampling and graph reuse coexist on RPC (Q4 risk a), and whether `ggml_argmax` and the CPU greedy sampler agree on ties, need a run.
- The brief's "~2x token-generation speedup" and "Q8_0 highest-ROI" claims could not be traced to any PR, fork or paper; they may come from a source I did not find, so they are reported as unsupported, not as disproven in general.
