# Distributed and pipeline-aware speculative decoding, and what transfers to a laptop + phones llama.cpp pipeline

Research date: 2026-10-21. Scope: AMUSD, DSSD, FlowSpec, PipeInfer and neighbouring edge / pipeline / heterogeneous speculative-decoding systems, assessed against ShareCompute (one llama.cpp model layer-split over a 4 GB laptop, an Android phone and an iPhone via ggml-rpc, star topology through a laptop relay). Project figures are cited to local files; everything else to the primary paper, repo or issue page I fetched. "UNVERIFIED" marks anything I could not confirm from a primary source. Conventions: "arXiv HTML" means I read the paper text through the fetch tool, which summarises pages, so exact numbers are as the tool reported them; where it flagged a text/table mismatch I say so.

Name-collision warning for the report writer: three unrelated papers abbreviate to "DSD/DSI/DSSD": DSSD (Ning et al., split verification), DSD (Yu, Li, McDanel, Zhang, edge-cloud simulator), DSI (Timor et al., speculation parallelism). A fourth, "Decentralized Speculative Decoding (DSD)" from Gradient Network, turned up in search (not read; UNVERIFIED). I found no paper or project called "DistriSpec" ([search for the name returned only DSD, StarSD, DistillSpec and similar](https://arxiv.org/html/2511.11733v1)); treat it as not located.

## 1. Do AMUSD, DSSD and FlowSpec exist as described? Where do draft and verifier run, what crosses devices, what speedups, is code public, is it llama.cpp?

### Takeaway
All three exist as arXiv preprints with public code, but none is llama.cpp-based and none has been run on phones. AMUSD's "multi-device" means two GPUs in one host sharing CPU memory (no network at all), so it does not address a Wi-Fi star; DSSD is a device-to-base-station draft/verify split with an emulated link; FlowSpec is the only one of the three that is genuinely a multi-edge-device pipeline (5 Jetson Orin Nano on a LAN), and it is PyTorch/EAGLE-2, not ggml.

### Cited Findings

**AMUSD (Asynchronous Multi-Device Speculative Decoding)**
- Paper: "AMUSD: Asynchronous Multi-Device Speculative Decoding for LLM Acceleration", Bradley McDanel (Franklin and Marshall College), arXiv 2410.17375, submitted 22 Oct 2024; arXiv preprint, no peer-reviewed venue named on the page — [arXiv HTML](https://arxiv.org/html/2410.17375v1), [PDF](https://arxiv.org/pdf/2410.17375).
- Placement: draft process on GPU 0, verify process on GPU 1; the paper says processes could run on "GPUs, CPUs, or specialized accelerators" — [arXiv HTML](https://arxiv.org/html/2410.17375v1).
- What crosses between "devices": two shared tensors in shared CPU memory (draft tokens, verified tokens) plus `multiprocessing.Event` control flags; on a mismatch at position i the verifier keeps tokens up to i-1 and sets a rollback flag, the drafter crops its tokens and KV cache. No locks because each buffer has one writer. Network and interconnect are not discussed — [arXiv HTML](https://arxiv.org/html/2410.17375v1).
- Hardware/models: 4x NVIDIA A100 plus an AMD EPYC 7313; verify Llama-3.1-8B, draft Llama-3.2-1B (draft about 10 ms/token, verify about 25 ms/token standalone) — [arXiv HTML](https://arxiv.org/html/2410.17375v1).
- Speedups vs autoregressive: HumanEval 1.57x (14.08 ms/token) vs plain speculative 1.24x; MT-Bench 1.31x vs 1.06x; RefactorChat 1.96x vs 1.43x; abstract: average 29% over speculative decoding. Draw is about 300 W across two GPUs vs 150-220 W for single-GPU methods; on one RefactorChat sample AMUSD accepted fewer drafts per verify step (2.75 vs 5.35) — [arXiv HTML](https://arxiv.org/html/2410.17375v1).
- Code: https://github.com/BradMcDanel/AMUSD/ (link given in the paper; I did not open the repo, so its language/framework is UNVERIFIED). The paper does not mention llama.cpp or ggml — [arXiv HTML](https://arxiv.org/html/2410.17375v1).

**DSSD (Distributed Split Speculative Decoding)**
- Paper: "DSSD: Efficient Edge-Device LLM Deployment and Collaborative Inference via Distributed Split Speculative Decoding", Jiahong Ning (Dalian Maritime University), Ce Zheng (Pengcheng Laboratory), Tingting Yang; arXiv 2507.12000 (v2 dated 17 Jul 2025). The ICML 2025 virtual site lists it as a poster in the ML4Wireless workshop (a workshop, not the main track) — [arXiv HTML](https://arxiv.org/html/2507.12000v2), [ICML page](https://icml.cc/virtual/2025/47046).
- Placement: OPT-125M draft on the device proposes gamma tokens; OPT-6.7B or OPT-13B target at the base station. The base station performs only Accept/Reject; the device performs Resample, which is needed only on rejection — [arXiv HTML](https://arxiv.org/html/2507.12000v2).
- Messages: uplink is token indices plus the scalar draft probability for each of gamma tokens ("less than 50 bytes each time" vs about 61,269 bytes per round for the DSD-style baseline that uploads vocabulary distributions); downlink is a full vocabulary distribution only when a rejection occurs, otherwise the accepted token and index — [arXiv HTML](https://arxiv.org/html/2507.12000v2).
- Results: homogeneous (two H800): text claims 1.5x-2.4x for DSSD while the baseline "only remains at 1x or even lower". Heterogeneous (A6000 device, H800 base station): up to 1.8x (OPT-13B) and 1.4x (OPT-6.7B). Link is emulated: RTT 0/20/50 ms, bandwidth 100 Mbps (tables also use 10 and 50 Mbps); GPUs are real; 128-token prompt, 128 generated, top-k 10, temperature 1.0. The fetch flagged mismatches between text and Table 2/3 (for example gamma=6 text vs gamma=8 table rows), so treat exact ratios as approximate — [arXiv HTML](https://arxiv.org/html/2507.12000v2).
- A later survey restates DSSD at 50 ms delay, 10 Mbps, gamma=8 as 2.19x (OPT-6.7B) and 1.62x (OPT-13B) over cloud autoregressive, where its predecessor reaches only 43% of cloud-AR throughput — [Lyu et al. survey](https://arxiv.org/html/2606.25091).
- Code: https://github.com/JasonNing96/DSSD-Efficient-Edge-Computing. Not llama.cpp; only OPT models tested; a Chinese patent application is noted in the paper (CN2025108856278) — [arXiv HTML](https://arxiv.org/html/2507.12000v2).

**FlowSpec (Continuous Pipelined Speculative Decoding)**
- Paper: "FlowSpec: Continuous Pipelined Speculative Decoding for Efficient Distributed LLM Inference", Xing Liu, Lizhuo Luo, Ming Tang (corresponding), Chao Huang, Xu Chen (SUSTech, Montclair State, Sun Yat-sen); arXiv 2507.02620, v3 dated 10 Jan 2026; arXiv preprint, no venue named — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Placement: N+1 devices, one per stage. Device 0 runs the draft model and owns the draft tree (tree ops on CPU, forward on GPU); the base model is split into N layer blocks on devices 1..N — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Messages per step: draft token segments with tree position IDs and attention masks, pipeline intermediate results, and pruning info (index sets, "a few hundreds of bytes") — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Mechanisms (per abstract summary): score-based step-wise verification, draft management that prunes invalid tokens while keeping causal order, dynamic draft expansion — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3). Targets sparse single-request edge workloads where a plain pipeline sits mostly idle.
- Testbed: 5x NVIDIA Jetson Orin Nano (8 GB unified, about 5 GB usable GPU), LAN at up to 1000 Mbps; 13B models on four devices with W4A16 (bitsandbytes); LLaMA2-Chat 7B/13B and Vicuna-v1.3 7B/13B inside EAGLE-2; six datasets — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Speedup vs Chunk-PP (plain pipeline), mean over six tasks (Table I, T=0): 1.43x (LLaMA2 7B), 1.43x (Vicuna 7B), 1.69x (LLaMA2 13B), 1.68x (Vicuna 13B); PipeDec baseline 1.14-1.21x; abstract says 1.37x-1.73x over baselines (the text's "up to 1.73x" is not exactly in the table) — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Tensor-parallel baselines (Megatron-LM, Galaxy; 7B fp16 only) reach only about 0.33-0.35x of Chunk-PP throughput — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Bandwidth: pipeline methods keep over 90% of performance dropping from 1000 to 125 Mbps while tensor parallel falls to about 40%; FlowSpec stays above 1.37x over Chunk-PP at every tested bandwidth (125 Mbps was the lowest shown) — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).
- Stack and code: PyTorch 1.11 on JetPack 5.1.2, extends the EAGLE-2 codebase, not llama.cpp. Code: https://github.com/Leosang-lx/FlowSpec (link from the paper; repo not opened). Stated limits: bounded by draft quality; more stages add transmission overhead — [arXiv HTML v3](https://arxiv.org/html/2507.02620v3).

### Inferences
- AMUSD's contribution that transfers is the idea (decouple drafting from verifying, roll back on mismatch), not its transport: its "device" boundary is shared host memory, so none of its numbers say anything about Wi-Fi.
- DSSD's contribution that transfers is the traffic-minimisation idea (send ids + scalars up, full distribution down only on rejection). It is built for a draft-on-device / target-on-server split, which is the wrong shape for ShareCompute (the "server" here is itself a three-device pipeline). Its experiments emulate links and use GPUs.
- FlowSpec is the closest architectural match (a draft stage plus N verification stages of one layer-split model over a LAN) but it assumes direct stage-to-stage forwarding and GPUs with at least 125 Mbps, versus phones at about 48 Mbit/s through a relay in ShareCompute (see Q5 for the project's link figures).

### Gaps
- Did not open the three GitHub repos; framework, licence, maintenance and any llama.cpp port are UNVERIFIED.
- Peer-reviewed venues for AMUSD and FlowSpec were not found (preprints as of the fetched versions).
- DSSD's text/table inconsistencies mean exact per-condition ratios could not be pinned down.

## 2. What other distributed / edge / pipeline-aware speculative-decoding systems matter?

### Takeaway
The pipeline-aware family (PipeInfer, PipeDec/SpecPipe, FlowSpec) and the edge-cloud family (DSSD, PicoSpec, SpecEdge, DSD, AceSpec) solve different problems: the first keeps layer-split stages busy; the second hides WAN round trips and shrinks distribution traffic. Only PipeInfer is llama.cpp-based, and only llama.cpp itself (June 2026 maintainer statement) supports a remote draft over RPC.

### Cited Findings
Entries: what it does / draft vs verifier / messages / numbers / code / llama.cpp.

**Pipeline-aware**
- **PipeInfer** — "PipeInfer: Accelerating LLM Inference using Asynchronous Pipelined Speculation", Branden Butler, Sixing Yu (Iowa State), Arya Mazaheri (TU Darmstadt), Ali Jannesari (Iowa State); arXiv 2407.11798, SC 2024 per the arXiv v2 listing and a TU Darmstadt BibTeX entry (I did not open the ACM/IEEE record). Details in Q4 — [arXiv HTML v1](https://arxiv.org/html/2407.11798v1), [arXiv v2 abs](https://arxiv.org/abs/2407.11798v2), [TU Darmstadt BibTeX](https://hlr-244.parallel.informatik.tu-darmstadt.de/pub-lists/get_bibtex.php?pubid=1971). llama.cpp-based; code https://github.com/AutonomicPerfectionist/PipeInfer (MIT).
- **PipeDec / SpecPipe** — arXiv 2504.04104 (Yin et al., Shandong University; v1 titled PipeDec, v2 retitled SpecPipe). Draft model integrated into the large model's pipeline, each draft prediction forwarded immediately to later stages, a dynamic prediction tree manages sequences across nodes. v1: Llama-3.2-1B draft with a 14-stage pipeline accelerating Llama-3.1-70B, 4.46x-7.79x over plain pipeline parallelism and 2.2x-2.69x over tree-based speculative decoding; v2 (8-stage): 4.19x-5.53x and 2.08x-2.38x. Code availability not found; not llama.cpp as far as I could tell (UNVERIFIED) — [v1](https://arxiv.org/html/2504.04104v1), [v2](https://arxiv.org/html/2504.04104v2), [search summary](https://arxiv.org/pdf/2504.04104). FlowSpec uses PipeDec as a baseline — [FlowSpec](https://arxiv.org/html/2507.02620v3).
- **SpecInfer** (tree verification origin) — Xupeng Miao et al., arXiv 2305.09781, ASPLOS 2024. Merges small-model speculations into a token tree and verifies all branches in one pass with tree attention, preserving the output distribution — [arXiv](https://arxiv.org/pdf/2305.09781). PipeInfer's verification reuses SpecInfer's algorithm — [PipeInfer](https://arxiv.org/html/2407.11798v1). I did not retrieve SpecInfer's own speedup numbers (UNVERIFIED).
- **Staged speculative decoding** — Benjamin Spector and Chris Re, arXiv 2308.04623, ICML 2023 workshop. Restructures the speculative batch as a tree and adds a second speculation stage that accelerates the draft model itself; aimed at small-batch on-device inference; 3.16x single-batch latency reduction for a 762M GPT-2-L (abstract only; I did not read the body) — [arXiv](https://arxiv.org/pdf/2308.04623).
- **DSI (Distributed Speculative Inference)** — Nadav Timor et al., ICLR 2025, arXiv 2405.14105. "Speculation parallelism": target and drafter instances run concurrently on separate processors; simulated 1.29-1.92x over standard speculative inference; code released. A single-node multi-GPU technique, so no network cost model — [ICLR page](https://proceedings.iclr.cc/paper_files/paper/2025/hash/b36554b97da741b1c48c9de05c73993e-Abstract-Conference.html), [arXiv](https://arxiv.org/abs/2405.14105v5).
- **EdgeShard** — Mingjin Zhang, Jiannong Cao, Xiaoming Shen, Zeyang Cui, IEEE Internet of Things Journal 2025 (DOI 10.1109/JIOT.2024.3524255), arXiv 2405.14371. Layer-sharding across edge devices and cloud with dynamic programming over compute, bandwidth and memory; pipeline-parallel inference; up to 50% latency reduction and 2x throughput on a heterogeneous physical testbed with Llama2 models. I found no speculative-decoding component in the sources I read, so it is a placement/pipelining reference, not a speculation system — [arXiv HTML](https://arxiv.org/html/2405.14371v1), [PolyU record](https://research.polyu.edu.hk/en/publications/edgeshard-efficient-llm-inference-via-collaborative-edge-computin/).
- **Jupiter** — arXiv 2504.08242. Collaborative edge inference; decode phase combines "outline-based" pipeline parallelism with self-drafting speculative decoding (extra FFN heads on the logits); abstract reports up to 26.1x end-to-end latency reduction with "on-par" quality. The outline mechanism appears to change what is generated, so the 26.1x is likely not a lossless-decoding number (UNVERIFIED; I read only search-result abstract text) — [arXiv](https://arxiv.org/pdf/2504.08242).

**Edge-cloud / draft-on-edge**
- **PicoSpec** — Yida Zhang et al. (USTB), arXiv 2603.19133, 27 Mar 2026, no venue. Draft SLM on a Jetson AGX, target on A100s (Qwen3-32B on 2, Llama-3.1-70B on 4). Asynchronous pipeline: verification of step i overlaps drafting of step i+1. Uplink under 50 bytes per round (probabilities), downlink only on rejection: top-K (id, prob) pairs (K=10), versus about 500 KB per rejected token for a full 128,256-entry vocabulary. Throughput vs cloud autoregressive: Qwen 0.6B/32B 1.45x (GSM8K), 1.13x (HumanEval); Llama 1B/70B 2.51x, 2.90x; vanilla speculative 0.44-1.45x. WAN described but bandwidth/RTT values not given; no code link; not llama.cpp — [arXiv HTML](https://arxiv.org/html/2603.19133).
- **SpecEdge** — KAIST (project page on ina.kaist.ac.kr; author list not checked), NeurIPS 2025 spotlight, arXiv 2505.17052. Edge consumer GPUs draft, server verifies; only token outputs cross the network; proactive edge drafting overlaps with server verification; 2.22x server throughput, 1.91x cost efficiency, 11.24% lower inter-token latency vs server-only; code released. A later survey says its latency advantage holds only below about 50 ms RTT (36.5 ms vs 42.4 ms/token at low RTT; at 65 ms RTT, 44.5 ms, slower) — [arXiv HTML](https://arxiv.org/html/2505.17052v2), [NeurIPS](https://proceedings.nips.cc/paper_files/paper/2025/hash/8587069d00a69d0ea498d547fffad6dd-Abstract-Conference.html), [project page](https://ina.kaist.ac.kr/projects/specedge/), [survey](https://arxiv.org/html/2606.25091).
- **DSD (edge-cloud)** — Fengze Yu, Leshu Li, Brad McDanel, Sai Qian Zhang, arXiv 2511.21669 v2 (1 Dec 2025), "under review". Headline results come from a calibrated discrete-event simulator (DSD-Sim, built on VIDUR; latency predictor error 7.4% prefill, 5.2% decode), RTTs of 10 and 30 ms assumed from public cloud latency reports; up to 1.1x speedup and 9.7% throughput over speculative baselines via Adaptive Window Control; distributed execution loses to cloud-only beyond roughly 50-60 ms RTT in the sim; no code link found — [arXiv HTML](https://arxiv.org/html/2511.21669).
- **AceSpec** — Yida Zhang et al., arXiv 2609.02514, 2 Sep 2026. Precomputes a probabilistic state cache on idle edge compute so a rejected-draft flush is a local lookup; uplink = main-chain token indices, downlink = sparse probability distributions; up to 3.52x throughput, near-peak under a 50 Kbps WAN. Abstract only; setup and baselines UNVERIFIED — [arXiv abs](https://arxiv.org/abs/2609.02514).
- **Koh and Yang** — "Collaborative Large Language Model Inference via Resource-Aware Parallel Speculative Decoding", arXiv 2511.01695 (Nov 2025). Draft on phones, target on edge servers; multi-agent RL for user association and resource allocation; Sionna simulation only, up to 28.0% (average 23.7%) latency reduction — [search summary of arXiv listing](https://arxiv.org/pdf/2511.01695).
- **Zhu et al.** — "Efficient LLM Inference over Heterogeneous Edge Networks with Speculative Decoding", arXiv 2510.11331 (Oct 2025). Draft SLM at a small base station, target at a macro base station over wired fronthaul; simulation only; up to 44.9% latency reduction vs uniform bandwidth allocation; pipelined serving 30-32% lower latency than non-pipelined SD — [arXiv HTML](https://arxiv.org/html/2510.11331v1).
- **Survey with a break-even analysis** — Yuan Lyu, Bharath Irukulapati, Jaya Prakash Champati (University of Victoria), "Speculation at a Distance: Where Edge-Cloud Speculative Decoding Actually Pays Off", arXiv 2606.25091 v2, 5 Sep 2026. Covers DSSD, TSLT, PicoSpec, DSD, SLED, SpecEdge, PipeSD, Koh et al.; proves pipelined distributed SD cannot beat co-located SD when RTT >= gamma x t_d (Prop. 12); gives break-even RTTs (for example standard target t_ar=50 ms, gamma=5, t_d=10 ms: 47 ms at acceptance 0.7, 108 ms at 0.85); notes systems avoid |V|-sized payloads by greedy verification (token IDs only), DSSD's rejection-only downlink, or TSLT's truncated logits — [arXiv HTML](https://arxiv.org/html/2606.25091).

**Heterogeneous CPU/GPU and on-device**
- **Dovetail** — National University of Defense Technology; arXiv 2412.18934, EMNLP 2025. Draft model on the (weaker) GPU, target on the CPU; fewer, deeper draft steps and a Dynamic Gating Fusion module; earlier preprint: 5.86 tokens/s for LLaMA2-Chat-7B with 3 GB VRAM (about 2.77x over CPU-only); EMNLP version: 1.79x-10.1x on 13B across devices. Repo https://github.com/ddInference/Dovetail has a thin README, 3 commits, no licence shown, stack not stated (llama.cpp use is UNVERIFIED and unlikely from what I saw) — [arXiv HTML](https://arxiv.org/html/2412.18934v2), [repo](https://github.com/ddInference/Dovetail).
- **Ghidorah** — Jinhui Wei et al., arXiv 2505.23219 (Jun 2025). Speculative decoding plus CPU/GPU hetero-core parallelism on a Jetson NX (unified memory); verification width 16 was best because the 6-core ARM CPU's efficient range ends around 16 tokens; up to 7.6x over sequential decoding (3.27x algorithmic x 2.31x parallel); FasterTransformer/CTranslate2-derived, not llama.cpp; code "will be open-sourced" — [arXiv HTML](https://arxiv.org/html/2505.23219).
- **Mobile NPU context** — arXiv 2510.15312 reports 1.06x-3.81x speedups on commercial phones by drafting from retrieved context rather than a model, and argues model-based drafting costs too much memory on mobile NPUs — [arXiv HTML](https://arxiv.org/html/2510.15312v4). Blog posts claiming 2-3x for a draft model on phones cite no reproducible benchmark and I did not use them.
- **prima.cpp** (llama.cpp-derived, home clusters over Wi-Fi) — Zonghang Li et al., arXiv 2504.08791 (Apr 2025). Piped-ring parallelism with prefetching, Halda layer-assignment scheduler; four-node home cluster beats llama.cpp, exo and dllama on 30B+ models. No speculative decoding component found in the sources I read — [arXiv HTML](https://arxiv.org/html/2504.08791v1).

**llama.cpp itself (current upstream)**
- Speculative types now include `draft-simple`, `draft-eagle3`, `draft-dflash`, `draft-dspark`, `draft-mtp`, and several n-gram types (`ngram-cache`, `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`, `ngram-mod`); draft flags include `--spec-draft-model`, `--spec-draft-device`, `--spec-draft-n-max` (default 3); the page says nothing about RPC — [docs/speculative.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md).
- Issue #23982 (opened 1 Jun 2026, closed 22 Jun 2026) asked for a GPU draft model over the network; maintainer ggerganov replied it is "already supported via the RPC backend" using `--rpc`, `--spec-draft-model` and `--spec-draft-device RPC0` on the main machine with `rpc-server` on the drafting machine (example used 127.0.0.1 for both) — [issue 23982](https://github.com/ggml-org/llama.cpp/issues/23982). I did not run this.
- The project's pinned llama.cpp revision 4da6337 is PR #28876 (a server reranker change) — [commit page](https://github.com/ggml-org/llama.cpp/commit/4da6337767f973e2b4d0797e5b323d77d8565e4a), pin recorded in [native/split/llama-revision.txt](../../native/split/llama-revision.txt). PR number 28876 is higher than issue 23982 (June 2026), so the pin is very likely newer than the RPC-draft statement (inference from numbering; the commit date was not shown).

### Inferences
- For ShareCompute the useful split is: pipeline-bubble techniques (PipeInfer, PipeDec/SpecPipe, FlowSpec) address the 3-stage idle time; the edge-cloud papers (DSSD, PicoSpec, SpecEdge, AceSpec, DSD) mostly contribute payload-shrinking tricks, because their bottleneck is a WAN RTT that ShareCompute does not have between the laptop and its own drafter.
- Several headline gains (DSD, Koh, Zhu) are simulation-only; DSSD emulates the link; only FlowSpec, PicoSpec, SpecEdge, Dovetail, Ghidorah and PipeInfer report physical hardware, and none of those includes a phone.

### Gaps
- SpecInfer's own speedup figures, PipeDec's hardware and code status, and Staged SD's body were not retrieved.
- SLED and TSLT (listed in the survey) were not read. A "Decentralized Speculative Decoding" (Gradient) paper appears in search but was not read.
- Whether `--spec-draft-device RPC0` works in the pinned build with the project's custom `probe.cpp` is untested.

## 3. Which systems show gains specifically in pipeline-parallel, bandwidth-limited or heterogeneous settings, and by how much?

### Takeaway
Pipeline-parallel gains are real but shrink with shallow pipelines and are reported almost entirely over 1 Gbps links or better: FlowSpec 1.37x-1.73x over a plain pipeline on five Jetsons; PipeInfer up to 2.15x over standard speculative inference on 1 GbE CPU clusters but "marginal" in shallow pipelines; PipeDec/SpecPipe 2-5x on 8-14 stages. The bandwidth-limited results (DSSD, PicoSpec, AceSpec) are about the draft-to-verifier link and win by sending a few bytes, not by pipelining. Nobody reports a 3-stage, phone-class, ~50 Mbit/s star.

### Cited Findings
- Pipeline-parallel: FlowSpec 1.43x-1.70x (mean over six tasks vs Chunk-PP), 5 Jetson Orin Nano, up to 1000 Mbps — [FlowSpec](https://arxiv.org/html/2507.02620v3). PipeDec 4.46x-7.79x over plain pipeline parallelism (14 stages, 70B); SpecPipe 4.19x-5.53x (8 stages) — [PipeDec/SpecPipe](https://arxiv.org/html/2504.04104v2). PipeInfer up to 2.15x over standard (pipeline-parallel SpecInfer-style) speculative inference; roughly 1.5-2.15x across cases, up to 1.7x for well-aligned models and 2.15x for poorly aligned ones; continuous speculation alone up to 1.5x; improvement "marginal when deployed in shallow pipelines" — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Bandwidth-limited, pipeline: FlowSpec keeps above 1.37x over Chunk-PP at all tested bandwidths, lowest shown 125 Mbps; pipeline methods keep over 90% of throughput from 1000 to 125 Mbps while tensor-parallel drops to about 40% — [FlowSpec](https://arxiv.org/html/2507.02620v3). PipeInfer states "a tolerance to latency and throughput limitations" on Gigabit Ethernet (numbers only in a figure I could not read) — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Bandwidth-limited, draft-to-verifier link: DSSD with 10-100 Mbps emulated links and 0-50 ms RTT: 1.4x-2.4x depending on setting — [DSSD](https://arxiv.org/html/2507.12000v2). PicoSpec 1.13x-2.90x over cloud autoregressive on a WAN of unspecified bandwidth — [PicoSpec](https://arxiv.org/html/2603.19133). AceSpec claims near-peak throughput under 50 Kbps (abstract) — [AceSpec](https://arxiv.org/abs/2609.02514).
- Heterogeneous: DSSD A6000 device + H800 server up to 1.8x (13B), 1.4x (6.7B) — [DSSD](https://arxiv.org/html/2507.12000v2). Dovetail (GPU draft, CPU target) 2.77x over CPU-only for 7B in 3 GB VRAM, 1.79x-10.1x on 13B — [Dovetail](https://arxiv.org/html/2412.18934v2). Ghidorah 7.6x on one Jetson (of which 3.27x is acceptance length) — [Ghidorah](https://arxiv.org/html/2505.23219). PipeInfer Cluster B was 13 heterogeneous nodes on 1 GbE; for Falcon extra slow nodes reduced performance "substantially", for Goliath slower nodes improved it — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Counter-evidence: pipelined distributed speculation cannot beat co-located speculation when RTT >= gamma x t_d; SpecEdge and DSD lose their advantage above roughly 50-65 ms RTT — [survey](https://arxiv.org/html/2606.25091), [DSD](https://arxiv.org/html/2511.21669).
- Project link context: the phones' weight uploads ran at about 6.1 MB/s (iPhone) and 6.2 MB/s (Android), i.e. about 45-49 Mbit/s; the emulation rates used in F49 were 216 Mbit/s to the laptop and 48 Mbit/s to each phone — [findings.md F45-F49](../../findings.md) (lines near 3019, 3247, 3579). Wi-Fi round-trip time has never been measured in the project — [findings.md F49 "Not verified"](../../findings.md).

### Inferences
- The lowest bandwidth at which any pipeline-parallel speculative system was shown to keep its gain is 125 Mbps (FlowSpec), about 2.6x the project's phone links; PipeInfer's GbE is about 20x. So transferring the pipeline results to the phones is an extrapolation.
- ShareCompute's pipeline has 3 stages. PipeInfer's own "marginal in shallow pipelines" statement and the fact that PipeDec/SpecPipe's best numbers are at 8-14 stages both suggest a smaller upside than the headline numbers; this is an inference, not a measurement.
- Most of the heterogeneous gains come from putting the draft on the faster device and the verifier on the weaker, memory-richer one (Dovetail, DSSD). ShareCompute's laptop is not clearly "fast": it is a 4 GB machine whose free RAM bottomed at 89.2 MiB of 3,973 during the 3B run — [CLAUDE.md](../../CLAUDE.md).

### Gaps
- No source reports speculative decoding on phones as pipeline stages, on Wi-Fi, over a relayed star, or on x86+ARM mixes.
- PipeInfer's per-cluster tokens/s are only in figures; I could not extract them.

## 4. PipeInfer in detail: what it changes in llama.cpp, is the code usable against a 2026 llama.cpp, and what does it need from the RPC layer?

### Takeaway
PipeInfer is a fork of a 2024 llama.cpp that relies on a custom MPI backend (upstream removed MPI on 2024-05-20). The repo's main branch was last updated 8 Aug 2024 and I found no newer branch. Using it against a 2026 llama.cpp or ggml-rpc means re-implementing its ideas, not rebasing; the ideas (several runs in flight, micro-batched speculation, cancellation, KV multibuffering) all require things the synchronous, client-driven RPC protocol, as the project documents it, does not provide.

### Cited Findings
- Implementation base: reference implementation built on llama.cpp with MPI for inter-node communication; ggml not discussed — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Changes to llama.cpp: (1) asynchronous speculation, two loosely coupled pipelines for target and speculative model; (2) continuous speculation, generating speculation trees whenever the head node would be idle, in micro-batches of 1-4 tokens, with confidence-cutoff recovery and decay factors; (3) pipelined KV-cache multibuffering with sequence IDs allocated from a FIFO pool, sequence 0 as canonical; (4) early inference cancellation, a cancel signal carrying only a run identifier, back-propagated through the pipeline, non-speculative runs never truly cancelled; (5) transaction-based communication, each atomic operation with a start message and MPI tag for deterministic ordering. Verification uses SpecInfer's algorithm — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Messages crossing nodes: run configuration (batch size, sequences per token), activation tensors node to node, logits to the head node (which samples and verifies), KV-cache commands pipelined like activations, cancel signals; cancelled runs still send empty activation tensors to preserve ordering. The paper gives no tensor sizes ("relatively small") — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Placement: head node does sampling/verification and evaluates the first layers; the speculative model runs on a dedicated pipeline (one node dedicated to speculation in low-bandwidth tests) — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Hardware: CPU only; Cluster A 8 nodes 2x Xeon E5-2650 with 1 GbE; Cluster B up to 13 heterogeneous nodes with 8 GB DDR3 and 1 GbE; Cluster C up to 32 nodes with InfiniBand EDR; models 70B-180B quantised (Q2_K to Q3_K_M); 128-token prompts, 512 output tokens, greedy only, mean of 10 runs — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Ablations: removing KV multibuffering produced incoherent output; removing asynchronous speculation corrupted the KV cache, so neither ablation has performance numbers; hybrid tensor/pipeline parallelism and multi-GPU left to future work — [PipeInfer](https://arxiv.org/html/2407.11798v1).
- Repo: https://github.com/AutonomicPerfectionist/PipeInfer, MIT, 33 stars, 4 forks, 1 open issue, README says "Based on llama.cpp commit 9656026", requires MPI (`LLAMA_MPI=ON`, `mpicc`/`mpicxx`, `mpirun` or Slurm, SSH from the head node). The README mentions a separate branch porting to a newer llama.cpp, but the branches page lists only `main`, last updated 8 Aug 2024 — [repo](https://github.com/AutonomicPerfectionist/PipeInfer), [branches](https://github.com/AutonomicPerfectionist/PipeInfer/branches). The README does not mention RPC.
- Upstream llama.cpp removed the MPI backend ("llama : remove MPI backend (#7395)", 2024-05-20) — [commit page](https://app.semanticdiff.com/gh/ggml-org/llama.cpp/commit/d359f30921a9f62a0fd299c412ff3f270286fea6).
- RPC facts from the project's own evidence: layer split costs about one blocking exchange per link per token; a copy between two RPC servers goes get-to-host then set (`ggml_backend_rpc_buffer_cpy_tensor` returns false across servers), so in the star "a copy between two phones is phone, relay, probe, relay, phone"; the RPC backend exposes only `add_server` and `start_server` through `get_proc_address` — [findings.md F49](../../findings.md) (lines about 3569-3578).
- A failed endpoint is dead for the life of a llama.cpp process (restarted peer gets zero connections, 3/3) — [CLAUDE.md fact 11 and F35](../../CLAUDE.md).

### Inferences
- "Usable against 2026 llama.cpp" is no on the evidence: MPI backend gone upstream since May 2024, repo frozen August 2024, no newer branch found. I did not build it. A faithful port would touch the scheduler, KV cache and a transport, all of which have changed upstream since (that last clause is general knowledge, not sourced here).
- What PipeInfer asks of a transport, mapped to ggml-rpc as the project documents it (RPC source not re-read this session, no local copy of the tree): (a) several outstanding graph computes per endpoint with ordering guarantees (RPC is request/response, one blocking exchange per link per token); (b) a cancel message that interrupts a run without closing the connection (closing would trip the dead-endpoint latch above); (c) per-run KV sequence management on workers; (d) ideally direct stage-to-stage forwarding (star topology forces every inter-stage hop through the client and relay). All four are protocol or client-scheduler changes, not configuration.
- A pipeline-bubble approach still matches the shape of the problem: in a 3-stage, one-token-in-flight layer split each stage is busy about one third of the time. Whether the bubble is compute or network time is unmeasured (per-node compute time has never been measured in the project).

### Gaps
- The date of llama.cpp commit 9656026 was not established (my commit-page fetch failed with 404 on a guessed full hash).
- PipeInfer's per-configuration tokens/s and the Fig. 7c Gigabit results could not be read.
- I did not read ggml-rpc source this session; points (a)-(d) rest on the paper's message list plus the project's F35/F49 evidence.
- Whether the README's "newer llama.cpp" branch exists in a fork is UNVERIFIED.

## 5. Star-topology Wi-Fi failure mode: does batching N draft tokens make verification traffic erase the benefit?

### Takeaway
Activations are not the problem (about 8 KB per token per hop); logits are. If the verifier ships F32 logits for every position, an (N+1)-token verify moves (N+1) x 0.608 MB over the output-layer worker's link. With the phone-class link rate the project measured (about 6 MB/s) that is about 0.10 s per row, so it dilutes but does not by itself erase the gain at N=4; it does erase it at larger N or low acceptance, and tree verification multiplies it by node count. Computing argmax (greedy) or a truncated top-k on the last worker removes the problem; the edge-cloud literature does exactly this, and upstream llama.cpp has backend sampling, but its documented limits make it unverified for multi-position verification.

### Cited Findings
- Measured per-token traffic (layer split, 3B Q8_0, loopback counting proxy): client-to-worker 0.011/0.011/0.010 MB, worker-to-client 0.008/0.008/**0.608 MB** on links 1/2/3; 0.608 MB = 151,936 x 4 B, "the output layer sits on the last endpoint and returns F32 logits every token"; activation copies about 8 KB (2048 x 4 B, inferred from size) — [findings.md F49, lines about 3563-3574](../../findings.md).
- F49 states the ceiling for batched sequences is "the 608 KB of logits per sequence over the last worker's link" — [findings.md F49 item 4](../../findings.md).
- Physical decode: about 1.2-1.4 tok/s; the physical whole-loop figure quoted against the emulated link is 0.77 s per token — [CLAUDE.md](../../CLAUDE.md), [findings.md F49](../../findings.md).
- Measured link rates: about 6.1 MB/s to the iPhone and 6.2 MB/s to the Android phone during weight upload (laptop-to-phone direction); the relay-to-local-laptop-worker path measured about 27 MB/s (a relay/TLS throughput figure, not a Wi-Fi rate) — [findings.md F46-F48](../../findings.md) (lines about 3247 and 3408).
- Literature on the payload: naive exact protocols send |V| x b_prob bytes per draft token; systems avoid it with greedy verification (token IDs only), DSSD's rejection-only downlink, or TSLT's truncated candidate logits — [survey](https://arxiv.org/html/2606.25091). PicoSpec estimates about 500 KB per rejected token for a 128,256-entry vocabulary vs under 100 bytes with top-K=10 — [PicoSpec](https://arxiv.org/html/2603.19133). PipeInfer ships logits to the head node, which samples — [PipeInfer](https://arxiv.org/html/2407.11798v1). FlowSpec and AMUSD exchange tokens/trees, not distributions — [FlowSpec](https://arxiv.org/html/2507.02620v3), [AMUSD](https://arxiv.org/html/2410.17375v1).
- Upstream llama.cpp: PR #17004 "sampling : add support for backend sampling", merged 4 Jan 2026 by ggerganov (author danbev). When the whole sampler chain runs on the backend only the sampled token IDs are copied to host; greedy and dist samplers are supported. Documented limits at merge: "Only one output per sequence per batch is supported", not compatible with grammar sampling. Speculative decoding and RPC are not mentioned on the PR page text I read (first 100,000 of about 585,000 characters only) — [PR 17004](https://github.com/ggml-org/llama.cpp/pull/17004). The speculative docs list `--backend-sampling`, plus `--spec-draft-backend-sampling` for the draft side, and say tensor-split mode does not support backend sampling — [docs/speculative.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md).
- Parallel verification is not free on CPUs: Ghidorah found its 6-core ARM CPU efficient only up to about 16 verified tokens and chose width 16 — [Ghidorah](https://arxiv.org/html/2505.23219). The speculative docs default `--spec-draft-n-max` to 3 — [docs/speculative.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md).
- The Android worker is hard-coded to 2 compute threads and reports 3,472 MiB visible memory — [findings.md F49 item 5](../../findings.md).

### Inferences
Worked example (my arithmetic, not a measurement). Assumptions: one verify pass takes the same compute as one plain token (0.77 s whole loop, so no growth with batch size; unverified and probably optimistic on 2-thread phone CPUs), the draft is free or fully overlapped, independent per-token acceptance alpha, F32 logits for all N+1 rows on a link running at 6.0 MB/s. Expected tokens per round = (1 - alpha^(N+1)) / (1 - alpha). Extra logits time = N x 0.608 / 6.0 = N x 0.101 s.

| N draft tokens | alpha | tokens/round | round time, full logits | tok/s | vs 1.30 tok/s | round time, argmax on last worker | tok/s | vs 1.30 |
|---|---|---|---|---|---|---|---|---|
| 4 | 0.5 | 1.94 | 1.17 s | 1.65 | 1.27x | 0.77 s | 2.52 | 1.94x |
| 4 | 0.7 | 2.77 | 1.17 s | 2.36 | 1.82x | 0.77 s | 3.60 | 2.77x |
| 4 | 0.8 | 3.36 | 1.17 s | 2.86 | 2.20x | 0.77 s | 4.36 | 3.36x |
| 8 | 0.5 | 2.00 | 1.58 s | 1.26 | 0.97x | 0.77 s | 2.59 | 2.00x |
| 8 | 0.7 | 3.20 | 1.58 s | 2.02 | 1.56x | 0.77 s | 4.15 | 3.19x |

- So the user's worry is correct in direction and size for tree/large-N verification: logits traffic grows linearly with the number of verified positions (tree: with nodes, not depth), turns N=8 at alpha=0.5 into a net loss, and gives an interior optimum of N. It is not fatal at N around 3-4 with decent acceptance, and it vanishes if only IDs (greedy) or a few top-k values come back. At 27 MB/s (the relay-to-laptop-worker figure; the emulation's laptop-side rate was 216 Mbit/s) the same extra cost is about 0.023 s per row, negligible, so the question that decides this is which device holds the output layer, which I did not determine for the physical runs.
- Greedy verification is lossless and matches the project's existing "tokens equal the pinned reference" gate, which compares greedy output (inference from the gate's description in CLAUDE.md; sampling mode of the gate not re-checked). Stochastic verification needs the target's probabilities at the draft tokens: DSSD/PicoSpec-style sparse payloads reduce it but add protocol design.
- The activation side is benign: (N+1) x 8 KB is about 40 KB at N=4. Draft tokens and accepted ids are bytes. The star topology adds relay hops to each stage boundary but does not change the byte counts.
- Backend sampling is the obvious upstream route to "argmax on the last worker", but its documented single-output-per-sequence limit is the opposite of what verification needs (N+1 outputs for one sequence), and RPC compatibility is unstated; a small carried patch (argmax rows on the worker, return N+1 ints) is the fallback and fits the project's existing pattern of carried patches (budget, cache, parallel load). Whether the pinned revision still has that limit is UNVERIFIED.

### Gaps
- Uplink rate phone-to-relay (the direction logits travel) has not been measured; only the laptop-to-phone upload rate is known. Wi-Fi RTT never measured.
- Which device holds the output layer in the physical runs was not extracted.
- Whether compute per verify pass grows with N on the phones (2 threads, Q8_0 3B) is unmeasured; acceptance rates of any draft/target pair on the project's prompts are unmeasured.
- Backend sampling's current multi-output status and RPC behaviour: UNVERIFIED (read only the PR page's first portion).

## 6. Assessment of the four designs

### Takeaway
Ranked by fit: (1) draft on the laptop, verify on the ring, with greedy verification and logits reduced to ids, is the only design the literature, upstream llama.cpp and the project's constraints all support; (3) tree verification is a second-step refinement of (1) that raises logits traffic unless (1)'s payload fix exists; (4) PipeInfer-style asynchrony targets the real 3-stage idle time but needs RPC changes and its published gains are for deeper pipelines and faster links; (2) draft on a phone is the weakest on memory, latency and topology grounds.

### Cited Findings
(Findings that the assessment rests on are cited in Q1-Q5; the items below are the ones specific to this question.)
- Edge-cloud analysis: pipelined distributed speculation cannot beat co-located speculation when RTT >= gamma x t_d; the draft should sit next to the coordinator — [survey](https://arxiv.org/html/2606.25091).
- Upstream already lets a draft sit on an RPC device (`--spec-draft-device RPC0`) — [issue 23982](https://github.com/ggml-org/llama.cpp/issues/23982), and offers draft-free modes (n-gram types) and `--spec-draft-n-max` default 3 — [docs/speculative.md](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md).
- Laptop memory pressure: free RAM floor 89.2 MiB of 3,973 in the 3B runs; Android visible 3,472 MiB with 282-439 MiB available at the low point; 3B Q8_0 pooled 3,209.1 MiB against a 2,048 MiB largest budget; the repository's 0.5B test model is 469 MiB — [CLAUDE.md](../../CLAUDE.md), [findings.md F49 item 5 and the 0.5B note near line 2608](../../findings.md).
- A failed RPC endpoint is not re-attachable within a process — [CLAUDE.md fact 11](../../CLAUDE.md).

### Inferences
**(1) Draft on the laptop, verify on the ring: recommended first experiment.**
- Draft tokens never cross Wi-Fi; per verification round the new traffic is N+1 token ids down and N+1 logits-rows (or ids) back plus about 8 KB x (N+1) of activations per hop. This is the DSSD/PicoSpec/SpecEdge shape with the RTT between drafter and coordinator equal to zero.
- Cost drivers specific to this project: (a) the laptop has almost no spare RAM, so a model draft (a 0.5B Q8 is about 469 MiB here) is paid for by moving layers to the already-tight phones, whereas llama.cpp's draft-free `ngram-*` types need no memory or network but only help on repetitive text, and the recorded runs are 16 tokens of one prompt, too short to judge them; (b) the draft competes for the laptop's CPU with its own worker unless drafting is overlapped with the phones' stages, where the laptop (first in the pipeline, with phones downstream per F48) is otherwise idle; (c) the verify pass on 2-thread phone CPUs may stop being memory-bound at small N (Ghidorah's CPU saturated near width 16 on 6 cores; the phones have fewer threads), so the gain at N=4-8 must be measured, not assumed.
- Lossless with greedy verification; keeps the reference-token gate meaningful.
- Highest-leverage enabling work: return ids (or top-k) instead of F32 logits from the last worker (Q5 table). Without it, the model above suggests roughly 1.3x-2.2x at N=4; with it, about 1.9x-3.4x, under optimistic assumptions.

**(2) Draft on a phone.**
- Every draft token step would be a relayed Wi-Fi round trip (draft via an RPC device, as upstream's recipe does), so drafting N tokens costs N round trips of unmeasured RTT through TLS and the relay, against the survey's rule that remote drafting loses when RTT >= gamma x t_d. Phones are also the scarcest memory (Android 282-439 MiB available at low points). The only argument for it is making use of an idle phone core, which competes with that phone's own layer stage. Not recommended; DSSD/PicoSpec/SpecEdge put the draft on the *client-side* device that talks to the verifier, which here is the laptop.

**(3) Tree / batched verification.**
- SpecInfer/Staged SD/FlowSpec/PipeDec use trees to raise accepted length per pass; FlowSpec reports accepted length per SD round of 8.67 against 4.89 for Chunk-PP on LLaMA2-Chat 7B at T=0 ([FlowSpec](https://arxiv.org/html/2507.02620v3)). In llama.cpp it means a multi-sequence verify batch with a tree attention mask (upstream's `--spec-draft-p-split` suggests tree-style branching exists; I did not read the code).
- It multiplies the Q5 problem: logits rows scale with node count, and each additional row costs about 0.10 s at 6 MB/s if sent as F32, so a 16-node tree sent as full logits costs about 1.7 s of link time per round, more than two baseline tokens' worth of wall clock. It only pays with worker-side argmax/top-k, and then CPU compute growth with batch size becomes the limit. Treat as step two.

**(4) PipeInfer-style asynchronous speculation keeping all stages busy.**
- The concept fits: with one token in flight, each of 3 stages idles about two thirds of the time. But (i) PipeInfer reports marginal gains in shallow pipelines and its numbers are on CPU clusters with 1 GbE-InfiniBand and 70B-180B models, (ii) it needs several concurrent runs, cancellation without closing connections, and per-run KV handling, none of which RPC provides today, and the dead-endpoint latch rules out connection-drop cancellation, (iii) the code is a frozen 2024 MPI fork, (iv) the star topology serialises each inter-stage hop through the client, which reduces the overlap available.
- Cheaper approximations to try before any RPC change: overlap drafting with the phones' stages (AMUSD/PicoSpec/AceSpec idea: pre-draft the next tree while the current verification is in flight; drop it on rejection), which needs no protocol change because the draft is local to the laptop.
- First measurement needed regardless: per-node compute time per token versus network/relay time per hop on the physical devices. Without it, none of the pipeline-bubble gains can be sized.

### Gaps
- None of the four designs has been implemented or measured by me; all numbers in the Q5 table and this section are arithmetic on stated assumptions, not measurements.
- No acceptance-rate data for any draft/target pair on the project's model family (Qwen2.5 per CLAUDE.md; the 0.5B model's family not re-verified) was found.
- I did not test `--spec-draft-device RPC0`, backend sampling over RPC, or tree verification in the pinned build.
