## 1. Does upstream ggml-rpc support async operation and events, and does pipeline parallelism across RPC backends work? (items a, key Q1)

### Takeaway
Yes, since PR #18626 (merged 2026-08-26): one dispatcher thread per endpoint, async set/get/graph-compute, and event record/synchronize. It is in the pin, and F45/F48 `split.log` show "pipeline parallelism enabled", 4 splits, 4 scheduler copies on the physical devices. RPC still lacks `cpy_tensor_async` and a remote-completion event, so stage-to-stage copies go through the client host and block it.

### Cited Findings
- **PR #18626 "rpc : implement event and async backend APIs" (rgerganov): MERGED by ggerganov on 2026-08-26** (opened 2026-01-05). Stated intent: "The intent is to enable pipeline parallelism with the RPC backend." Adds `rpc_dispatcher` (one per endpoint, background network thread); event creation enqueues a dummy message and synchronize waits for the thread to process it; commands `FREE_BUFFER`, `BUFFER_CLEAR`, `INIT_TENSOR` stop sending responses. Open TODOs listed by the author: whether `event_synchronize()` and `event_wait()` are equivalent, **implement `cpy_tensor_async()`**, split the backend into client/server/common. ggerganov (Jan 10): since all traffic for an endpoint shares one socket, "event_wait() would have to be a noop". rgerganov at merge: "Let's merge and improve in follow ups." — [PR #18626](https://github.com/ggml-org/llama.cpp/pull/18626)
- **PR #24675 (sredman) "Implement events and async processing for RPC backend, enabling pipeline parallel input processing": CLOSED, not merged** (closed 2026-08-11 the same day sredman said he would review #18626, which implements the same design; the page gives no explicit reason). ### Inferences
- **[src-read] What overlaps today:** (i) the client can enqueue `SET_TENSOR`/`GRAPH_COMPUTE`/`GET_TENSOR` on each endpoint's dispatcher without blocking the caller; (ii) different endpoints' servers compute concurrently; (iii) with `n_copies=4`, the host can write inputs for the next ubatch while a worker is still on the previous one, safe only because the server is in-order. What does **not** overlap: any cross-stage hand-off (blocking get then set through the host), anything behind a response-bearing request (hash check, alloc-size cache miss, `GET_TENSOR`), and the server's own receive versus compute (one thread per connection).
- **[src-read] The host thread is on the critical path of every stage boundary** because the copy is a blocking `get_tensor`. A stage-k graph must finish before the host can even queue stage k+1. In a star topology (all links through the laptop) a direct worker-to-worker copy does not exist as an option anyway; #18626's `cpy_tensor_async` TODO would need worker-to-worker connectivity, which the TLS reverse-tunnel design does not provide.
- **Not a ShareCompute decision input right now:** since pipeline parallelism is already enabled at the pin with 4 copies, "turn on pipeline parallelism" or raise `GGML_SCHED_MAX_COPIES` is not an available lever; copies only matter if more ubatches than copies are in flight.
- Issue #28487 matters to this project (exactly 3 endpoints, async path on) but F49 ran 4 to 15 loopback endpoints without a hang, and #28487 has no root cause. Treat as an unconfirmed risk, not as an explanation for anything observed.

## 2. What gains have been reported from async/overlap work on RPC, and under what conditions? (key Q2)

### Takeaway
Reported gains are all prefill (pp), on GPUs or CPU workers on localhost or Ethernet, with 2 stages giving +30-70% and a third stage often making it worse. Token generation does not improve. No report found for Wi-Fi, phones, or an emulated-star topology.

### Cited Findings
- **#18626 benchmarks (4x A100 box, localhost RPC servers, 2026-08-25):** "Adding a second RPC server running on localhost gives us 30-70% PP improvement, depending on the model"; a third server "makes things worse, I guess due to the communication overhead"; Phi-4-mini pp4096 7557.80 t/s (1 server) to 9552.90 (2) to 5007.86 (4); Qwen3.5 27B Q8_0 pp4096 1173.31 to 1929.63 with two. A larger-batch test (`-b 8192 -ub 256 -p 8192`) was "not much difference". Another tester (sredman) reports **near-linear gains to four CPU RPC devices over Ethernet** and negative scaling beyond two GPUs on one host. — [PR #18626](https://github.com/ggml-org/llama.cpp/pull/18626)
- **#24675 benchmarks:** two 4-thread CPU workers, Phi-4-mini Q4_K_M pp4096: 59.84 +/- 0.74 t/s pipelined versus 37.96 +/- 0.14 t/s on one worker (1.58x), but a single 8-thread CPU process reached 89.69 +/- 1.17 t/s; two MI25 Vulkan workers 904.55 versus 527.89 t/s (1.71x; local two-device Vulkan 860.53); a "hybrid lab setup" (GLM 5.1, four CPU workers) from "about 5 to about 20 t/s" (metric not stated on the page). — [PR #24675](https://github.com/ggml-org/llama.cpp/pull/24675)
- **#6017 (CUDA, 8x A100 PCIe, CodeLlama-7B F16, `-b 8192`, `-ub 256`):** pp4096 6276.87 t/s (1 GPU) to 25504.36 (8 GPUs) = 4.1x [derived ratio]; **token generation 74.12 (1 GPU) versus 71.87 (8 GPUs): no speedup**. slaren: `-ub 256` usually better for F16, default 512 kept because it suits quantized models. — [PR #6017](https://github.com/ggml-org/llama.cpp/pull/6017)
- **Third-party loopback/10 GbE data point (unreviewed repo, date not shown):** Mac Studio M2 Ultra + DGX Spark over 10 GbE, Qwen2.5-7B Q4_K_M: pp 76.1 local to 317.7 with RPC (remote Blackwell tensor cores), tg 91.8 to 52.7; author attributes decode loss to a network round trip per token (~0.17 ms measured). Prefill gain here is faster remote compute, not overlap. — [kjaiswal/llama-cpp-distributed-benchmarks](https://github.com/kjaiswal/llama-cpp-distributed-benchmarks)
- **Latency-sensitivity evidence:** #12943 (above) gave 1.04x on LAN versus 1.24x on WiFi for TG by removing one blocking response; benefits scale with latency. — [PR #12943](https://github.com/ggml-org/llama.cpp/pull/12943)
- **Project's own prior art on the same machinery:** F27, local 217.3 t/s PP versus 112.5 t/s over loopback RPC (0.5B Q4_K_M, 4-core Xeon, no GPU), TG slightly higher under RPC for same-box scheduling reasons; second peer free. This predates #18626 being in the pin. — [findings.md F27](../../findings.md)

### Inferences
- The upstream wins come from **splitting compute that is large relative to the hand-off** (GPU prefill of thousands of tokens). The ShareCompute prompt is 5 tokens (`prompt_tokens: 5` in `physical-f48-spans/warm/report.json`), so there is nothing to pipeline.
- "Third server makes it worse" and #28487 both suggest the dispatcher/hand-off overhead grows with endpoint count; ShareCompute's 3-stage configuration sits right at that edge, but there is no measurement for it.

### Gaps
- No published numbers for Wi-Fi, ARM phones, or CPU-only stages with different speeds. No data on the time the star topology adds (every hand-off through the laptop).
- #24675's "hybrid lab" metric (pp or tg) unstated.

## 3. Micro-batching / ubatch and chunked prefill across RPC, and Wi-Fi star topology (item b, key Q3)

### Takeaway
`llama_decode` splits a long prompt into `n_ubatch`-sized micro-batches and the pinned scheduler can overlap them, but with RPC's blocking hand-offs the overlap is shallow (my reading: at best the **last** stage hides behind the earlier stages of the next chunk). It does nothing for the 5-token prompt in the physical runs. There is no measured data on chunk size for a Wi-Fi star; the cost model says link bandwidth is not what limits prefill, per-chunk round trips and stage compute are.

### Cited Findings
- `llama_decode` processes ubatches in a loop; `process_ubatch` builds/reuses a graph, calls `ggml_backend_sched_graph_compute_async`, then queues an async logits fetch; **there is no synchronization at the end of `llama_decode`** (the `synchronize()` is commented out: "wait for the computation to finish (automatically done when obtaining the model output)"). With pipeline parallelism, if a graph is reused, `ggml_backend_sched_synchronize` is called before the next ubatch's inputs are set. — [pin llama-context.cpp:1395-1417, 1458, 1887-1946, 2093-2094](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/src/llama-context.cpp)
- With `n_batch=256, n_ubatch=64` the probe splits any prompt over 64 tokens into several ubatches; the physical test prompt is 5 tokens, hence one ubatch. Recorded `prefill_ms`: 28,946 ms (F48 warm), 14,013 (F45 warm), 15,301 (F45 cold); decode 11,459 / 12,994 / 12,230 ms for 16 tokens. — [probe.cpp:70](../../native/split/probe.cpp), [F48 report.json](../../docs/evidence/physical-f48-spans/warm/report.json), [F45 warm](../../docs/evidence/physical-f45-logging/warm/report.json), [F45 cold](../../docs/evidence/physical-f45-logging/cold/report.json)
- Measured per-token and per-hop volumes on the project's layer split (3B Q8_0, loopback): activations about 8 KB per token per hop (2048 x 4 B, F32, inferred from size); roughly 1 blocking exchange per link per token; logits 0.608 MB per token on the last link. — [findings.md F49 section 3](../../findings.md)
- Upstream evidence on ubatch: `-ub 256` best for F16 and 512 default for quantized on A100s (#6017); a pp8192 run with `-ub 256` showed "not much difference" versus default in an RPC test (#18626). Both GPU, no Wi-Fi. — [PR #6017](https://github.com/ggml-org/llama.cpp/pull/6017), [PR #18626](https://github.com/ggml-org/llama.cpp/pull/18626)
- Compute buffers at `n_ubatch=64` in the physical run: laptop 11.82 MiB, Android 11.82 MiB, iPhone 39.85 MiB, CPU 1.26 MiB; reserve took 313 ms. — [F48 split.log:2513-2518](../../docs/evidence/physical-f48-spans/warm/split.log)

### Inferences
- **[derived from src-read] Pipelined prefill speedup with the pinned host-blocking hand-off.** Ideal balanced pipeline with S stages and M chunks gives S*M/(S+M-1) (S=3: 1.5x at M=2, 2.0x at M=4, 2.4x at M=8). Because the host blocks on a `get_tensor` of stage k before queueing stage k+1, only the last stage is hidden; total ~ M*(S-1)*t + t versus M*S*t, i.e. 1.33x at M=4, 1.41x at M=8, limit 1.5x for S=3, and only if stage times are balanced (here layers are 7/17/12 on very different devices, so less). This matches the upstream shape (2 stages: +30-70%). Not measured on this project.
- **Link bandwidth is probably not the prefill limiter:** 8 KiB per token per leg means a 64-token chunk moves 512 KiB per leg; at the phones' observed 5.7-6.2 MB/s store rate (a receive+cache-write rate, F48 caveat, not a clean network rate) that is about 0.09 s per leg per chunk. A phone running 1.3 GB of weights on 2 threads almost certainly needs longer than that per chunk (not measured). Larger `n_ubatch` therefore buys fewer round trips and less per-chunk dispatch cost but shallower pipelines and bigger compute buffers (the 4 GB laptop already bottomed at 89.2 MiB free, F45). Smaller chunks add pipeline depth but pay a fixed per-chunk, per-link blocking round trip.
- **Prompt-length caveat for any recommendation:** all physical evidence is a 5-token prompt. If the real use is long prompts (hundreds of tokens), prefill becomes the dominant interactive latency and chunk pipelining becomes relevant; for short prompts it is irrelevant.
- `prefill_ms` in the probe stops when `llama_decode` returns, and sampling (which forces synchronization) happens afterwards, so the **last stage's compute and the logits fetch are counted in `decode_ms`, not `prefill_ms`** [src-read, derived]. The effect is at most one stage's share of a single pass, small relative to 29 s, but it means "prefill" and "decode" in F45/F48 are not cleanly separated.

### Gaps
- No measurement anywhere of: ubatch size versus time on this star, Wi-Fi RTT (F49: never measured), per-stage compute time, or whether graph reuse (`RECOMPUTE`) applies across equal-sized chunks here.
- Whether upstream pipelining of multiple ubatches actually reached more than 2-way overlap over RPC: no source found.

## 4. Why single-sequence decode cannot overlap stages, and the per-token lower bound (item c, key Q4)

### Takeaway
Autoregressive dependency means exactly one stage works at any instant (utilisation 1/S). Pipeline parallelism does not speed up generation even on 8 GPUs. Per-token time is at least the sum of stage compute plus per-link round trips and logits transfer; on this evidence compute dominates, and the only structural way to fill the pipe for one user is speculative decoding (or more sequences, which does not shorten one answer).

### Cited Findings
- #6017's own benchmark: 8 GPUs gave no token-generation gain (74.12 t/s on 1 GPU versus 71.87 on 8); the pipeline helps batch/prompt processing. — [PR #6017](https://github.com/ggml-org/llama.cpp/pull/6017)
- PipeInfer's thesis: speculative techniques "reduce memory-bandwidth bottlenecks but increase per-run latency"; it proposes Continuous Asynchronous Speculation (single-token runs alongside several speculative runs) and Early Inference Cancellation, "up to 2.15x improvement in generation speed **over standard speculative inference**", aimed at single-request latency and low-bandwidth interconnects. It is a modification of llama.cpp at an old commit (9656026), over **MPI** (`ggml-mpi`), not ggml-rpc; a port to current llama.cpp is on a separate branch. — [arXiv 2407.11798](https://arxiv.org/abs/2407.11798), [PipeInfer repo](https://github.com/AutonomicPerfectionist/PipeInfer)
- prima.cpp (llama.cpp-based home-cluster system): "pipelined-ring parallelism" described as overlapping disk I/O with compute and communication; Halda scheduler; reported "674 ms/token TPOT" for 70B on four home devices and "5-17 times lower TPOT" than llama.cpp, exo, dllama. Speculative decoding with a 5-token draft said to give a further 25-45% latency reduction across 14-70B (**secondhand**: from a search-engine summary of the paper; the PDF text could not be extracted here). — [arXiv 2504.08791](https://arxiv.org/abs/2504.08791)
- Layer split costs about 1 blocking exchange per link per token and moves 0.608 MB of logits per token on the last link; tensor split needs about 145 per link and was 2.1-2.8x slower on loopback. — [findings.md F49](../../findings.md)
- Measured token time: 0.77 s per decode step across the three physical devices (16 calls in 11.5 s; `decode_ms` 11,459 over 15 `llama_decode` calls = 0.76 s). On loopback (no network, 4-core Xeon) the same 3B layer split took 0.50 s per token (F49; single run). — [F48](../../findings.md), [F49](../../findings.md)
- Batched/multi-sequence: a scratch batched probe on an emulated Wi-Fi link gave 0.95, 2.3, 2.4 tok/s aggregate at 1, 8, 32 sequences; ceiling is the 608 KB logits per sequence (F49 section 4, **[worker]-measured, not re-run**). — [findings.md F49](../../findings.md)
- Remote-draft speculative decoding is not built into llama.cpp's own tooling as far as I found: a feature request says `--spec-draft-model` needs a local draft file (**secondhand**, from a search snippet of issue #23982, not opened); ik_llama.cpp maintainers said network speculative decoding is not supported (discussion #839, search snippet). — [issue #23982](https://github.com/ggml-org/llama.cpp/issues/23982), [ik_llama.cpp discussion #839](https://github.com/ikawrakow/ik_llama.cpp/discussions/839)
- libllama exposes an **experimental backend sampling API** at the pin (`llama_context_params.samplers`, sampled-token getters, `needs_raw_logits` skips the logits copy when all sequences use backend sampling) — [pin llama.h:417-420, 1167-1189](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/include/llama.h), [pin llama-context.cpp:1692-1706, 1934](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/src/llama-context.cpp). The RPC device's `supports_op` returns `true` unconditionally (TODO to query the remote), so op support is decided on the worker at run time — [pin ggml-rpc.cpp:2216-2221](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/ggml-rpc.cpp)

### Inferences
- **Lower bound [derived].** T_token >= sum over stages c_s(1 token) + sum over links (RTT_l + bytes_l/BW_l) + host overhead, with one blocking exchange per link per token (F49), plus the final logits fetch: 0.608 MB on the iPhone link. Using the 5.7 MB/s phone store rate as a stand-in for that link (it is a *download* rate with cache writes; the upload rate is unmeasured) gives about 0.11 s, 14% of 0.77 s: **a rough upper bound on one component, not a measurement**. RTT terms: three links times a Wi-Fi RTT that this project has never measured (F49). Typical Wi-Fi RTT of a few ms would put the RTT term near 10-30 ms of 770 ms, but that figure is **UNVERIFIED** (no source).
- **Compute dominates, on weak evidence.** Loopback layer decode was 0.50 s per token with no network, against 0.77 s physical, so everything that is network, phone-versus-Xeon speed and relay overhead together is at most about 0.27 s (35%) of the physical token time. This is two different machines and single runs, so it is a ceiling on "overlappable" time, not a decomposition. Overlap work can only hide transfers, so its ceiling on decode is bounded by that remainder and is likely much smaller.
- **Speculative verification looks cheap on CPU [derived from F27]:** local 0.5B Q4_K_M ran 217.3 t/s prompt processing versus 24.9 t/s generation, i.e. about 40 ms for the first token of a pass and about 4.6 ms for each extra batched token; verifying 5 tokens would cost roughly 1.45x a single-token pass. For a memory-bound 3B Q8_0 ring this suggests a verify pass for k drafts costs well under k single passes, but the 3B/ARM/phone ratios are **not measured**, and the acceptance rate for any draft/target pair here is **unknown**.
- **Practical costs of speculative decoding in this project:** needs a draft model on the laptop (F45 shows the 4 GB laptop already hit an 89.2 MiB free-RAM floor), turns every decode step into an n_tokens>1 batch (new graph shapes, no `RECOMPUTE` reuse unless the batch size is constant), and the draft/verify loop must live in `probe.cpp` since stock tooling expects a local target. PipeInfer-style asynchronous speculation is a research-prototype port effort (MPI, old llama.cpp).
- **Backend sampling is a possible way to delete the 0.608 MB logits transfer** (greedy argmax on the last worker), but whether the RPC path supports the needed sampler ops, and whether it is correct with the project's patches, is **UNVERIFIED**; it is source-read at the API level only.

### Gaps
- Per-stage compute time on each device and Wi-Fi RTT remain unmeasured (F49 says the same), so the compute-versus-network split of the 0.77 s is open.
- Speculative acceptance rate for Qwen2.5-0.5B (or any draft) against Qwen2.5-3B Q8_0 on this prompt: not found, not measured.
- prima.cpp's speculative numbers not verified from the paper text.

## 5. "Prefill on the strong device, decode on the ring": possible? What moves? Prior art? (item d, key Q5)

### Takeaway
Technically the KV state is serializable, but there is no "strong device": no single worker can hold the 3B Q8_0 model (largest budget 2,048 MiB versus 3,209 MiB pooled). Moving KV is cheap for short prompts (36 KiB per token) and slow at Wi-Fi speeds for long ones. Disaggregated prefill/decode (Splitwise, DistServe, Mooncake) is datacenter work on fast interconnects; the closest edge-scale prior art found (P/D-Device) is cloud-to-device, not device-to-device.

### Cited Findings
- KV lives with each layer's owner: physical log shows `llama_kv_cache: RPC0[...:55700] 3.50 MiB`, `[...:55714] 6.00 MiB`, `[...:55721] 8.50 MiB` at `n_ctx=512` (7, 12 and 17 layers), model dims `n_layer=36, n_head=16, n_head_kv=2, n_embd_head=128`. — [F48 split.log:74-86, 1207-1209](../../docs/evidence/physical-f48-spans/warm/split.log)
- libllama can serialize and restore one sequence's state: `llama_state_seq_get_size/get_data/set_data` plus `_ext` variants with `LLAMA_STATE_SEQ_FLAGS_*` (partial, SWA-only, on-device). — [pin llama.h:882-945](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/include/llama.h)
- Budgets and capacity: pooled 3,209.1 MiB against a 2,048 MiB largest budget; laptop budget 768 MiB; Android reports 3,472 MiB visible RAM. — [CLAUDE.md](../../CLAUDE.md), [F45](../../findings.md), [F49 section 5](../../findings.md)
- Observed phone store rates 5.70 MB/s (iPhone) and 6.18 MB/s (Android) cold, receive plus cache write, not clean network throughput; laptop checksum read 134 MiB/s. — [F46/F48](../../findings.md)
- **Splitwise** (Patel et al., arXiv 2311.18677): runs prompt and token phases on separate machines; state transfer over fast cluster back-plane interconnects; about 1.4x throughput at 20% lower cost or 2.35x throughput at equal cost/power. — [arXiv 2311.18677](https://arxiv.org/abs/2311.18677)
- **DistServe** (Zhong et al., OSDI 2024, arXiv 2401.09670): separate GPUs for prefill and decode, bandwidth-aware placement "to minimize the communication caused by disaggregation"; "7.4x more requests or 12.6x tighter SLO". — [arXiv 2401.09670](https://arxiv.org/abs/2401.09670)
- **Mooncake** (arXiv 2407.00079, v5 revised 2026-10-08): KVCache-centric disaggregated architecture behind Kimi, pooling CPU/DRAM/SSD across GPU servers; up to 525% throughput in simulated scenarios, 75% more requests under real workloads. — [arXiv 2407.00079](https://arxiv.org/abs/2407.00079)
- **P/D-Device** (arXiv 2508.09035, Aug 2025): cloud does part of the prefill for each device and streams the first tokens; device shows the first token immediately; TTFT down at least 60%, cloud throughput up to 15x (abstract-level; what is transferred, KV versus hidden states, not determinable from the abstract page). — [arXiv 2508.09035](https://arxiv.org/abs/2508.09035)
- Serving-framework docs state the economics: disaggregation only helps when decode workers can reach the prefill's KV quickly; NIXL supports TCP but high-bandwidth fabrics (IB/RoCE/EFA) are "highly recommended". (From search snippets, not opened.) — [NVIDIA Dynamo docs](https://docs.nvidia.com/dynamo/v1.2.0/user-guides/disaggregated-serving), [llm-d guide](https://llm-d.ai/docs/guides/pd-disaggregation)

### Inferences
- **What would move [derived]:** KV per token = 2 (K,V) x 256 (n_embd_k_gqa) x 2 B (f16) = 1,024 B per layer, 36 KiB across 36 layers; this reproduces the logged 18.0 MiB total at 512 tokens (3.5 + 6.0 + 8.5). So 5 tokens = 180 KiB, 512 = 18 MiB, 2,048 = 72 MiB, 4,096 = 144 MiB. At about 6 MB/s that is roughly 3 s, 13 s and 26 s respectively [derived, using a store rate as a proxy]. Short prompts are cheap to transfer; the 5-token case moves 180 KiB.
- **But it requires a device that can run the whole model for prefill.** None of the three can: the laptop has a 768 MiB budget. The only variant that fits is a "strong helper" outside the current set, or layer streaming from disk (prima.cpp-style): reading the 3.6 GB model at the 134 MiB/s checksum rate is about 27 s per pass [derived], comparable to the unexplained 29 s prefill, so not an obvious win either.
- Within the existing split, "prefill elsewhere" has no meaning: each worker must hold KV for the layers it owns, and moving KV to a different layer owner means re-placing layers (a reload of the 98 s kind, F48).
- All prior art found is datacenter GPU-to-GPU (RDMA/NVLink-class) or cloud-to-device; I found **no edge-scale (phone + laptop over Wi-Fi) disaggregated prefill/decode system**. P/D-Device is the nearest and uses a cloud tier ShareCompute does not have.

### Gaps
- P/D-Device transfer mechanism and bandwidth assumptions not read (abstract page only).
- Splitwise/DistServe/Mooncake KV-transfer sizes and rates are in the full papers; not read.
- Whether any of the operator's devices could host a full 3B Q4 prefill (the Q4 file fits the Android budget alone, F40) was not evaluated; that would be a different model/quantization than the pinned reference.

## 6. What dominates the 29 s prefill in F48, and what upstream says about RPC overhead during prefill (item e, key Q6)

### Takeaway
Not established, and not an overlap problem: it is a 5-token, single-ubatch pass, there is nothing to micro-batch, pipeline parallelism was already on, and the same code took 11-15 s on four other runs. Upstream has no model of RPC prefill overhead over Wi-Fi; the nearest documented mechanisms are blocking alloc-size queries behind in-flight compute and per-token blocking responses, both of which are already mitigated in the pin or are one-time.

### Cited Findings
- F48: warm `split_generation` 139,985 ms; loading ended at 98.3 s; laptop worker's first graph **finished** about 127.5 s in (29 s after the last weight); `graph_calls` counts completions so "zero" does not prove idle; phones are downstream of the laptop; steady-state decode 0.77 s per step; at that rate a 5-token prefill would be about 4 s, so at least 25 s of 28.9 s is above steady state; waiting versus computing "is not established". Leading candidate in F48: paging on the 4 GB laptop (minimum free RAM 197 MiB, 89.2 MiB in F45), untested. — [findings.md F48](../../findings.md)
- Prefill durations for the same 5-token prompt: 12.4 s and 11.3 s (F43), 14.0 s warm and 15.3 s cold (F45), 28.9 s warm (F48). — [findings.md F43/F45/F48](../../findings.md), [F48 report.json](../../docs/evidence/physical-f48-spans/warm/report.json)
- `GET_ALLOC_SIZE` is a **blocking request with a response**, issued only for quantized tensors with `ne[0] % 512 != 0` or ops that "may expand" (`ggml_op_alloc_size_may_expand`), cached per (device, type, op, params, ne, nb, endpoint); the source comment says cache misses "block the main thread behind in-flight GRAPH_COMPUTE commands". A new graph shape (5-token prefill, then 1-token decode, versus the 64-token reserve) is a set of new keys. — [pin ggml-rpc.cpp:847-920](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/ggml-rpc.cpp); rgerganov on #24675 that waiting on these "was killing pipeline overlap". — [PR #24675](https://github.com/ggml-org/llama.cpp/pull/24675)
- A new graph topology is serialized in full to each worker (`GRAPH_COMPUTE`), while repeated graphs send only `GRAPH_RECOMPUTE`; this graph had 1,230 nodes. — [pin ggml-rpc.cpp:1038-1057](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/ggml-rpc.cpp), [F48 split.log:2517](../../docs/evidence/physical-f48-spans/warm/split.log)
- Upstream's published guidance on RPC overhead: #12943 (per-token SET_TENSOR response removal, benefit scales with latency, 1.24x TG on WiFi); the RPC README is described in secondary sources as a proof-of-concept designed to pool memory rather than speed up compute (F32 quotes `tools/rpc/README.md`). — [PR #12943](https://github.com/ggml-org/llama.cpp/pull/12943), [Discoverer HPC blog](https://hpcwithus.discoverer.bg/?p=439) (secondary)

### Inferences
- **What the 29 s is not [src-read + data]:** not missing micro-batch pipelining (one 5-token ubatch); not absence of async/events (enabled); not weight transfer (loading ended 29 s earlier; the loader is a separate phase); not the logits fetch (one token's worth, small).
- **Candidates, ranked only by what the source supports; none tested:** (1) the laptop worker's first graph running slowly or late (paging under the 89-197 MiB free floor, or the thread-pool/first-touch cost on a freshly loaded buffer) because the host blocks on the laptop's output first; (2) blocking `GET_ALLOC_SIZE` misses on the first graph of each new shape, each a Wi-Fi/relay round trip per endpoint, possibly queued behind compute; (3) the probe not yet sending (host-side work between load end and first graph, for example the sched reserve and graph build; reserve itself reported 313 ms); (4) first-run costs on the phones (not visible since the phones' counters read 0 until the first graph completes). The run-to-run spread (11-29 s for the same prompt) points to an environmental, not structural, component, which favors (1).
- **Cheap discriminators that need no upstream change [proposed, not run]:** timestamp graph start and end on the workers (F48's own recommendation); log time-in-`llama_decode` split by `process_ubatch` calls and by blocking calls (set/get/alloc-size) in the probe; run one throwaway warm-up `llama_decode` of the same shape before the timed prefill (also tells whether the excess is one-time); record laptop free RAM and page-fault counters across the prefill.
- `prefill_ms` excludes the last stage's tail (section 3), so the reported 28.9 s slightly under-counts the iPhone's contribution; it cannot explain 25 s.

### Gaps
- No upstream document or issue found that models RPC prefill overhead for Wi-Fi/phone-class links; searches ("llama.cpp RPC prompt processing slow network ubatch graph split tensor copies") returned benchmarks and user reports only.
- No instrumentation separates waiting from computing in F48's prefill. Wi-Fi RTT, per-stage compute, count of `GET_ALLOC_SIZE` misses, and laptop page-fault behaviour are all unmeasured.

## 7. Verdict for ShareCompute (single user): realistic gain from overlap work versus effort

### Takeaway
Overlap work has close to zero payoff for the target workload: one user, one sequence, short prompt. The pin already has everything upstream built for overlap, and the structure of autoregressive decode forbids stage overlap. Spend effort first on measuring the prefill delay; then, if decode speed is the goal, on speculative decoding in `probe.cpp`, which is the only lever that changes per-token economics for one sequence.

### Cited Findings
- (See sections 1-6; no new sources.) Key anchors: pipeline parallelism already enabled (F45/F48 `split.log`), 5-token prompt (`report.json`), no token-generation gain from pipelining even on 8 GPUs ([#6017](https://github.com/ggml-org/llama.cpp/pull/6017)), upstream prefill gains +30-70% for two stages on GPUs/CPU workers ([#18626](https://github.com/ggml-org/llama.cpp/pull/18626), [#24675](https://github.com/ggml-org/llama.cpp/pull/24675)), PipeInfer 2.15x over standard speculative inference on MPI ([arXiv 2407.11798](https://arxiv.org/abs/2407.11798)).

### Inferences
| Lever | Realistic gain here | Effort | Confidence / caveat |
|---|---|---|---|
| Turn on pipeline parallelism / raise copies | none (already on, 4 copies) | none | verified in logs |
| Decode stage overlap (single sequence) | 0 (structural) | n/a | #6017 TG result |
| Chunked-prefill pipelining, long prompts | about 1.3-1.4x on prefill only, from a derived model of the host-blocking hand-off; 0 for 5 tokens | none to enable (already in), high to improve (`cpy_tensor_async` needs worker-to-worker links, not available in the star) | derived, unmeasured; bigger if prompts are long |
| Larger or smaller `n_ubatch` | unknown; tradeoff is per-chunk round trips versus pipeline depth and compute-buffer memory | trivial to try | no Wi-Fi data; laptop memory floor argues against going up |
| Disaggregated "prefill on strong device" | not possible with these devices (no device holds the model); KV 36 KiB/token if it were | very high | prior art is datacenter only |
| Find and fix the 29 s prefill | potentially the largest single saving on a short-prompt run (up to about 25 s of 140 s warm, F48) | low to instrument, unknown to fix | cause unknown; may be paging; run-to-run 11-29 s |
| Speculative decoding in `probe.cpp` (local draft on laptop, verify on ring) | plausibly the only per-token gain for one sequence; magnitude depends on acceptance (unmeasured); prima.cpp claims 25-45% extra (secondhand) | medium; laptop RAM is tight | acceptance and 3B verify cost on phones unmeasured |
| Backend sampling to avoid 608 KB logits/token | up to roughly 0.1 s of 0.77 s if the logits link is slow (derived from a proxy rate) | low to try if supported | UNVERIFIED over RPC |

- Caveats to carry into any report: single prompt, 16 tokens, one Wi-Fi network; every overlap estimate above is derived from source reading, not execution; F49's emulated-link and batched numbers are worker-measured and not re-run; issue #28487 (open) is a standing risk for 3 endpoints on the async path.

### Gaps
- No overlap-specific experiment has been run on this project's hardware or even on loopback with a latency-injecting proxy; the cheapest informative one would be a loopback run with a latency/bandwidth shaper on the phone links, long (hundreds of tokens) prompt, `n_ubatch` in {32, 64, 128, 256}, with `SC_PARALLEL_LOAD` unchanged, comparing prefill time and counting blocking requests per ubatch. Not run.
