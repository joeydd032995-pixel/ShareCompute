## 1. What existing systems report (model/hardware scale, partition strategy, placement algorithm, tokens/s, dynamic re-balancing)

### Takeaway
Almost every home/edge system partitions by contiguous layer ranges (pipeline/ring) or by tensor-parallel slices; only prima.cpp (disk-offload aware, profiled, ILP) and LinguaLinked/Petals/Parallax (runtime balancers) go beyond memory-proportional splitting, and none of the *edge* systems re-plans live without either replicated weights on every device (prima.cpp mmap, LinguaLinked replicas) or a restart of the stage. No system reports a measured crossover or live re-plan on a 4 GB laptop + two phones over Wi-Fi like ShareCompute's.

### Cited Findings

**prima.cpp (Li, Li, Feng, Guizani, Yu; arXiv 2504.08791; v1 "PRIMA.CPP: Speeding Up 70B-Scale LLM Inference on Low-Resource Everyday Home Clusters", Apr 2025; v2 / ICLR 2026 "Prima.cpp: Fast 30-70B LLM Inference on Heterogeneous and Low-Resource Home Clusters")**
- Partition strategy: pipelined-ring parallelism over llama.cpp; weights are mmap'd and prefetched so disk loading overlaps compute; each device holds a "window" of layers and a token can circulate the ring k times when windows are smaller than the model. Split between CPU and GPU within a device is part of the plan. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2); [search summary of v1/v2 abstracts](https://arxiv.org/html/2504.08791v1)
- Testbed (Table 3 of v2): D1 Mac M1 (2.4 GiB avail. RAM), D2 Linux laptop i9 + RTX 3070 (4.1 GiB RAM, 8 GiB VRAM), D3 Linux desktop i9 + 2080Ti (9.7 GiB RAM, 11 GiB VRAM), D4 Huawei Mate40Pro (HarmonyOS, Termux, 1.9 GiB), D5 Honor Pad (Android, 5.1 GiB), D6 Mac Air Intel (6.8 GiB). Default cluster D1-D4, 37 GiB aggregate. Links: local Wi-Fi router, **320-610 Mbps, 3-7 ms latency**. exo ran on D1-D3 only because D4 needs root. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- Results, TPOT = ms per output token (Table 4; llama.cpp / exo / dllama / prima.cpp): 8B 15 / 263 / 459 / 15; 14B 20 / - / - / 20; 30B 202 / - / - / 72; 45B 328 / - / - / 233; 60B 7,965 / - / - / 468; 65B 8,807 / - / - / 569; **70B 10,120 / OOM / OOM / 674** (about 1.5 tok/s). Headline "5-17x lower TPOT". These are the authors' own measurements on their own cluster against baselines they ran. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- Ablations (same table): without Halda, 70B is 20,848 ms and 8B 78 ms; without prefetching, 70B is 755 ms. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- Speculative decoding (Appendix A.9, Table 10): Llama 3.3-70B 803 -> 442 ms/token (3B draft on GPU); Qwen-2.5-32B 55 -> 38 ms; DeepSeek-R1-Distill-Llama-70B 859 -> 593 ms; "additional 25-45% latency reduction across 14-70B models". — [arXiv v2 HTML, appendix](https://arxiv.org/html/2504.08791v2)
- Device-count scaling (A.7): 3 devices (38 GiB aggregate, below the 40 GiB the Q4K 70B needs) still gave the lowest latency; adding a 4th "reduced TPOT by roughly half"; **6 devices gave higher TPOT** because D4 and D6 have weak CPUs and slow disks; Halda drops devices that would hold only one layer, and keeps a would-be-ring-breaking device as a no-work relay. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- Dynamic re-balancing: the paper says Halda's rerun cost is negligible (scheduling takes 10-12 ms for 4-32 devices) and workloads "can be repartitioned whenever the task queue is empty to adapt to environmental changes". This is stated as a possibility; **no live monitoring loop is described**. Re-partitioning is cheap in prima.cpp specifically because every device has the full model file on disk and mmaps what it needs. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)

Going 4 -> 8 devices made 7B and 13B **slower** because transfer grew faster than compute shrank. — [fork README mirror](https://github.com/Dyl777/distributed-llama/blob/main/README.md)
- On prima.cpp's Wi-Fi cluster dllama measured 459 ms/token on 8B and OOM on 70B (see above). — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)

**exo (exo-explore/exo)**
- Current README: automatic device discovery; "topology-aware auto parallel" that picks a split from real-time device resources and **latency and bandwidth on each link**; tensor parallelism with claimed "up to 1.8x speedup on 2 devices and 3.2x on 4"; day-0 RDMA over Thunderbolt 5 ("99% reduction in latency between devices"); MLX backend, Apple GPUs on macOS (needs macOS Tahoe 26.2+), Linux is CPU-only; a `/instance/previews` endpoint lists valid placements and the user picks. Benchmarks in the README are images only (Qwen3-235B, DeepSeek v3.1 671B, Kimi K2 on 4 x M3 Ultra Mac Studio), no numbers readable. Instances are created and deleted manually; **no automatic rebalancing is described**. — [exo README](https://raw.githubusercontent.com/exo-explore/exo/main/README.md)
- The older "ring memory-weighted partitioning" default (each device runs layers in proportion to its memory) is my recollection of exo's earlier README; the current README does not describe it. UNVERIFIED.

**Petals (Borzunov, Ryabinin, Chumachenko, Baranchuk, Dettmers, Belkada, Samygin, Raffel; NeurIPS 2023; arXiv 2312.08361 "Distributed Inference and Fine-tuning of Large Language Models Over The Internet")**
- Scale: Llama 2 70B and BLOOM 176B over the public internet; README also lists Llama 3.1 up to 405B, Mixtral 8x22B, Falcon 40B+. README claims single-batch up to 6 tok/s (Llama 2 70B) and 4 tok/s (Falcon 180B). — [Petals README](https://raw.githubusercontent.com/bigscience-workshop/petals/main/README.md); [paper](https://arxiv.org/abs/2312.08361)
- Measured steps/s, batch 1 (paper): Llama 2 70B on 3 x T4: 2.29 (128 tok) at 1 Gbit/s <5 ms; 2.29 at 100 Mbit/s <5 ms; **1.57 at 100 Mbit/s with 100 ms latency**; offloading 0.139. BLOOM 176B real-world (14 servers, two continents) 0.83 steps/s. — [paper HTML](https://arxiv.org/html/2312.08361)
- Placement: a joining server picks the contiguous block segment with the lexicographically smallest throughput vector (fills the narrowest bottleneck); greedy reaches ~90-100% of optimal in their simulations. **Dynamic**: servers re-check periodically (simulated every minute) and move only if estimated swarm throughput improves by at least **p = 20%**, because lower thresholds caused too many block changes, each of which resets attention caches. Clients route with D* Lite over per-server compute time x blocks plus pinged latency. Fault tolerance: client keeps the inputs it sent to each stage and **replays them** to a replacement server to rebuild its attention cache (O(t) data). Hidden states are int8-block-quantised on the wire; per-token transfer is a few kilobytes. — [paper HTML](https://arxiv.org/html/2312.08361)

**EdgeShard (Zhang, Cao, Shen, Cui; arXiv 2405.14371, 2024, under review)**
- Testbed: 15 devices (12 Jetson AGX Orin 32 GB, 2 Jetson Orin NX 16 GB, 1 RTX 3090 server), 1000 Mbps switch with Linux `tc` shaping, edge links 50 Mbps +/-20%, source-to-cloud 1 Mbps (one section says 11 Mbps; the page is internally inconsistent). Llama2 7B/13B/70B, full precision. — [HTML](https://arxiv.org/html/2405.14371)
- Placement: two dynamic programs. **Latency DP is a sum**: DP(i,j) = min_k [DP(i-1,k) + t_comp(i,j) + t_comm(i-1,k,j)], O(N M^2). **Throughput DP minimises the slowest stage**, O(N^2 2^M M^2), with memory constraints, plus a "no-bubble" micro-batch schedule. — [HTML](https://arxiv.org/html/2405.14371)
- Results (ms/token latency; tok/s throughput): Llama2-7B Edge-Solo 140.34 / 24.36 vs EdgeShard **75.88** / 52.45; 13B Cloud-Edge-Opt 243.45 vs EdgeShard 173.43; **70B EdgeShard 3,086.43 ms/token latency, 1.25 tok/s throughput** (others OOM). Above ~10 Mbps collaboration beats Edge-Solo; at 1 Mbps the optimiser collapses to local execution. Profiling is an offline one-off; **no runtime re-partitioning**. — [HTML](https://arxiv.org/html/2405.14371)

**EdgePipe / PipeEdge (Hu, Imes, Zhao, Kundu, Beerel, Crago, Walters; arXiv 2110.14895, 2021, "Pipeline Parallelism for Inference on Heterogeneous Edge Computing"; the v1 text names the system EdgePipe, the name PipeEdge is not on the page)**
- DP over layers, used devices and last device with device-category grouping (category-DP 0.01 s vs 18.6 s naive vs 71 min brute force on ViT-Base). **Objective: minimise the bottleneck (slowest stage)** for throughput; assumes async communication fully overlaps compute so stage period = max(compute, comm). Testbed: Atom-class boards (2 GB and 8 GB), 1 Gbps with tc, fixed 20 ms latency, ViT workloads; ViT-Huge 16 devices 11.88x over one device, up to 4.16x over PipeDream on heterogeneous devices; throughput "does not decrease significantly" until bandwidth falls below ~30 Mbps. Static, offline partitioning. — [HTML](https://arxiv.org/html/2110.14895)

**LinguaLinked (Zhao, Song, Liu, Harris, Jyothi; arXiv 2312.00388, Dec 2023)**
- Devices: 3 x Pixel 7 Pro (12 GB) + 1 CUBOT X30 (8 GB), CPU only; BLOOM 1.1b/1.7b/3b, full precision and int8. Assignment is a (MILP/Gurobi) optimisation: minimise T_compute + T_data, memory constraint beta x available. Reported: 1.11-1.61x (single thread), 1.73-2.65x (multithread), runtime load balancing a further 1.29-1.32x. — [abstract](https://arxiv.org/abs/2312.00388); [HTML](https://arxiv.org/html/2312.00388)
- Load balancer monitors bandwidth, inter-device latency, available memory, total memory and FLOP/s (not CPU load or battery). Sub-modules are **pre-placed as overlapping replicas on two adjacent devices**; inactive copies sit on secondary storage. Migration (BLOOM 1.7b, 8 sub-modules): release 0.03 s, reload ~2.45 s full precision (0.234 s int8); per-token time 4.624 s -> 3.587 s (FP) and 2.756 -> 2.087 s (int8). Three-phone BLOOM-3b int8 inter-device hops about 1.5 MB per activation transfer. — [HTML](https://arxiv.org/html/2312.00388)

**Galaxy (Ye, Du, Zeng, Ou, Chu, Lu, Chen; arXiv 2405.17245, INFOCOM 2024)** — abstract only: hybrid model parallelism, heterogeneity-aware planning, tile-based comm/compute overlap, "up to 2.5x end-to-end latency reduction". Hardware, models and rebalancing not on the page. — [abstract](https://arxiv.org/abs/2405.17245)

**HexGen (Jiang, Yan, Yao, Zhou, Chen, Yuan; ICML 2024, arXiv 2311.11514)** — asymmetric tensor + pipeline partitioning across heterogeneous GPUs and networks, Llama-2 70B, "up to 2.3x lower latency deadlines or 4x more request rates"; scheduler described only as "constrained optimization" on the abstract page. — [abstract](https://arxiv.org/abs/2311.11514)

**Parallax (Gradient, with HKUST/NUS; arXiv 2509.26182, Sep 2025, "Parallax: Efficient LLM Inference Service over Decentralized Environment")**
- Exists, and is the closest recent analogue of a heterogeneous placement + re-balancing planner (datacenter/consumer GPUs, not phones). Phase 1 layer allocation: per-GPU layer capacity c_i from VRAM, DP over replica count, **score Z(k) = k^alpha / (T_comp + (s*(k)/k) * r_RTT)** (additive compute + stages x hop RTT, not a max), water-filling x_i = min(c_i, lambda F_i), largest-remainder rounding to contiguous intervals. Phase 2 request routing: DAG DP over live per-layer latency tau and one-way RTT rho, both published to a DHT every 1-2 s. Join: new GPU takes a slice starting at the bottleneck layer; global rebalance re-runs Phase 1 when a full pipeline is missing or the coefficient of variation of layer load exceeds a threshold. "Only the affected GPUs undergo weight reloading or eviction"; how weights move is not described. Testbed 5 x RTX 5090 + 2 x RTX 4090, ~10 ms inter-machine, Qwen3-32B; vs HexGen up to 3.6x (avg 1.58x) throughput and up to 3.2x (avg 1.66x) lower latency; Petals not benchmarked. — [arXiv HTML](https://arxiv.org/html/2509.26182v1)

**Alpa (Zheng et al.; OSDI 2022, arXiv 2201.12023)** — training-oriented inter-/intra-operator parallelism; the pipeline DP minimises **T* = min [ sum_i t_i + (B - 1) * max_j t_j ]** (B micro-batches), solved by enumerating t_max. — [Alpa paper PDF, Eq. 2-4](https://arxiv.org/pdf/2201.12023)

**Others useful for placement/migration** (abstract-level only): Helix (Mei et al., ASPLOS 2025) max-flow + MILP placement on 24-42 heterogeneous GPU nodes, up to 3.3x throughput, prompt/decode latency -66%/-24% — [abstract](https://arxiv.org/abs/2406.01566); SpotServe (Miao et al., ASPLOS 2024) re-parallelises on preemption and maps devices with Kuhn-Munkres matching to minimise context migration — [abstract](https://arxiv.org/abs/2311.15566); Llumnix (Sun et al., OSDI 2024) live-migrates requests and in-memory state between instances — [abstract](https://arxiv.org/abs/2406.03243).

**llama.cpp RPC itself**: default is to spread weights and KV over all devices (local and remote) **in proportion to available memory**; `--tensor-split` overrides the proportions; README states the feature is "in a proof-of-concept development stage" and "fragile and insecure"; RDMA is used only when both peers support it. — [RPC README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/rpc/README.md); `-sm layer` is the default split mode and means "split layers and KV across GPUs (pipelined)", `tensor` is "EXPERIMENTAL" — [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)

**ShareCompute's own placement** (for comparison): `StagePlanner.plan` weights each node by `usableBytes - perNodeOverhead` and apportions layers by Hamilton largest-remainder, with a per-node feasibility check; it has no speed, link or thermal input — [StagePlanner.swift:204-216, 267](file:///home/user/ShareCompute/Sources/ShareComputeCore/StagePlanner.swift). The native physical path does not call it: `native/split/probe.cpp` passes the per-worker **RPC buffer budgets (768/2048/1536 MiB) as `params.tensor_split` with `LLAMA_SPLIT_MODE_LAYER`**, so llama.cpp's own proportional rule produced 0-6 / 7-23 / 24-36 plus `output.weight` on the iPhone for the 3B model — [probe.cpp:29-59](file:///home/user/ShareCompute/native/split/probe.cpp), [findings.md F43](file:///home/user/ShareCompute/findings.md#L2724).

### Inferences
- The two-line summary of prior art is: *memory-proportional is the default everyone starts from* (llama.cpp RPC, exo's older default, ShareCompute); *profiled, cost-model placement* is what prima.cpp (ILP, disk-aware), EdgeShard (DP), LinguaLinked (MILP), Parallax (DP + water-filling) add; only Petals, LinguaLinked and Parallax re-balance at runtime, and all three have either replicated/pre-placed weights, stateless-ish inference (Petals replays inputs), or a datacenter-class link.
- The prima.cpp equal 8B/14B TPOT with llama.cpp (15/20 ms) is consistent with its scheduler collapsing to a single device when the model fits; the paper does not say this in so many words.
- Closest ancestor of ShareCompute's situation is prima.cpp (phones + laptops, Wi-Fi, 3-7 ms RTT, home cluster); closest on the algorithmic side is Parallax's additive latency score. Neither runs an RPC-style star topology, so neither pays ShareCompute's "every hop passes through the laptop" cost (F49).

### Gaps
- prima.cpp repo README not retrievable (404); Halda implementation details beyond the paper unknown, and whether the shipped repo implements runtime re-partitioning is unknown.
- Whether dllama's 459 ms/token on prima's cluster ran all four devices or a subset is not stated on the pages read.
- Galaxy's, HexGen's and EdgeShard's full device lists/algorithms were only partly available (abstract pages); HexGen's search algorithm (believed to be evolutionary) is UNVERIFIED.
- No published number found for any system running a 3B-class model across a 4 GB x86 laptop and two phones; no independent (non-author) reproduction of prima.cpp's table found.

## 2. prima.cpp's placement algorithm (Halda) in detail

### Takeaway
Halda minimises a **sum** of per-device compute, memory-access, disk-loading and communication terms (explicitly "T = sum T_m instead of T = max T_m"), over integer window sizes w_m, GPU layers n_m and ring rounds k, by enumerating the few valid k and solving a small ILP (HiGHS) per k; it takes about 10-12 ms and needs a device/model profiling step.

### Cited Findings
- **Objective**: minimise time-per-output-token as a sum over devices of compute, memory-access, disk-loading and communication terms plus a constant offset kappa; the paper states it minimises "T = sum T_m instead of T = max{T_m}" because OS prefetch timing is unknown and it takes a worst-case view. Appendix form (Eq. 37): TPOT = L (a^T w + b^T n + e^T c) / (e^T w) + kappa. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- **Variables**: w_m = layer window on device m; n_m = how many of those run on its GPU; k = rounds per token with L = k W and W = sum w_m. **Constraints**: n_m <= w_m <= L; window fill L - k(e^T w) = 0 (equal windows assumed in the proof, not required in the implementation); per-device RAM and VRAM bounds. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- **Solver**: enumerate valid factors k of L (at most 11 for L <= 100), solve a standard ILP with HiGHS for each k, iterate over device-set assignments until stable; initialise w proportional to available memory, n = 0; a calibration step moves the slowest-disk device to a forced set if some device has spare VRAM while another is overloaded. Paper calls the full problem NP-hard. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- **Device sets**: M1 macOS w/o Metal and short on RAM, M2 macOS with Metal and short on RAM, M3 Linux/Android short on RAM, M4 devices with enough RAM or slow disk (no overload allowed). A device assigned only one layer is dropped. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- **Profiler inputs**: model side, FLOPs per layer per quantisation (Q4_K, Q5_K, Q6_K, Q8_0, FP16, FP32) plus output-layer FLOPs; device side, FLOPS per backend (CPU/CUDA/Metal) x quant pair, KV-cache copy times, RAM-VRAM copy times, **communication latency measured between neighbours**, disk read throughput (random on macOS, sequential on Linux), available RAM/VRAM, Android swap-out behaviour. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)
- **Cost of the scheduler**: 10-12 ms on 4-32 devices; Halda off makes 70B 20,848 ms vs 674 ms. — [arXiv v2 HTML](https://arxiv.org/html/2504.08791v2)

### Inferences
- Halda's objective being a sum is evidence that the people who built the best-performing home-cluster planner reached the same conclusion as section 3 below: with one token in flight, per-token latency adds up.
- Its inputs are the ones ShareCompute lacks: per-device throughput per quantisation, neighbour latency, and available memory. The `CapabilityProfile` in Swift Core carries memory, power/thermal state and trust, but no throughput or link terms (fields listed at `CapabilityProfile.swift:93-162`).
- The disk term does not apply to ShareCompute (weights are held in RPC buffers, not mmap-paged), so a ShareCompute planner is a strict simplification of Halda: windows k = 1, no disk term, memory is a hard cap, not a soft penalty.

### Gaps
- Exact coefficient definitions a, b, c in Eq. 37 were not read (the relevant equations lie in the middle of the paper, outside the summarised ranges).
- No statement found of how Halda handles Wi-Fi jitter, or of re-profiling frequency.

## 3. Which objective is right for single-stream decode: min max-stage, or min sum of stage times + link latencies?

### Takeaway
For one sequence with one token in flight the right objective is **the sum**: T_token = sum over used stages of (compute + hop cost) (+ logits return). "Makespan = max stage cost" is the objective for *throughput with many in-flight micro-batches*; Alpa's formula T = sum t_i + (B-1) max t_j shows both are one expression, which collapses to the sum at B = 1. Under the sum objective faster devices should simply take as many layers as their memory allows, a slower device should receive only what the faster ones cannot hold, and every extra hop must pay for itself.

### Cited Findings
- General pipeline latency with B micro-batches: **T* = min [ sum_{i=1..S} t_i + (B - 1) * max_j t_j ]** (Alpa, Eq. 2); at B = 1 the max term vanishes. — [Alpa PDF](https://arxiv.org/pdf/2201.12023)
- EdgePipe/PipeEdge minimises the slowest stage because its target is throughput of a stream of inputs (ViT images) with overlapped communication. EdgeShard uses a *sum* DP for latency and a *min-max* DP for throughput (the latter paired with a no-bubble micro-batch schedule), i.e. both objectives coexist and are chosen by use case. — [EdgePipe HTML](https://arxiv.org/html/2110.14895); [EdgeShard HTML](https://arxiv.org/html/2405.14371)
- prima.cpp: "T = sum T_m instead of T = max{T_m}". Parallax scores allocation by T_comp + stages x hop RTT (additive). LinguaLinked minimises T_compute + T_data (both sums). — [prima.cpp v2](https://arxiv.org/html/2504.08791v2); [Parallax](https://arxiv.org/html/2509.26182v1); [LinguaLinked](https://arxiv.org/html/2312.00388)
- Link latency adds linearly to a single stream: Petals step rate falls from 2.29 to 1.57 steps/s (about 437 -> 637 ms per step, +200 ms, my arithmetic) when 100 ms latency is added to a 3-server Llama 2 70B chain at 100 Mbit/s, while dropping bandwidth from 1 Gbit/s to 100 Mbit/s changes nothing (2.29 both) because per-token activations are kilobytes. — [Petals paper HTML](https://arxiv.org/html/2312.08361)
- ShareCompute facts that fix the cost terms: layer split costs about one blocking round trip per link per token (2 direction switches/token/link); per-token payload is ~8 KB of activations per hop but **608 KB of F32 logits (151,936 x 4 B) returned from the last endpoint**; cross-server copies go worker -> host -> worker because `ggml_backend_rpc_buffer_cpy_tensor` returns false across servers; measured physical decode on the 3B Q8_0 run is 11,624 ms for 16 tokens (**0.73 s/token, 1.2-1.4 tok/s**); phones receive at ~5.68 MB/s (~45 Mbit/s); the laptop's relay moved 573.9 MB at 27.1 MB/s; Wi-Fi RTT has **never been measured** and per-node compute time has never been measured. — [F49](file:///home/user/ShareCompute/findings.md#L3521), [F43](file:///home/user/ShareCompute/findings.md#L2724), [F45](file:///home/user/ShareCompute/findings.md#L2983), [F48](file:///home/user/ShareCompute/findings.md#L3394)
- Qwen2.5-3B: hidden 2048, 36 layers, 16 heads, 2 KV heads, vocab 151,936, tied embeddings (so `output.weight` is a 151,936 x 2048 matrix, ~330 MB at Q8_0). — [Qwen2.5-3B-Instruct config](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/raw/main/config.json)

### Inferences

**Cost model proposed for the native path** (all terms measurable with small patches): T_token = sum over used workers i of ( c_i * n_i + h_i ) + logits_bytes / BW_out + act_bytes terms, subject to n_i * bytes_layer + overhead <= budget_i. Here c_i = decode ms per layer on device i, h_i = round-trip cost to worker i (probe <-> worker, measured), n_i = layers on i.
- For a *fixed set of used workers* the objective is linear in n_i, so the optimum is greedy: sort by c_i ascending (decode is memory-bandwidth-bound, so rank devices by effective memory bandwidth for the bytes of the chosen quant, not by FLOPs) and fill to each device's memory cap. Choosing the used set is a fixed-charge problem; with <= 15 endpoints (F49) enumerating 2^N subsets is trivial, so no ILP solver is needed.
- A slower device receives a layer only if faster ones are full, or if it is cheap enough to beat its hop cost: adding device s and moving k layers from faster f costs k (c_s - c_f) + h_s, which is positive whenever c_s >= c_f, so under the sum objective extra devices are never added for speed, only for capacity (this matches F49's conclusion "more devices add memory, not speed" and prima.cpp's observation that a 6-device cluster was slower than 3-4).
- Two decision variables the memory-proportional rule cannot express: **who holds `output.weight`** (the logits return is 608 KB per token; at the iPhone's ~5.68 MB/s that is ~107 ms, about 15% of the measured 0.73 s/token, whereas over the laptop relay at 27 MB/s it would be ~22 ms, at a cost of ~330 MB of the laptop's 768 MiB budget); and **whether a slow device (the 4 GB laptop) should be in the ring at all** besides being the coordinator.
- Decode and prefill need separate cost vectors: decode is bandwidth-bound, prefill compute-bound. prima.cpp profiles both (FLOPS per quant, memory/disk throughput).

**Worked numeric example (ASSUMED speeds; method reproducible in a ~40-line enumerator).** Model: 36 layers + output slot. Assumed decode ms per layer: laptop 30, Android 15, iPhone 10 (1:2:3 speed ratio, an assumption, calibrated so the current plan lands at the measured value); hop cost h = 2 / 8 / 8 ms; output slot adds 25 ms compute plus logits transfer ~107 ms on a phone (22 ms on the laptop); layer caps from budgets at ~80 MiB per layer (F43's held bytes divided by layers): laptop 9, Android 25, iPhone 15 (it also holds the 330 MB output). Results, ms per token (stage times in brackets):

| Plan | layers (laptop/Android/iPhone) | stage times | SUM = latency | MAX = bottleneck |
|---|---|---|---|---|
| Current memory-proportional (budget shares) | 7 / 17 / 12 (+out) | 212 / 263 / 260 | **735** (1.36 tok/s; measured 727) | 263 |
| Min-max ("makespan") | 8 / 16 / 12 | 242 / 248 / 260 | **750** (worse than current) | **260** |
| Min-sum (latency) | 0 / 21 / 15 | 0 / 323 / 290 | **613** (1.63 tok/s, -17%) | 323 |
| Min-sum, output slot placed on laptop (laptop cap 5) | 0 / 19 / 17 (+ laptop holds output) | 49 / 293 / 178 | **520** (1.92 tok/s, -29%) | 293 |

Sensitivity: with phone RTT raised to 20 ms the min-sum plan is 637 vs 759 current; with the iPhone throttled 1.5x (15 ms/layer) it is 688 vs 795 current and min-max moves to 825. Min-max balances the stages but leaves the *sum* unchanged or worse, because balancing pushes layers onto the slowest device. Using Alpa's formula with B in flight on the same two plans (A-case): B = 1: 750 vs 613 ms; B = 2: 1010 vs 936; B = 3: 1,270 vs 1,259; B = 4: 1,530 vs 1,582 (crossover near B = 3-4, which is the number of stages); B = 8: 2,570 vs 2,874. So min-max only wins once ~3-4 sequences (or speculative branches) are in flight, e.g. F49's batched emulation (0.95 -> 2.3 tok/s aggregate at 1 -> 8 sequences) but not for one user's single answer.
- Caveat: the 17-29% gains come from assumed speed ratios and from using only two of three workers; the robust result is structural (min-max is not a latency objective; the current memory-proportional split sits within a few percent of min-max, not of min-sum). The magnitude requires measured c_i and h_i.
- Pipeline utilisation for one stream is ~1/S: the idle stages cannot be used by balancing; the levers that do use them are speculative decoding (prima.cpp: 25-45% lower latency with a draft model) or multi-sequence batching.

### Gaps
- No measured per-layer decode time per device, no Wi-Fi RTT, and no jitter distribution exist for ShareCompute's devices (F49 states both). The numbers above are therefore unvalidated.
- Whether llama.cpp's RPC path overlaps the next token's early stages with the previous token's last stage (it does not for a single sequence, but this was not instrumented) is unverified; a stage period of max(compute, comm) (EdgePipe's assumption) does not hold for blocking RPC calls.

## 4. Telemetry fields that are actually useful

### Takeaway
Four signals earn their keep: (1) per-stage compute ms per token measured *inside the worker around graph compute*, (2) per-link round-trip and bytes per token measured at the coordinator (so network time = exchange time minus worker compute), (3) free/available memory and (4) thermal/power state. Everything else (RSSI, frequency, battery %) is secondary.

### Cited Findings
- What systems actually collect: LinguaLinked monitors bandwidth, inter-device latency, available and total memory, and FLOP/s (not CPU load or battery; battery listed as future work). Parallax publishes per-layer latency tau and one-way RTT rho to a DHT every 1-2 s. Petals ranks servers by min(network throughput, GPU throughput) and pings candidates for routing. prima.cpp profiles FLOPS per backend x quantisation, KV-copy and RAM-VRAM copy times, neighbour latency, disk throughput, available RAM/VRAM. — [LinguaLinked](https://arxiv.org/html/2312.00388); [Parallax](https://arxiv.org/html/2509.26182v1); [Petals](https://arxiv.org/html/2312.08361); [prima.cpp](https://arxiv.org/html/2504.08791v2)
- What ShareCompute already records: `report.json` with `phases`, `host_memory`, `loop_stalls`, per-node `upload:*` and `cache:*` spans, graph-call counters incremented after `ggml_backend_graph_compute` returns, and phone `mem` rows (Android `total_mib` 3,472, `avail_mib` dipping to 282 MiB; iOS headroom). **No per-stage time per token and no per-link RTT exist yet.** — [F44-F48](file:///home/user/ShareCompute/findings.md#L2802), [F49 section 5](file:///home/user/ShareCompute/findings.md#L3521)
- Platform thermal sources (documented APIs, but the official pages could not be read through the proxy, so API levels and semantics here are from general knowledge, UNVERIFIED): Android `PowerManager.getCurrentThermalStatus()` / `addThermalStatusListener` (API 29) and `getThermalHeadroom(forecastSeconds)` (API 30, a forecast where ~1.0 means throttling); iOS `ProcessInfo.thermalState` (nominal/fair/serious/critical) and `thermalStateDidChangeNotification`. — [Android PowerManager](https://developer.android.com/reference/android/os/PowerManager); [Apple thermalState](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.property)
- The Swift `PowerProfile` already has a `ThermalState` of nominal/fair/serious/critical and `isUnderDuress`, mirroring the iOS enum. — [CapabilityProfile.swift:93-130](file:///home/user/ShareCompute/Sources/ShareComputeCore/CapabilityProfile.swift)

### Inferences
- **Per-stage ms/token**: wrap `ggml_backend_graph_compute` in the worker (the existing `llama-budget.patch` already increments a counter right after that call) with a monotonic-clock delta and report an EWMA plus p50/p95 per run. This single field converts "decode ms/layer" into c_i = stage_ms / n_i, the one term the planner is missing. Not built or tested (UNVERIFIED that the patch point is as simple as described).
- **Link RTT and split**: the coordinator times each exchange; subtracting the worker-reported compute time gives h_i (network + relay + (de)serialisation + TLS framing). Report bytes per token per direction too (608 KB logits is the largest single term). A cheap active probe (tiny RPC echo, 20 pings) before loading gives h_i for the *first* plan, before any decode has run.
- **Memory**: free RAM at plan time and the floor seen during the previous run (laptop floor was 89.2 MiB of 3,973 in F45; Android visible RAM is 3,472 MiB, not 8 GB, F49) turn the budget from an operator guess into a measured cap; the planner should treat budget as min(configured, observed headroom).
- **Thermal**: use as a gate and as a slow multiplier on c_i (a throttled phone's c_i rises; Android headroom is a forecast, iOS gives four coarse states). Sample on state-change callbacks plus a 10-30 s timer; do not feed it into per-token decisions.
- Telemetry should be **observe-only inside a generation**, written to the run report and a per-device profile file, then used at the next plan (section 5).

### Gaps
- Official Android/Apple thermal API documentation could not be fetched; verify API levels, rate limits and semantics before relying on them.
- No source found quantifying Wi-Fi RTT variance for phone-laptop links in homes; prima.cpp reports 3-7 ms mean range on its router.
- Whether the phones' RPC server threads can expose compute time without a patch to the worker is not checked.

## 5. Applying a new plan: weight movement, KV cache, quiescing, reload cost; soft re-balancing vs plan-once; verdict on propose/commit

### Takeaway
Real systems avoid paying a reload per re-plan by having weights already present (prima.cpp mmap on every device, LinguaLinked pre-placed adjacent replicas, Parallax reloading only affected GPUs), by replaying inputs instead of migrating KV (Petals), and by throttling re-plans with hysteresis (Petals' 20% threshold). ShareCompute has none of these: a plan change means a new llama context and, in practice, a reload of ~100-140 s warm (~190 tokens' worth of decode), so in-session soft re-balancing cannot pay back on short generations and the propose/commit protocol degenerates into "pick the plan at the next epoch".

### Cited Findings
- Petals: switching blocks "resets attention caches", which is why the threshold is p = 20%; on failure the client replays cached stage inputs to rebuild a replacement server's attention cache (O(t) data, recompute only failed stages). — [Petals paper HTML](https://arxiv.org/html/2312.08361)
- LinguaLinked: replicas pre-placed on adjacent devices, inactive ones on storage; migration pauses only each device's own compute in sequence; release 0.03 s + load ~2.45 s for 8 sub-modules of BLOOM-1.7b FP (0.234 s int8); per-token time ~4.6 s -> ~3.6 s. — [LinguaLinked HTML](https://arxiv.org/html/2312.00388)
- Parallax: global re-balance only when a full pipeline is missing or load CV exceeds a threshold; "only the affected GPUs undergo weight reloading or eviction"; weight transfer mechanism not described. — [Parallax HTML](https://arxiv.org/html/2509.26182v1)
- prima.cpp: repartition possible "whenever the task queue is empty"; each device already has the model file so no layer migration is needed. — [prima.cpp v2](https://arxiv.org/html/2504.08791v2)
- SpotServe formulates device remapping on preemption as bipartite matching (Kuhn-Munkres) to minimise migration; Llumnix live-migrates requests with in-memory state (details of KV migration downtime not confirmed; my recollection that it overlaps copy with decoding and keeps downtime to tens of ms is UNVERIFIED). — [SpotServe](https://arxiv.org/abs/2311.15566); [Llumnix](https://arxiv.org/abs/2406.03243)
- ShareCompute constraints: a failed llama.cpp RPC endpoint cannot be re-attached within a process (F35, `/health` still says ok); every token is an all-ranks barrier; the supervisor uses a fresh bounded subprocess and discards a failed generation; physical 3B reload costs: cold wall 492-557 s, warm 140-166 s, of which loading is 98.3 s (70%) with the phones loaded strictly one after the other (0.0-0.4 s overlap) and the laptop's own weights 21 s; phones pull weights over Wi-Fi at ~5.68 MB/s cold, warm hits are 30-37 MB/s of flash reads plus a hash check on each hit. `llama-parallel-load.patch` cut loopback split_generation by ~31% but has not been measured on the phones. — [F35](file:///home/user/ShareCompute/findings.md#L2116), [F43](file:///home/user/ShareCompute/findings.md#L2724), [F45](file:///home/user/ShareCompute/findings.md#L2983), [F48](file:///home/user/ShareCompute/findings.md#L3394), [F51](file:///home/user/ShareCompute/findings.md#L3669)
- Prefill after a restart is not cheap on the physical devices: 11.3-12.4 s (F43) and 28.95 s (F48 warm) for a 5-token prompt, partly an unexplained excess. — [F43](file:///home/user/ShareCompute/findings.md#L2724), [F48](file:///home/user/ShareCompute/findings.md#L3394)

### Inferences
- **Break-even formula** for a re-plan: N* = R / (T_old - T_new), where R is the reload+re-prefill cost in seconds and T the per-token latency. With R ~ 98-140 s and an assumed gain of 122 ms/token (the 735 -> 613 ms example in section 3), N* ~ 800-1,150 generated tokens, about 8-12 minutes of continuous generation at ~1.6 tok/s. For the project's 16-token proof runs a re-plan can never pay back. Compare LinguaLinked, where migration costs ~0.5 token-times (2.45 s / 4.6 s) so soft rebalancing is almost free; ShareCompute's would be ~190 token-times (140 s / 0.727 s).
- **Cost is proportional to model size, not to layers moved**: even if only 4 layers change owner (~80 MiB each; ~14.8 s per layer at 5.68 MB/s if the new owner has not cached them, my arithmetic, so ~60 s for four), a new `llama_model` load re-reads and re-hashes every cached tensor on every worker (F38/F51) and re-uploads the laptop's own weights. Incremental movement would need a patch to move tensors between RPC buffers or a long-lived context; no llama.cpp API for that is known (UNVERIFIED claim that none exists, inferred from how buffers are allocated at load).
- **KV migration is not worth building at this context length**: n_ctx is 512 in `probe.cpp`; KV for Qwen2.5-3B is 36 KiB/token at f16 (2 x 36 layers x 2 KV heads x 128 x 2 B), so ~18 MiB total at 512 tokens. Cheaper than migrating it is Petals' approach: the coordinator already holds all generated token ids, and greedy decoding is deterministic (tokens equal reference in F37/F43), so after a re-plan **re-prefill prompt + generated prefix** (cost = one prefill, 11-29 s measured). The safe quiesce point is between tokens (each token is already an all-ranks barrier, CLAUDE.md fact 2), which is a coordinator-side decision and needs no worker cooperation.
- **Why in-session soft re-balancing is not worth it here**: (a) the closed 3-device roster has little churn, and Petals' own experience was that frequent switching hurts; (b) reload dwarfs the plausible gain; (c) F35 forces process-level replacement for any changed endpoint set anyway; (d) the gains from correcting a placement (section 3: 17-29% in the example) are larger and cheaper to capture by choosing a good plan *once* than by chasing drift.
- **Recommended design**: observe-only telemetry in every run -> persisted device profile (EWMA of c_i, h_i, headroom, thermal) -> plan at the next epoch boundary (new session, or after a failure that already forces a restart). Re-plan mid-session only if all hold: predicted (T_old - T_new) x expected remaining tokens > R + risk margin; improvement >= a hysteresis threshold (Petals uses 20%); a failure is already forcing a restart. Add local-first (section 6) as a candidate plan.
- **Verdict on the propose/commit protocol**: two-phase commit with epoch fencing is the right *consistency* mechanism and ShareComputeCore already has epochs, but for the native path "commit" means "kill the probe and workers' endpoints, reload, re-prefill", so the protocol's value is limited to agreeing on the next epoch's plan at a boundary, not to live migration. Treat the rebalance proposal as a *planning* output consumed at epoch start; do not build quiesce/KV-migration machinery for the llama.cpp path. The MLX/Swift path has separate constraints (finalize() across repos) and was not assessed here.

### Gaps
- No measured reload cost for a *partial* plan change on the physical devices; no measurement of whether phone links are independent (could change parallel-load savings, F51).
- Llumnix and SpotServe migration mechanics (downtime figures, progressive migration) were only seen at abstract level.
- Whether llama.cpp can reassign a tensor to a different RPC buffer without reloading: not checked in source (pinned tree is not on this machine; `native/split/llama-revision.txt` pins `4da6337...`).

## 6. Local-first hybrid execution: measured crossovers

### Takeaway
Published crossovers are defined by *memory fit*, not by link speed: below the fit point the best distributed planner collapses to one device (prima.cpp 8B/14B identical to llama.cpp; EdgeShard at 1 Mbps), above it distribution wins big (30B: 202 -> 72 ms; 60B+: >10x because single-device llama.cpp thrashes disk). The only on-hardware crossover the project has is the 0.5B run where the 4 GB laptop alone was slower per token than the split, but 4x slower in wall time because of the upload.

### Cited Findings
- prima.cpp (strong GPU laptop/desktop plus phones, Wi-Fi 320-610 Mbps, 3-7 ms): single-device and distributed TPOT are identical at 8B (15 ms) and 14B (20 ms); distributed wins from 30B (202 -> 72 ms, 2.8x), 45B (328 -> 233), 60B (7,965 -> 468, 17x), 70B (10,120 -> 674). llama.cpp's numbers at 60B+ are mmap/disk-thrash numbers. — [prima.cpp v2](https://arxiv.org/html/2504.08791v2)
- EdgeShard: collaborative beats Edge-Solo above ~10 Mbps; at 1 Mbps its optimiser collapses to local execution; 7B: Edge-Solo 140.34 ms/token vs EdgeShard 75.88 ms (Jetson cluster + RTX 3090, 50 Mbps +/-20% edge links). — [EdgeShard HTML](https://arxiv.org/html/2405.14371)
- Petals vs offloading for a model that does not fit: 2.29 vs 0.139 steps/s (Llama 2 70B), i.e. pipeline over a network beats local offload by ~16x at batch 1, even at 100 ms latency (1.57). — [Petals paper HTML](https://arxiv.org/html/2312.08361)
- distributed-llama on Raspberry Pi 4B over Gigabit: scaling 1 -> 2 -> 4 Pis helps 7B (1,312 -> 793 -> 494 ms), but 8 Pis hurts (588 ms; transfer 1.8 -> 289.75 ms). — [fork README mirror](https://github.com/Dyl777/distributed-llama/blob/main/README.md)
- ShareCompute 0.5B (physical, F37): laptop-alone vs split: prefill 3,554 vs 1,942 ms; decode (16 tokens) 10,885 vs 5,489 ms, i.e. ~680 vs ~343 ms/token; wall 15,611 vs 66,352 ms, dominated by uploading 324 MiB to the phones. No laptop-alone attempt exists for the 3B model (F43 says a memory-mapped 3.4 GB model may still run on 4 GB, slowly). — [F37](file:///home/user/ShareCompute/findings.md#L2241), [F43](file:///home/user/ShareCompute/findings.md#L2724)

### Inferences
- Local-first rule for the planner: compute T_local = (local ms/layer x layers) + paging penalty if the model does not fit in RAM, against T_pipe = section 3's sum for the best multi-device plan, plus amortised load R / expected tokens. Choose local when the model fits comfortably in the local budget and T_local <= T_pipe + R/N. For a slow CPU like the AMD A9-9420e the measured 0.5B result says "fits" is not sufficient: the phones' CPUs were faster per layer than the laptop, so the pipeline wins on decode even for a model that fits (F37), and loses on wall time unless weights are cached (F39: 92.5% less upload on the second run).
- Because the sum objective prefers the fastest devices, the planner will often *drop the laptop's layers* and use it only for tokenisation and orchestration, which is exactly "local-first inverted": the laptop is the weakest compute node and the coordinator.
- The memory-fit crossover for ShareCompute is set by budgets (768/2048/1536 MiB), not by Wi-Fi: 3B Q8_0 (3,209 MiB held) fits no single worker; the Q4 file fits Android alone (F40).

### Gaps
- No data point for a 3B model on the 4 GB laptop alone (mmap or not), no phone-alone 3B Q4 vs split Q8 comparison, no Wi-Fi RTT: the actual local-vs-pipeline crossover on this hardware is unmeasured.
- Published crossovers use much stronger devices than the A9-9420e; they transfer qualitatively only.

## 7. KV-cache quantisation and per-device mixed precision

### Takeaway
KV quantisation (`-ctk/-ctv`, q8_0 near-lossless, q4_0 risky; quantised V needs flash attention) saves memory not time, and at ShareCompute's n_ctx = 512 it saves under 10 MiB in total, so it is irrelevant until contexts reach several thousand tokens. Per-layer mixed-precision GGUFs are possible with `llama-quantize --tensor-type` regex, and academic work (LLM-PQ, SplitQuant, Voltron) plans partition and precision jointly, but it conflicts with ShareCompute's exact-token proof gate and its content-hash weight cache.

### Cited Findings
- Flags (current master README): `-ctk/--cache-type-k` and `-ctv/--cache-type-v` accept f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1, **default f16**; `-fa` is on/off/**auto (default)**. — [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)
- Constraint in current source: in the `llama_context` constructor, if flash attention is off and `ggml_is_quantized(type_v)`, it throws `"quantized V cache was requested, but this requires Flash Attention"`; in auto mode a probe may disable FA, in which case a quantised V cache then also errors. No separate quantised-K check was seen. This is master, not the project's pinned revision. — [llama-context.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-context.cpp)
- Quality evidence is secondary: one benchmark (Qwen2.5-Coder-7B Q4_K_M, 8K context, 12 prompts x 256 greedy tokens) found q8_0 81.6% similar to f16 (difflib) and q4_0 8.3% ("quality cliff"); memory saved at 8K was only 208 MB (q8_0) and 320 MB (q4_0); on Metal q4_0 was 42% slower (54.1 -> 31.2 tok/s); the article admits difflib is a blunt metric and tested K and V together. Search summaries of other blogs say q8_0 is near-lossless (<0.1% perplexity change) and q4_0 K tolerable but q4_0 V not; they were not individually opened. — [InventiveHQ benchmark](https://inventivehq.com/blog/kv-cache-quantization-quality-benchmark)
- Per-tensor quantisation tool: `llama-quantize --tensor-type` "quantize specific tensor(s) to specific quant types. Supports regex syntax" (example `"\.(\d*[13579])\.attn_k=q5_k"` for odd layers); also `--output-tensor-type`, `--token-embedding-type`, `--imatrix`, `--prune-layers`. — [quantize README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/quantize/README.md)
- Joint partition + quantisation prior art: LLM-PQ ("Phase-Aware Partition and Adaptive Quantization", arXiv 2403.01136) and SplitQuant (Cluster 2025) decide layer partition, micro-batch size and per-layer bit-width on heterogeneous GPU clusters; Voltron (Cho, Kim, Son, Lee, Kim; arXiv 2607.07046, Jul 2026) targets elastic multi-device edge execution, reportedly scaling layer precision in ascending importance, with up to 16.5% higher accuracy than single-device LLMs at the same QoS (only the abstract was read; device types, models and baselines unknown). prima.cpp profiles FLOPS separately per quant format. — [LLM-PQ](https://arxiv.org/pdf/2403.01136); [SplitQuant PDF](https://i.cs.hku.hk/~cwu/papers/jtzhao-cluster25.pdf); [Voltron abstract](https://arxiv.org/abs/2607.07046); [prima.cpp](https://arxiv.org/html/2504.08791v2)
- ShareCompute facts: probe uses `n_ctx = 512`, default KV type, `LLAMA_SPLIT_MODE_LAYER`; F49 ran flash attention forced through RPC workers in tensor mode with equal tokens (so FA executes over RPC for f16 KV); the phones' spare memory during the 3B runs was 206/700/237 MiB (laptop/Android/iPhone). — [probe.cpp:55-71](file:///home/user/ShareCompute/native/split/probe.cpp), [F49](file:///home/user/ShareCompute/findings.md#L3521), [F43](file:///home/user/ShareCompute/findings.md#L2724)

### Inferences
- Qwen2.5-3B KV size (config: 36 layers, 2 KV heads, head_dim 2048/16 = 128): f16 36,864 B/token; q8_0 (34 B per 32 elements) 19,584 B/token; q4_0 (18 B per 32) 10,368 B/token. At n_ctx 512: 18.0 / 9.6 / 5.1 MiB total; at 8,192: 288 / 153 / 81 MiB, split across devices by layer. Against 3.4 GiB of weights and 200-700 MiB spare per worker, q8_0 KV is worth enabling only for long contexts, and it is the safe first choice there.
- Any lossy KV or weight quantisation breaks the project's pass criterion (tokens identical to a pinned reference, F37/F43), so it needs a separate gate with tolerance (token match rate or perplexity delta) and its own reference. F37/F40 already flag near-tie drift across x86 and ARM.
- Per-device precision interacts with the cost model: in the bandwidth-bound decode regime, per-layer time scales roughly with bytes read, so a Q4 layer runs ~1.9x faster than Q8_0 on the same device (inference, unmeasured here). The planner would choose bits and layer ranges jointly (cost per layer = bytes_l / BW_i). But the weights are one GGUF sent as-is to RPC workers and cached by content hash (1 MiB threshold), so mixed precision means authoring one mixed GGUF (via `--tensor-type` regex per layer range), not quantising per device on the fly; and every plan change would need a different file and a cold cache.
- The F40 design choice (use Q8_0 so the model does not fit one worker) is itself a precision decision that mixed precision would reverse: lower-precision layers on phones would let one phone hold more and push toward fewer hops.

### Gaps
- Pinned-revision behaviour (`4da6337...`) for quantised KV over the RPC path is untested; `ggml_backend_rpc` `supports_op` for flash-attention with q8_0 K/V on a CPU worker is UNVERIFIED.
- No primary-source perplexity table for q8_0/q4_0 KV was retrieved (only a blog benchmark and search summaries).
- Voltron's and SplitQuant's details beyond abstracts/search snippets were not read; LLM-PQ was seen only through a search summary.

## 8. Assessment of the StagePlanner design (as described plus the code)

### Takeaway
The existing `StagePlanner` is a sound *feasibility* planner (disjoint contiguous ranges, per-node budgets, deterministic) but not a *cost-model* planner: it ignores speed and links, and a "makespan = max stage cost" upgrade would optimise the wrong quantity for one-user decode. The right upgrade is a sum-of-stage-times-plus-hops model solved by greedy fill over a small subset search, driven by measured per-stage ms and RTT, applied at epoch boundaries; live propose/commit migration is not justified on the llama.cpp path.

### Cited Findings
- `StagePlanner` apportions layers by usable-memory weights with Hamilton's method and checks each node against its own budget; there is no throughput, link or latency term — [StagePlanner.swift:129-318](file:///home/user/ShareCompute/Sources/ShareComputeCore/StagePlanner.swift). The physical path passes budgets as `tensor_split` directly to llama.cpp instead — [probe.cpp:29-59](file:///home/user/ShareCompute/native/split/probe.cpp), [split_cluster.py:64-87, 650](file:///home/user/ShareCompute/scripts/split_cluster.py).
- Prior art on objective and dynamism is in sections 1-5: sum for latency (Halda, EdgeShard latency DP, Parallax, LinguaLinked), max only for throughput (EdgePipe, EdgeShard throughput DP, Alpa with B > 1), hysteresis and replay for dynamic changes (Petals).

### Inferences
1. **Replace makespan with sum-of-stages + hops** for the single-user objective; keep max as a secondary objective only if batched/speculative decoding is later enabled (T = sum + (B-1) max).
2. **Add three inputs** the planner lacks: c_i (decode ms per layer, from in-worker timing), h_i (probe-to-worker round trip), and measured headroom replacing configured budget; treat the output-layer owner and the used-set (including dropping the laptop's layers) as explicit decisions.
3. **Greedy fill + subset enumeration** is sufficient (<= 15 endpoints, linear objective); no ILP dependency. This also keeps `ShareComputeCore` dependency-free if implemented there.
4. **Realisation constraint**: on the native path the planner's output has to be expressed as `tensor_split` shares and device order; whether shares equal to slot counts reproduce exact layer counts (e.g., 7/17/12 + output) is untested (UNVERIFIED) and should be checked on loopback, which F43 shows is a faithful rehearsal for placement.
