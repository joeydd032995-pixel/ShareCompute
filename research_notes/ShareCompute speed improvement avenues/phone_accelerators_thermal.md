## Q1. Do Vulkan, OpenCL (Adreno) or Hexagon/NPU give a realistic speedup on a mid-range Android phone such as the moto g 5G 2024?

### Takeaway
No evidence found that any GPU/NPU llama.cpp path works on, let alone beats the CPU on, a Snapdragon 4 Gen 1 / Adreno 619. OpenCL's own doc says Adreno 6xx phones are "likely not supported", the Hexagon backend targets only v73/v75/v79/v81 (8 Gen 2 and newer class), and Vulkan on Adreno has open or closed-unfixed reports of being slower than CPU or producing wrong output. Even on flagships, vendor numbers show GPU decode roughly at CPU level, because decode is memory-bandwidth bound.

### Inferences
- For a 3B Q8_0 or Q4 model on SD 4 Gen 1 the realistic GPU/NPU speedup for decode is **zero to negative**, and "unknown" is the honest label for prefill: no source tested this SoC, the OpenCL doc excludes it by driver age, the Hexagon backend does not list its generation, and the only Vulkan evidence on Adreno is negative. The two gaps are Adreno 619's Vulkan capabilities (Vulkan 1.1-class driver, fp16/16-bit-storage support) and its Hexagon version, neither established here.
- Decode on every mobile SoC is DRAM-bound, so a GPU/NPU can only help by (a) making prefill faster, (b) lowering energy per token, or (c) reaching a higher effective fraction of DRAM bandwidth. Qualcomm's flagship table (12 tok/s for 7B on Adreno 750) is the same order as the CPU figure above (about 12.8 tok/s on a newer chip), which is consistent with that.
- If any accelerator is attempted on the moto g it should be OpenCL (the only Adreno-specific, vendor-maintained path) and only after a CPU baseline exists; Vulkan on Adreno 619 should be treated as a research dead end until a maintained report says otherwise.

## Q2. Is a GPU backend behind the RPC worker beneficial (iPhone Metal; Android Vulkan/OpenCL), given unified memory and the RPC data path?

### Takeaway
Mechanically it is possible (the RPC server accepts any ggml device, Metal included) and unified memory makes the weight copy cheap, but at the current 5-token / 16-token test the phones' share of the roughly 0.7-0.85 s per token is probably small and unmeasured, so the achievable gain from a phone GPU is bounded to a few percent to low tens of percent of token time, while the costs are real: a new build flavour, no per-op CPU fallback on the server, a Metal working-set cap, Jetsam risk, GPU thermals, and foreground-only execution. The right first step is per-node compute timing, not a backend.

### Cited Findings
- The upstream RPC README diagrams a server fronting a Metal device, and the server accepts a list of `ggml_backend_dev_t`. The project's worker hard-codes the CPU registry and requires exactly one device (`ggml_backend_cpu_reg()` ... `dev_count != 1` returns 3), then calls `ggml_backend_rpc_start_server(endpoint, cache, threads, 1, &dev)`. — [tools/rpc/README.md (pinned)](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/tools/rpc/README.md), [native/split/worker.cpp:9-27](/home/user/ShareCompute/native/split/worker.cpp)
- RPC server internals: `alloc_buffer` uses `ggml_backend_get_default_buffer_type(backends[dev_id])` (`ggml-rpc.cpp:1252`); the server runs `ggml_backend_graph_compute(backends[device], graph)` and asserts success ("Unsuccessful graph computations are not supported with RPC", lines 1779 and 1795); the client-side RPC device's `supports_op` returns `true` unconditionally with `//TODO: call the remote backend` (lines 2216-2221). So the scheduler cannot route an unsupported op to a CPU fallback; the whole subgraph runs on the server's one backend. — [ggml-rpc.cpp (pinned)](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-rpc/ggml-rpc.cpp)
- Per-token wire traffic on the layer split is about 8 KB of activations per hop plus the F32 logits (0.608 MB per token) on the last link; weights cross the wire once at load. — [findings.md F49 section 3](/home/user/ShareCompute/findings.md)
- Metal in ggml at the pin: `has_simdgroup_mm` needs `MTLGPUFamilyApple7` (A14 and later); shared buffers are used when the device has unified memory; the Metal-4 "tensor API" is disabled by default for pre-M5 / pre-A19 chips (log line "tensor API disabled for pre-M5 and pre-A19 devices"); `max_working_set_size = recommendedMaxWorkingSetSize` (iOS 16+), `max_buffer_size = maxBufferLength`; residency sets are used by default. — [ggml-metal-device.m:1133-1161, 1269-1292](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-metal/ggml-metal-device.m)

- The ComputeWorker app already stops the session when the scene goes to the background (`onChange(of: phase) { if $0 == .background { model.stop("Backgrounded ...") } }`) and keeps the screen on with `isIdleTimerDisabled`. — [ComputeWorkerApp.swift:56](/home/user/ShareCompute/Apps/ComputeWorker/Sources/ComputeWorkerApp.swift), [WorkerModel.swift:384](/home/user/ShareCompute/Apps/ComputeWorker/Sources/WorkerModel.swift)

### Inferences
- Unified memory does remove the discrete-GPU transfer problem: with Metal shared buffers the server's `set_tensor` is one `memcpy` into memory the GPU can read, once per weight at load, and the per-token traffic is kilobytes. The "weights transit CPU memory first" concern is therefore small for Metal on iPhone (not for a discrete GPU). On Android Vulkan/OpenCL the same is true in principle (`uma 1` in the #20603 log) but UNVERIFIED for the moto g.
- Bounded benefit, back-of-envelope (assumptions stated, not measured): the iPhone holds 1,298.6 MiB (1.36 GB) of Q8_0 layers (F43). If its 2 performance cores sustain 25-40 GB/s the weight read costs about 0.03-0.05 s per token; an MLX-like GPU reached about 33 GB/s equivalent when cool and about 20 GB/s when hot (0.87 GB model assumed for Qwen2.5-1.5B 4-bit). So the iPhone stage is likely 0.03-0.07 s of a 0.7-0.85 s token whichever processor does it; Metal would save at most a few hundredths of a second per token on decode. The Android stage holds 1,348.3 MiB (1.41 GB); at the quoted 17 GB/s peak (soft) and 50-70% efficiency, 0.12-0.17 s per token is its bandwidth floor, and a GPU cannot go below that floor either because it reads the same DRAM.
- Where a phone GPU could matter is prefill of long prompts (compute-bound, per Qualcomm slide 13) and maybe energy; the project's test prompt is 5 tokens, so it cannot show that benefit. F48 also found a 29 s prefill whose cause is unrelated to phone compute (the phones are downstream of the laptop's first graph).
- Risk list for Metal behind RPC: no per-op fallback (a Metal-unsupported op aborts the worker via the GGML_ASSERT), `recommendedMaxWorkingSetSize` cap and Jetsam both apply, GPU work stops when the app leaves the foreground (the app already stops then), GPU thermals can floor clocks as in the MLC/Adreno run, the Xcode metal compile and `GGML_METAL_EMBED_LIBRARY` add a build flavour (CI macOS can build it), and the existing budget/cache patches would need re-checking against a Metal buffer type (UNVERIFIED, not read).

### Gaps
- No per-node compute time exists anywhere in the project (F49 states this); without it neither the bound above nor any accelerator's payoff can be ranked. The same applies to Wi-Fi round-trip time and to the 0.608 MB-per-token logits return path at the phones' roughly 5.7-6.2 MB/s store rates (those rates were measured laptop-to-phone, not phone-to-laptop).

## Q3. What are the cheapest CPU-only speedups (build flags, dot-product / i8mm, Q4_0 repack, KleidiAI, thread count, big.LITTLE)?

### Takeaway
In order of cost and certainty: (1) log CPU features and per-graph busy time; (2) raise the compile baseline for the two known phones (Android `armv8.2-a+dotprod+fp16`, iPhone `armv8.6-a+i8mm+dotprod+fp16` or similar), which the pinned code shows is currently absent; (3) sweep thread count and core placement on the moto g. Q4_0 online repack and KleidiAI, the usual big wins, are **blocked in the RPC worker at this pin**: the server rejects any tensor a backend marks with `extra`.

### Cited Findings
- Repack and KleidiAI both rely on CPU "extra buffer types". Currently unimplemented." ### Inferences
- Because every kernel dispatch is compile-time here, the phones run the slowest NEON fallback today. Expected effect of adding dotprod (and i8mm on the A18): large for any multi-token batch (prefill; the dot product is the inner loop and the emulation costs several NEON ops per 16 MACs), modest for single-token decode, which is DRAM-bound (Qualcomm slide 13). My rough estimate of the emulation cost on two A78 cores at 2.0 GHz is of the same order as the DRAM floor for the Android stage (about 0.07 s of compute versus about 0.12-0.17 s of memory time per token), so some decode gain is plausible but unquantified. UNVERIFIED; needs `llama-bench`-style measurement.
- Dotprod is safe on the moto g if all eight cores report `asimddp` (A78 documented; Cortex-A55 supports Armv8.2 dot product from my own knowledge, UNVERIFIED here; read `Features` for every CPU). A baseline above Armv8.0 turns an unsupported phone into a SIGILL at the first kernel, so the Android app needs a pre-start feature check or two library variants; the pinned CMake itself warns about SIGILL when loading backends on older CPUs. The iPhone deployment target is iOS 16.0 (A11), so an i8mm baseline would crash on an A11-A14; the operator has one known iPhone.
- Repack/KleidiAI for the RPC worker require a fourth carried patch: keep `extra` traits server-side (the code comment says exactly that) or re-attach traits when graphs are deserialized, allocate weight buffers from the extra buffer type, and prove tokens still match. A naive switch of the allocation type would hit the `extra != nullptr` refusal. This is real work and its gain on a no-i8mm A78 phone is capped by dotprod-only repack (4x4 variants); on the iPhone the i8mm 4x8 variants apply.
- A thread count of 2 is the number of big cores on both phones, which fits decode (bandwidth saturates early, per the S25 table) but not prefill or the 6 small A55 cores' extra bandwidth; the right number for the moto g is unknown (candidates 2, 4, 6, 8) because heterogeneous cores make added slow threads stall ggml's per-op barrier. Because ggml creates its compute threads from the serving thread and the default threadpool applies no affinity (inferred from `ggml-cpu.c`, not run), a `sched_setaffinity` call on the worker's start thread would propagate to compute threads on Linux/Android; UNVERIFIED and subject to the cpuset the OS gives the process. On iOS there is no affinity API; QoS class is the only lever (not researched).
- Integer dot products are exact, but float accumulation order differs between kernels; `ggml-cpu-impl.h:309` itself notes the emulation "produces the same total sum ... but with different per-lane grouping". Any kernel change can flip a near-tie token against `reference-capacity.json` (F37/F40 already flag near-tie drift); a mismatch then needs triage, not an automatic bug label.

## Q4. What does thermal throttling look like for sustained phone LLM decode, and what could the apps read and feed to a scheduler?

### Takeaway
There is solid evidence that sustained back-to-back GPU inference on phones loses 35-45% of throughput within minutes (iPhone 16 Pro) or hits a hard clock floor (S24 Ultra), but none of it is llama.cpp CPU decode, and this project's own runs are far too short and too idle to say anything: every thermal sample on both phones in every physical run was nominal/NONE. Both apps already log thermal state; the missing pieces are Android thermal headroom, the CPU frequency/placement, and feeding the values into the coordinator between generations.

### Cited Findings
- iPhone 16 Pro, MLX Swift on the GPU, Qwen 2.5 1.5B 4-bit, 20 iterations: Normal (iterations 1-2) mean 37.58 tok/s (peak 40.35), Warm (3-7) 25.31, Hot (8-20) 22.56 +/- 1.14; Warm -37.3% and Hot -44.1% from peak; the Hot state lasted 65% of the run; the 1-second inter-iteration gap was "insufficient to permit any thermal recovery". `ProcessInfo.thermalState` was the state source; no temperatures reported for the iPhone. Galaxy S24 Ultra, MLC-LLM OpenCL on Adreno 750: iterations 1-5 mean 9.93 tok/s with GPU/CPU at 63.0/61.1 C; at iteration 6 GPU 78.3 C, CPU 73.8 C, GPU clock floored at 231 MHz from 629-680 MHz, and inference ended; the paper says sustained back-to-back inference is "not viable on this platform" and suggests duty-cycling. — [arXiv 2603.23640 v1 HTML](https://arxiv.org/html/2603.23640v1) (single model and prompt; abstract: [arXiv abs](https://arxiv.org/abs/2603.23640))
- iPhone thermal states and throughput, MLX on the GPU, several models: relative to the "fair" state, throughput in "serious" fell to 52% (iPhone 12 Pro), 82% (iPhone 13), 72% (iPhone 15 Pro, `iPhone16,1`) and 45% (iPhone 16 Pro Max, `iPhone17,2`); a single "critical" sample on the 16 Pro Max read 5.1 tok/s; both iPads stayed in nominal/fair. The study's app cooled down before each question only if the state reached critical. — [arXiv 2502.08954](https://arxiv.org/pdf/2502.08954)
- Android API facts (Google ADPF page): `getCurrentThermalStatus()` (levels NONE, LIGHT, MODERATE, SEVERE, CRITICAL, EMERGENCY, SHUTDOWN) with a change listener; `getThermalHeadroom(forecastSeconds)` since Android 11 returns 0.0 (no throttling) to 1.0 (severe throttling), more than 1.0 meaning at least severe; call at most once every 10 seconds from a single thread or it returns NaN; NaN on the first call means the API is unsupported; if headroom is 0.85 or more while the status still reads NONE, the status is stale and headroom should be used; guidance thresholds 0.85 (light), 0.95 (moderate), 1.0 (severe); NDK `AThermal_*` equivalents from Android 12; `getThermalHeadroomThresholds()` appears as an Android 15 preview item. — [Android Developers: ADPF Thermal API](https://developer.android.com/games/optimize/adpf/thermal)
- The project's apps: Android registers a `PowerManager` thermal listener (API 29+) and logs status only (`WorkerService.java:171-178`, `EventLog.java:264`); iOS logs `ProcessInfo.thermalState`, Low Power Mode and `thermalStateDidChangeNotification` (`EventLog.swift:362-375, 436`). Neither reads headroom or temperatures, and neither sends thermal data to the coordinator: a grep for "thermal" in `scripts/*.py` and in `WorkerSession.java` finds nothing, so thermal exists only in each phone's exported log (the iOS `telemetry` log row carries `thermal` and `low_power`). — [WorkerService.java](/home/user/ShareCompute/Apps/AndroidWorker/app/src/main/java/com/sharecompute/worker/WorkerService.java), [EventLog.swift](/home/user/ShareCompute/Apps/ComputeWorker/Sources/EventLog.swift)
- Project thermal data: 24 Android thermal events (all `NONE`) and 315 iPhone log rows carrying a `thermal` field (telemetry plus launch rows, all `nominal`) across the four physical runs; compute (prefill + decode) is about 27 s of a 140-560 s run, so each phone is mostly idle, loading or hash-checking. — [docs/evidence/physical-f45-logging/](/home/user/ShareCompute/docs/evidence/physical-f45-logging), [docs/evidence/physical-f48-spans/](/home/user/ShareCompute/docs/evidence/physical-f48-spans), [findings.md F45 section 3](/home/user/ShareCompute/findings.md)
- The Hexagon doc warns its `burst` power mode "may thermal-throttle on sustained workloads". — [snapdragon README](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md)

### Inferences
- Do not transfer the GPU numbers to the project's CPU workers; they bound the problem from above for GPU/NPU paths (a backend switch would add thermal risk, not remove it) but say nothing about two A78 or two A18 cores decoding at a low duty cycle. A 3B / 16-token test that spends about 12 s per run in decode will not throttle; a 10-minute or multi-prompt run is the first thing that could.
- The right early-warning signal differs by OS: iOS has only a four-level state (the cited study sees the loss at "serious", with the 16 Pro Max already unstable at "fair" to "serious"), Android gives a continuous headroom number with a 10-second floor on polling, which is slow compared with a 0.7 s token but fine for between-generation decisions. Note the ADPF page says the status API can lag or stay NONE; the cited blog claim of a 2-5 s lag in sensors is low authority and not used.
- A scheduler feed that fits the "epochs, not mutation" rule (F35) can only act **between generations**: add `thermal` (iOS state / Android status) and `thermal_headroom` (Android) to each phone's heartbeat; the coordinator then (a) delays or refuses a new generation at serious/critical or headroom of 0.95 or more, (b) inserts a cool-down interval, (c) feeds the per-device layer weight that the F49 design already allows ("optional per-device layer weight ... defaults to the memory budget") at the next epoch. Threads cannot be changed mid-generation because the count is set once at server start (`ggml-rpc.cpp:2116-2118`). Design inference, nothing implemented.
- Heat sources the project controls on the phones: screen on with the idle timer disabled (iPhone), foreground service with `PARTIAL_WAKE_LOCK` and `WIFI_MODE_FULL_HIGH_PERF` (Android), and 500 s of Wi-Fi transfer on cold runs; the cold uploads at about 5.7-6.2 MB/s did not move either phone off nominal/NONE.

### Gaps
- No rigorous CPU-only llama.cpp sustained-decode thermal study on an Android phone was found; blog claims (30-40% loss within 90-120 s on a Snapdragon 8 Gen 2, scheduler migrating threads off the big cores on a Pixel 8 Pro) are low authority and mutually inconsistent and were not used.
- Android ADPF `PerformanceHintManager` hint sessions: the page I read does not cover them, so no claim is made about their effect on a native worker thread pool. `getThermalHeadroomThresholds()` availability on this phone (Android 15, SDK 35) is plausible but unverified.
- Skin-temperature, CPU frequency and cluster state during a run are not logged; battery level/charging state is also unlogged and affects thermals.

## Q5. Which quantization per tier, and does Q8_0 for the 3B test model leave speed on the table?

### Takeaway
Yes for speed, no for the capacity proof: Q8_0 is 8.5 bits per weight against 4.5 for Q4_0, Q4_K and IQ4_NL, so a bandwidth-bound decode stage reads about 1.9x more bytes than necessary; but the project chose Q8_0 on purpose because the Q4 3B file fits the Android budget alone (F40) and would not demonstrate pooling. A speed-oriented configuration should pair a Q4-class file with a larger model.

### Cited Findings
- Bytes per block from the pinned `ggml-common.h`: Q4_0 = fp16 scale + 16 = 18 B per 32 weights (4.5 bpw); Q8_0 = 2 + 32 = 34 B per 32 (8.5 bpw); Q4_K = 2x2 + 12 + 128 = 144 B per 256 (4.5 bpw); IQ4_NL = 2 + 16 = 18 B per 32 (4.5 bpw); Q5_K = 176 B per 256 (5.5 bpw); Q6_K = 210 B per 256 (6.56 bpw). — [ggml-common.h (pinned, static_asserts at lines 199, 256, 338, 356, 368, 452)](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-common.h)
- Decode is memory-bound; Qualcomm's example: a 4-bit 7B needs 3.5 GB read per token, so 60 GB/s gives a 17 tok/s ceiling. — [IWOCL 2025 slide 13](https://www.iwocl.org/wp-content/uploads/iwocl-2025-hongqiang-wang-lamacpp-backend-update.pdf)
- Q4_0 is the best-supported format across the accelerator paths researched: Adreno OpenCL "primarily optimized for Q4_0", Hexagon examples use Q4_0, repack and KleidiAI target Q4_0 first (the KleidiAI PR's tables are all Q4_0); OpenCL also lists Q4_K, Q5_K, Q6_K and IQ4_NL as supported. An older copy of the OpenCL doc (search-result summary of a Hugging Face mirror, not re-read) advises `--pure` Q4_0 quantization for best Adreno performance. — [IWOCL slide 10](https://www.iwocl.org/wp-content/uploads/iwocl-2025-hongqiang-wang-lamacpp-backend-update.pdf), [OPENCL.md (pinned)](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/docs/backend/OPENCL.md), [OPENCL.md mirror](https://huggingface.co/Aliguinga01/rule_violation2/blob/main/llama.cpp/docs/backend/OPENCL.md), [snapdragon README](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md), [PR #11390](https://github.com/ggml-org/llama.cpp/pull/11390)
- Project facts: the test model is Qwen2.5-3B-Instruct Q8_0, 3,448.6 MiB; the Q4 file of the same model "fits the Android budget alone", which is why Q8_0 was chosen for the pooling proof (F40); layer placement and byte counts were identical across x86-64 Windows, ARM Android and ARM iOS (F43), and token equality against `reference-capacity.json` held on all three devices. Weights are cached by the phones only if the tensor is 1 MiB or larger. — [findings.md F40, F43](/home/user/ShareCompute/findings.md)
- At the pin, repack tables also cover Q4_K (8x4, 8x8), IQ4_NL (4x4, 8x8) and Q8_0 (4x4, 4x8) in addition to Q4_0, but only for tensors in extra buffers, i.e. not over this RPC worker (see Q3). — [repack.cpp:4925-5121](https://raw.githubusercontent.com/ggml-org/llama.cpp/4da6337767f973e2b4d0797e5b323d77d8565e4a/ggml/src/ggml-cpu/repack.cpp)

### Inferences
- Tier suggestions (all conditional on measurement): **moto g class (2 big cores, about 17 GB/s soft peak, 3.4 GB visible RAM):** a Q4-class file would roughly halve the weight bytes read per token for the Android stage and halve the cold upload (the phones' store rate is about 6 MB/s, so a 1.36 GB stage would go from about 220 s to about 115 s); Q4_0 has the most kernel and accelerator support, Q4_K_M is the usual quality choice at the same bits. **iPhone 16e class (2 P-cores, high bandwidth, 3.4 GB app headroom):** its stage is the least likely to be the bottleneck, so quantization matters mostly for headroom and upload; Q8_0 is acceptable here. **Laptop:** out of scope.
- One file means one quantization for all three nodes, so the per-tier choice is really "which file for the whole pool"; a Q4 model large enough to exceed the 2,048 MiB largest budget (a 7B-class Q4_0 is about 3.5-4.5 GB, e.g. PR #11390's Llama 7B Q4_0 is listed at 3.56 GiB, secondhand) would keep the pooling proof and cut per-token bytes versus Q8_0 for the same capacity claim.
- Token-equality gates lose their meaning at a new quantization: a new pinned reference must be produced, and lower-bit models are more likely to hit near-ties (hypothesis; no measurement here).
- Accuracy cost of Q4_0 versus Q8_0 on a 3B model was not researched; treat Q4_0 as the lowest-accuracy 4-bit option and Q4_K_M as the safer one (general knowledge, UNVERIFIED).

### Gaps
- No measured tokens/s for Q4_0 versus Q8_0 on either phone; no perplexity comparison for Qwen2.5-3B at either quantization.
- No source quantified IQ4_NL versus Q4_K versus Q4_0 CPU speed on A78/A55 cores; the K-quant and IQ4_NL dequantization cost on in-order A55 cores is unmeasured.

### Inferences
- **Checkable in CI or the container, no phone needed:** (1) a regression assertion that the Android and iOS configure logs show `HAVE_DOTPROD - Success` (and `HAVE_MATMUL_INT8` for iOS) after any `GGML_CPU_ARM_ARCH` change; (2) compile and link of every flag combination under the NDK and Xcode; (3) correctness of the dotprod/i8mm kernels and of any RPC repack patch against the token-equality reference by running an arm64 build natively on an Arm Linux CI runner or under QEMU user-mode (feature coverage depends on the host CPU or emulated model; GitHub-hosted arm64 runners being available to this repo is UNVERIFIED) - this checks arithmetic, not phone speed; (4) the source-level claims in this note (repack rejection over RPC, compile-time dispatch, `supports_op` always true); (5) coordinator-side logic for thermal-aware refusal and cool-down, using fake heartbeats.
- **Only the physical devices can show:** tokens/s and per-node busy time per token; the thread-count sweep on the moto g (2/4/6/8) and the effect of `sched_setaffinity` under a foreground service versus an adb-shell process (an adb-pushed `llama-bench` runs under a different scheduling context, so its numbers may not match the app); each core's `Features` flags (SIGILL risk of a raised baseline); measured DRAM bandwidth; whether Adreno 619 runs Vulkan or OpenCL at all and how fast; Metal initialisation and behaviour on iOS 26.3.1 under SideStore signing; Jetsam and Android low-memory-killer margins at a larger model or Metal working set; thermal behaviour over 5-15 minutes with screen on and Wi-Fi active, ambient and charging state recorded; battery; the phone-to-laptop link rate for logits.
- Highest-value first physical step (cheap, no risk): add per-graph busy time to the RPC worker (a timer around `ggml_backend_graph_compute` next to the existing `sc_calls` counter), log CPU `Features` and `cpuinfo_max_freq` on Android, log `hw.optional.arm.*` and `hw.perflevel*` sysctls on iOS, and add Android `getThermalHeadroom` sampling every 10 s; then run the same 3B pair of runs plus one 10-minute loop of repeated generations to get the first sustained-load record.

- Whether the project's repository is public (relevant to free arm64 GitHub runners) was not checked.
